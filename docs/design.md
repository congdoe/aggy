# aggy design

This is the public design of aggy. It says what aggy is, why it exists, and how it works. For the vendor adapter contract, see [adapters.md](adapters.md).

**Status.** aggy is pre-release, heading for v0.1.0. Most of this design is built: read-only borrows, switching under the supervisor with a brief and the limit handoff, Codex edit borrows with `aggy check` and `aggy accept`, tool wiring, shared permissions, and OpenCode on screen. Parts not built yet say so where they are described, such as the commands inside a session (section 5) and the helper (section 9). Section 18 shows each milestone and its status.

## 1. What aggy is

aggy is one command that opens a real Claude Code, Codex, or Grok Build session on that vendor's subscription. You run `aggy` instead of `claude`, `codex`, or `grok`. The program on screen is always the official CLI, with its own tools, permissions, slash commands, and model picker.

aggy adds three things around those CLIs:

- **Switch.** Move the on-screen work to another vendor, for example when one hits its plan limit, with a handoff that does not depend on the vendor being left.
- **Borrow.** Send one bounded task to the vendor best suited to it (image, video, research, news, review, or edit) and get a short report back, without leaving the current session.
- **Parity.** Make every CLI see the same project rules, lessons, task state, and safety rules, so a switch lands in the same project instead of a stranger's.

Why: people who pay for more than one coding agent usually live in one of them. When that one runs out for the week, the others sit idle, and moving work by hand loses context. Some work also suits another vendor better: image and video generation, web research, and current news about tools. aggy lets that work go where it fits, using only the CLIs you already run.

## 2. Constraints

These are requirements, not preferences.

- **Official binaries only.** aggy launches the unmodified installed `claude`, `codex`, and `grok`.
- **Vendor sign-in only.** Each CLI signs in with its own flow: `claude` then `/login`, `codex login`, `grok login`.
- **No credentials.** aggy stores conversation ids, connection status, and its own index. Its goal is to never read, copy, or store OAuth tokens, session tokens, passwords, or credential files. A file-access guard enforces this for the vendor credential files (section 13).
- **No model requests.** Only the vendor CLIs talk to their vendors. aggy never calls a model to classify a task, summarize a transcript, or write a brief.
- **No proxy unless the user turns one on.** aggy never routes vendor traffic through anything unless the user explicitly turns on a local proxy tool (T6780, section 9): for one named vendor, at a terminal, after a warning and a typed confirmation. It is off by default, never runs for a borrow child, and is only a loopback process aggy started and health-checked, reached through that vendor's own base-URL variable. Otherwise aggy never sets `ANTHROPIC_BASE_URL`, `OPENAI_BASE_URL`, or `GROK_MODELS_BASE_URL`, and runs no compressor proxy of its own. A proxy sees every request, the login token included: running one through aggy carries the same risk as running it by hand, and aggy's part is the lifecycle, the health check, the scope, and saying so.
- **Subscription, not API.** If `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, or `XAI_API_KEY` is set, setup warns that the CLI may bill the API instead of the subscription. Settings that route a CLI to an API key or another endpoint, such as Grok's `endpoints.xai_api_base_url` (which its image and video tools use) and Codex's `openai_base_url`, are flagged by setup and `aggy doctor`; aggy never sets them. [adapters.md](adapters.md) lists every one checked and its source.
- **No service, no telemetry.** The project runs no hosted service, relay, or account system, and aggy sends nothing to the project. Each user runs aggy on their own machine against their own subscriptions. aggy makes no model or vendor API calls of its own. The only network surfaces aggy itself opens are planned, opt-in ones (section 13).
- **Any subset of vendors.** Setup works with one, two, or three vendors. A skipped vendor is absent from switching, borrows, usage, and tool wiring. The default vendor must be a connected one.
- **Per-repo allowlist.** A repo can list the vendors allowed to see it. A brief, borrow, or switch never sends that repo's content to a vendor outside the list.
- **Turn boundaries.** Switches happen after the current turn finishes. An in-flight shell or test belongs to the vendor process and stops when that process exits.
- **Vendor state stays put.** Hidden reasoning, tool-call ids, permission prompts, and the vendor's own todo list stay in the vendor session that created them. They come back when that session is resumed. They do not move to another vendor.
- **One hop.** aggy refuses a borrow from inside a borrow; a child with a shell can still bypass it (see section 7). Native same-vendor subagents still run.
- **One writer.** Only one process edits the main checkout. Edit borrows and parallel editors get their own git worktrees. A worktree is not a sandbox: isolation from the rest of the disk comes from each CLI's own sandbox and permission settings.
- **macOS and Linux first.** Windows needs ConPTY and different sandbox behavior, so it comes after 1.0.

## 3. Concepts

| Term | Meaning |
| --- | --- |
| Vendor | `claude`, `codex`, or `grok`. Each has its own subscription, tools, and session store. |
| Parent | An aggy session. It has a title, a directory, a last-active time, and the vendor that was last on screen. Many parents can exist, and several can share a directory. |
| Child | A real vendor session started inside a parent, interactive or a borrow. aggy stores the vendor's session id and its last-active time, taken from the modified time of the vendor's session file so a crash or sleep does not lose it. |
| Task file | `.aggy/task.md` in the working directory: goal, done, next, decisions, files touched. The on-screen agent keeps it current at step boundaries. It is the main input to a brief. |
| Brief | Optional handoff text, written to a file the new child is told to read. Never a command-line argument. |
| Borrow | One bounded task run headless in another vendor. The on-screen agent stays put and gets a short report. |
| Kind | What a borrow is for: `image`, `video`, `research`, `news`, `review`, or `edit`. |
| Routing table | A per-kind ordered list of vendors in config. It is aggy's only routing logic. |

## 4. Parents and children

`aggy sessions` lists parents with their directory, last vendor, and last-active time.

- `aggy` with no arguments starts a new parent in the current directory, as `claude` starts a new session, on `default_vendor`, else the first vendor connected, never the last one used, so it stays predictable. `aggy run <vendor>` starts a parent there on that vendor.
- `aggy <vendor> [flags]` (generic over the vendors; `aggy claude --model x`; `aggy opencode` passes none of OpenCode's own flags yet, only aggy's) does the same with the CLI's own flags: every flag goes to the CLI for that session, after aggy's own arguments, except what the adapter's `PassFlags` table takes over or refuses ([adapters.md](adapters.md)). aggy takes over `--model` (it goes on the child's row), `--continue`, and `--resume`, and refuses what clashes with what it passes at launch (`--session-id` and so on). The words keep their order, after aggy's own launch flags, so the CLI reads them as it would typed to it (T6961): a bare word directly after a flag that takes a value is that value (the table's `Values`, `Variadic`, and `Checked`), and any other bare word is the session's first prompt, which starts it with a turn running. The prompt is the person's own argv, so aggy passes it as typed; it never goes in a record (the launch logs only that there was one) and a later launch of the session never sends it again. A first prompt word that names one of the CLI's subcommands is refused, since the CLI could run it instead of the session aggy records: the prompt goes after `--` then, which reaches the CLI as typed (that Claude reads `--` as the end of its options is commander's convention, unverified, TODO(T6708)). A prompt with `--continue` or `--resume` passes on Claude only, where the reference shows `claude -r "<session>" "query"`; on Codex and Grok it is unverified, so it is refused. OpenCode takes no prompt yet.
- `aggy [flags] [prompt]` (no vendor word) is the same on the default vendor, chosen as bare `aggy` chooses it: `aggy --model opus`, `aggy "explain this repo"`. aggy's own command names come first, so `aggy review` is aggy's command and `aggy -- review` is a prompt, and a lower-case word one edit from a command (`aggy sesions`) is refused as a likely typo, as `claude udpate` is. `aggy -c` and `aggy -r` take the CLI's flags after them too, sorted by the vendor of the session they reopen, which the launch knows only once it has found it.
- Print mode (`claude -p`, `grok -p`, `--prompt-file`, `--prompt-json`, `codex exec`) and a stdin that is no terminal (`git diff | aggy -p "review"`, any script) are not sessions aggy can supervise: aggy runs the CLI on the person's terminal (`execrun.RunDirect`), with the stdin, stdout, and exit code untouched, no supervisor, no switch key, and nothing in the index. It still adds what it adds on screen: the safety policy (refused, as on screen, where it cannot be applied), the shared rules, the shared memory, and the configured model when none is given. It takes over none of the CLI's flags there, so `-c`, `-r`, `--model`, and `--session-id` mean what they mean to the CLI, and `aggy -c` in print mode is the CLI's own `--continue`; aggy's `-r <id>` is refused there, since an aggy id is no CLI session. The flags that defeat the policy still need `--no-policy`. A `cli.direct.exited` record says such a run happened. Bare `aggy` with no arguments still starts a new session and never resumes; with a stdin that is no terminal it is the CLI's own reading of that stdin. A flag that could get past aggy's safety policy or hooks needs `--no-policy`, and aggy notes and logs it at launch; one that only asks less passes where the vendor documents that deny rules hold (`--allowedTools`, `--permission-mode auto` on Claude), and a few pass with a line at launch, such as Codex `--profile`, since forcing `--no-policy` to keep a daily profile drops the whole policy (adapters.md). A resume of the same session keeps the flags, except the ones only `--no-policy` let through, since it drops `--no-policy`; a switch keeps none.
- `aggy --continue` (`-c`) reopens the session last active in the current directory that can still be reopened, looking through every parent there, and refuses when there is none, as `claude --continue` does. `aggy <vendor> --continue` does so for that vendor. `aggy --resume [id]` (`-r`) is `aggy resume`, except that with no id it refuses as `--continue` does.
- `aggy resume` reopens the latest parent in the current directory. `aggy resume <id>` reopens that one (a unique prefix of its id is enough), wherever it is.
- `aggy new` starts another parent in the current directory. The old one stays listed.
- Resume launches the child that was last on screen (the parent's most recently active interactive child) with that CLI's resume flag, in that child's directory, and injects no brief unless `--brief` is set: `aggy resume --brief` writes the child's brief to `.aggy/briefs/<child-id>.md` (through the `.aggy` rule, redacted) and tells the child to read it, and `aggy resume --brief --show` prints that brief and launches nothing. `aggy resume <id>` also takes a child id from `aggy session`, a borrow's included (section 7), which puts that child on screen instead of the latest, so a return brief has the turns other CLIs added since it was last closed; the latest child's brief says nothing was added. The briefs folder holds a `.gitignore` of `*`, so briefs stay out of git; the repo's own ignore files are not touched, and one already in the briefs folder that is not `*` (a cloned repo may ship it) is kept with a warning. A prefix that matches both a parent and a child is ambiguous and refused, and a child picked by id that is gone from the index when the launch refreshes it is an error, never a silent new child. It first takes the child's lease; if another live aggy holds it, resume refuses and says so. A new Claude or Grok child gets its id in advance (`--session-id`); a new Codex child cannot, so its id is recorded when the hook claim and the new rollout agree (table below); a Codex child whose id was never recorded is not resumable, and aggy says so and starts a new Codex child.
- If the vendor no longer has that session, aggy says so and keeps the parent's other children.
- Claude sessions are tied to their directory, so a child whose worktree was removed is closed, not resumable.
- A child's last-active time is its vendor session file's modified time, read with a stat when aggy lists or resumes sessions and after a CLI exits, so a crash or sleep of aggy loses nothing; a time more than five minutes in the future is capped when stored and not trusted when read. aggy never reads the file, never follows a symlink inside the vendor's sessions folder, and goes through `safefs`. The folders are under the vendor home recorded on the child at launch: Claude `projects/*/<id>.jsonl` under `~/.claude` (unverified layout; the cwd's folder is tried first), Codex `sessions/<YYYY>/<MM>/<DD>/rollout-*-<id>.jsonl` under `~/.codex` (source-verified; every day from the child's start through today, the date folders listed once per refresh), Grok `sessions/<encoded cwd>/<id>/` under `~/.grok` (newest entry). A child's state is worked out each time and never stored, since what it rests on can be temporary: **running** while a live process holds its lease (nothing else is checked), **closed** while its directory is missing, **gone** when a recorded layout's sessions folder has no file for it, or when no Claude project folder has its file and aggy never saw one for it (a Claude session quit before its first message is likely never saved, and resuming it would fail every time; the child row keeps a `file_seen` bit, schema version 11), **unknown** when the folder is missing, or a Claude file aggy saw before is missing now (resume still tries), else **open**. Resume starts a new child for a closed or gone one.
- Parents are matched by the directory's canonical form (`safefs.CanonicalPath`), so another spelling of it finds the same parent. A parent records its directory's device and inode: when the directory was removed and made again (a re-clone), `aggy resume` starts a new parent there and says how to reopen the old one, `aggy --continue` skips the old one, and `aggy resume <id>` warns.

`aggy session` lists the children of the open parent (the supervisor's, named by `AGGY_PARENT`, else the latest in the current directory): vendor, kind, title, model, last active, and status. `aggy sessions` shows directories to the local user and never prints a vendor session id or an env value; neither list goes into `aggy doctor --report`. Borrows are children too. The same list is the picker when one vendor has several children.

Inside a harness, a linked skill prints either list. Each vendor owns its built-in slash commands, and aggy adds only the commands in section 5, "Commands inside a session" (T6908 to T6911).

Session ids per vendor, checked against claude 2.1.311, codex-cli 0.164.0, and grok 1.0.70 unless marked unconfirmed:

| Vendor | New session | Resume | Notes |
| --- | --- | --- | --- |
| Claude | `--session-id <uuid>` | `--resume <id>` | `--fork-session` branches instead of reusing the id. |
| Codex | No pre-assigned id | `codex resume <id>`, `codex exec resume <id>` | Headless, the first `codex exec --json` event is `thread.started` with the `thread_id`. Interactive, any process the CLI starts can reach aggy's socket (section 11), so a hook alone never names the session: a thread id a Codex hook reports (`SessionStart` or `Stop` `session_id`, source-verified; hooks run only once the person has approved them, since Codex trusts hooks by hash and never one passed with `-c`) is a claim, kept only when the socket found the hook's process in the on-screen CLI's process tree (peer-pid lineage, section 5). That a Codex hook runs inside that tree is unverified: no Codex hook has been seen to fire live (verification.md, "Still open" 2 and 10). That tree also holds the agent's own tool subprocesses, so a nested `codex exec` passes it too (approving hooks partway through a session, or a `SessionStart` that misses aggy hook's 3 s bound, can let its claim come first). So a claim is recorded only once `$CODEX_HOME/sessions/<YYYY>/<MM>/<DD>/` holds a rollout of that id that was not there at launch and whose first line, its `session_meta`, has `source` `"cli"`: the interactive TUI sets it, where `codex exec` writes `"exec"` and a sub-agent an object (source-verified at rust-v0.164.0: `tui/src/lib.rs#L753`, `exec/src/lib.rs#L744`, `protocol/src/protocol.rs#L2959`, written first by `rollout/src/recorder.rs#L1936`; not yet seen live, TODO(T6616)). Only one process holds a vendor session at a time. The holder is recorded as a lease in the store. A borrow or event that targets a busy session waits for its turn to end, or uses `--fork` to branch instead. Two writers on one transcript corrupt it.

## 5. The supervisor and switching

aggy stays running as the parent process. The supervisor holds the vendor CLI in a pseudo-terminal and passes it straight through to your terminal. It draws no screen of its own. `exec` cannot work: once aggy replaces itself with the CLI, nothing is left to perform a switch, and a skill alone cannot cleanly end the CLI it runs in.

**The switch key.** `Ctrl+\` opens the switch menu. It is configurable, and pressing it twice sends it through to the CLI. It is not a known shortcut in any of the three CLIs (unverified: not yet in verification.md). Claude already uses `Ctrl+B` and `Ctrl+]`, which rules out tmux's default prefix. It is set as `[switch] key = "ctrl+<k>"`, where `<k>` is a letter or one of `\ ] ^ _`; keys that already mean something are refused: interrupt, end of input, and suspend (C, D, Z, Y), Backspace (H), Tab and Enter (I, J, M), Esc ([), flow control (S, Q), and line editing (U, W, V, R, O). aggy recognizes it as its control byte or, once a CLI turns on the kitty keyboard protocol, as its CSI-u press report (`ESC [ 92 ; 5 u` for Ctrl+\, with or without Caps or Num Lock, even split across two reads). Inside a bracketed paste it is data. A second press within 400 ms sends one switch key to the CLI; other input within that time opens the picker and goes to it. The picker pauses the pass-through both ways. When the CLI is on the main screen, the picker draws on the terminal's alternate screen, going there once per open, since xterm's `1049h` saves the cursor each time and a second one would lose the CLI's, so closing it puts the vendor's screen back without anyone redrawing it. The alternate screen does not nest, so aggy follows the CLI's own switches to it (`CSI ? 1049`, `1047`, or `47`, then `h` or `l`, across reads) and, while the CLI is on it, draws the picker over the CLI's top lines instead, then makes the CLI repaint with a resize to one row fewer and back. It lists the vendors in `switch.order` that `aggy setup` recorded and did not find signed out, except the one on screen; Esc, Ctrl+C, or the switch key closes it. Picking a vendor queues a switch to it for the turn end; opening the picker again shows it, Esc there cancels it, and picking it again says no turn is running (an Enter that started no turn leaves no turn end to wait for).

**A switch:**

1. You press the switch key and pick a vendor, a linked skill requests a switch (`aggy switch <vendor>`), or a vendor reports its limit (T6667).
2. The supervisor waits for that vendor's end-of-turn hook, then types `/exit` into the session.
3. With `--brief`, the brief builder writes `.aggy/briefs/<child-id>.md`.
4. The adapter launches the next CLI inline and, with a brief, tells it to read the file.

Typing into the user's session is input injection, so step 2 is guarded. A switch never interrupts a turn. It goes on only when all of these hold:

- a turn of this CLI has ended since it launched (below);
- a turn-end hook of the vendor on screen has arrived since the last Enter the user typed (or none was typed since a launch that started no turn). That is `Stop`, Grok's `StopCancelled`, or `StopFailure`, it must be marked as from the session (peer-pid lineage above; for Codex, whose hooks have not been seen to fire live, unverified, section 11), and its payload must name the on-screen child's own session id: the pre-assigned id for Claude and Grok, and for Codex the id the index recorded (section 4). A nested `claude -p` or `codex exec` run by the agent's shell inherits `AGGY_SOCKET` and `AGGY_VENDOR`, and its own `Stop` names its own session, so it does not count; nor does any turn end of a new Codex child before its id is recorded. aggy cannot scrub `AGGY_SOCKET` from the CLI's own tool subprocesses, so the id is the check. A `/clear` or an in-CLI `/resume` moves the id, as "Following the CLI to another session" below says;
- no other hook from the session is holding it. Any other event (`SessionStart` aside), in practice a `Notification`, which Claude and Grok send when they wait for the user, a permission prompt among others, holds the switch until the user has typed to the CLI and a turn has ended since. A later `Stop` alone does not clear it: a nested CLI's `Stop` can follow a prompt that is still open. Claude's idle reminder holds nothing: its `notification_type` is `idle_prompt`, "Claude finished responding about 60 seconds ago and you haven't typed since" (`hooks.md`, verification.md). It clears no hold either, so a forged one lets nothing through. Every other type holds, and all of Grok's, whose values are not recorded. A pick past a hold says at once why it waits. Besides answering the prompt, the way out when nothing is waiting on screen is Esc at that note, Enter on the empty prompt, and picking the vendor again, which spends no turn, where sending a message would spend one on a vendor perhaps being left for lack of quota. That Enter would answer an open prompt, so the note says it is only for then. A permission prompt's own `Notification` comes about six seconds after it opens (`hooks.md`), so a status line can show first; the status line asks the user to look;
- the user has typed nothing after their last Enter. Only a plain Enter counts as sending: a `\r` that ends what was typed, not preceded by Esc (Option+Enter, a newline in Claude) or by a backslash (backslash then Enter, also a newline, even across two reads), and not inside a bracketed paste (its markers are found even when split across reads). Nor does an Enter after an `@`, a leading `/`, or Ctrl+R (history search, unverified) since the last send: it may only accept an entry in the CLI's file, command, or history popup and leave the text, with more than was typed, in the composer, so from then on the prompt counts as holding text, Enter after Enter, until an Enter on a line the user explicitly emptied: with Ctrl+U (assumed to clear the composer line, unverified), or with Backspace down to nothing while aggy still knew the length (before any such Enter). Either counts only when no cursor key (Esc and the sequences it starts, Ctrl+A, B, E, F, N, P) or newline (Enter after Esc or a backslash, Ctrl+J) came since the `@` or the last Ctrl+U, and a Ctrl+U only when it cleared text: the `@` may be on another line, or after the cursor, and survive. Then the way out is Backspace down to nothing, or typing again and clearing that with Ctrl+U. A cursor key, yank (Ctrl+Y), undo (Ctrl+_), or a Ctrl+U on an empty line (some composers join the line before) after any `@` since the last send may put the cursor back in its token, so the prompt counts as holding text again. In a paste, an `@` followed by whitespace in the same paste leaves the cursor outside its token (assumed, unverified), so it does not count; one at the paste's end does. A turn-start hook such as `UserPromptSubmit` could confirm a send, but aggy installs none yet, and any process in the tree could forge one. Tab never counts as sending, on any CLI: on Codex it submits or queues most text ([chat_composer.rs#L3531](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/tui/src/bottom_pane/chat_composer.rs#L3531)), but idle not a `!` command (the same lines), and a `$` popup takes it (the same file, read by the reviewer), and elsewhere it may complete a word. So a message Tab did queue leaves the unsent-text note until Ctrl+U and an Enter: a false note costs a keystroke, and `/exit` on a draft costs the draft. An Esc types nothing, but an Esc on an empty composer, and an Enter after it, leave the prompt in doubt on every CLI, with any cursor keys between and however long ago the Esc came. Text typed after one Esc ends that, the everyday interrupt. After two it does not: Codex's preview takes `h`, `l`, `j`, `k`, and Ctrl+T as its own keys (`app_backtrack/legacy_input.rs#L195`, source only). Codex takes Esc, Esc, Enter there as a backtrack, which puts an earlier prompt back in the composer (`tui/src/app_backtrack.rs` at 6aaac694, source only, not seen live). When in doubt aggy counts the prompt as holding text. So aggy splits what it knows from what it does not. **Known text** is any text it counted since the last Enter, popup or not, so `hi @bob`, `/mod`, and a line typed after `/cost` are all known: the exit command would be sent along with the draft, so aggy says so once and waits; the user sends the text, or clears it (Ctrl+U or Backspace) and presses Enter on the empty prompt, and picking the vendor again does not clear it. Only text counts: printable characters, UTF-8 characters, what a paste holds, yank and undo, and the same keys reported as CSI u, so a CLI in kitty's report-all mode types nothing unseen, and its Enter is an Enter. Control bytes and function keys do not. Shift+Tab, Page Up, Page Down, Ctrl+C, D, K, L, O, and T change nothing aggy counts (assumed for the page keys and Shift+Tab, unverified). Every other key, such as a newline, an arrow, Home, Tab, Ctrl+W, or one aggy does not know, may move the cursor or change the text in a way it cannot follow, so until the next Enter no Ctrl+U or Backspace lowers the count, and a Backspace with none counted counts as text (Up may have recalled a line). The way out is Ctrl+U and an Enter; if that Enter sends what was left, the person sees it, and it is theirs. **Doubt** is what is left: an Enter a popup may have taken, with nothing typed since, a line cleared but not confirmed, an Esc on an empty composer, such a key with no text counted (Up then Down, a `/model` picker's arrows). Doubt does not block, since the person can see the screen and aggy cannot. The first pick brings a note saying aggy cannot tell if the prompt is empty, and to look (`switch.prompt_in_doubt`); picking the vendor again brings the status line, which says the same (`can't tell if the prompt is empty`), and only then can the switch key type the exit command. A key to the composer after that needs a new look. In doubt the status line names the command in front of the end of its keys (`Ctrl+\ types /exit, Esc stays.`) when the longer line would not fit, shortening until it does at 80 columns, with new session and brief on and for any vendor a switch can go to. A tool change's resume has no re-pick, so its status line says it alone.

**Local commands.** An Enter on a command Claude's docs list as starting no model turn leaves the prompt free, so the next message is an ordinary Enter at it and a turn end from that message is evidence: `/clear`, `/model`, `/usage`, `/cost`, `/status`, `/help`, `/config`, `/permissions`, `/memory`, `/context` (`adapter.LocalCommand`, each cited there; `commands.md`, read 2026-11-07, not seen live). Only an exact whole line, typed with no cursor key, edit, or paste, at the prompt. `/compact` is out, since it may run a turn, as are skills, custom commands, and any command with arguments. Other vendors' tables are empty; Codex must stay so, since its `SessionStart` comes inside a turn. What can go wrong: such a command may open a dialog aggy cannot see, so its doubt stays until a turn end, and the first pick over an open `/model` picker brings the note, not the status line. A user's own skill taking one of these names (unverified; a live check settles it, T6895) would start a turn aggy treats as none: `atPrompt` stays true during it, so the doubt note can open and hold that turn's output until a key, which the rule above forbids, and the status line still asks before anything is typed.

**A pick that waits.** A notice must never hold output while a turn may be running, so a pick that waits because an Enter may have started a turn, or a message may be queued, shows nothing further. The telling is in the list, which the person opened: it says a turn may be running or a message queued, that aggy switches when it ends, and that picking the vendor again goes on if nothing is running. If the prompt is in doubt the list says that too, so the next pick is also the confirm, and it takes two picks and not three. Nothing is held for the whole wait, however quiet the CLI is, and someone who picks with the number key without reading sees nothing until they open the list again or a turn ends. A turn end while the list is open blanks those words. Since the list promised that turn end, a person told of the doubt gets the status line at it, with its `can't tell` words, and needs no second pick; with no key since, a turn end stands for the look. Up counts as text for the queue, since Up and an Enter may send a line from history, so a turn runs after the first turn end; on an approval's menu that is a false wait, the safe side.

**An interrupted turn** (T6968). Claude's `Stop` "does not run if the stoppage occurred due to a user interrupt" (`hooks.md`), and its docs name no other hook for one; Grok sends `StopCancelled` with reason `user_interrupt` (`10-hooks.md`), which already counts as a turn end (not seen live for an interrupt); nothing is recorded for Codex or OpenCode. So a pick after Esc used to wait for a turn end that never came. Now a lone Esc sent while a turn of a CLI that has ended one runs (not at the prompt, no hold, no open ask), followed by `interruptQuiet` (2 seconds) with no output and no key, and no message queued, counts as a turn that may have ended, for a switch that waits, and for nothing else (`settleInterrupt`): aggy takes the CLI as at its prompt, with the composer in doubt, so the status line says it cannot tell if the prompt is empty and only the switch key types the exit command. A pick from the list, which promised a turn end, goes straight to that status line, as at a turn end; an agent's or a limit's switch gets the doubt note first. It is never a counted turn end: before the first one, aggy still never types the exit command into a possible launch dialog, and the list's words to quit by hand stand; notices that wait for `inputSinceTurn` still wait; any key, Enter, or hold after the Esc, or a message queued in the turn, drops it. What can go wrong: an Esc that interrupted nothing (one that closed a menu inside a turn), then a turn silent for two seconds, brings the status line over a running turn; the person sees the turn running, and Esc there keeps it. A live check (T6895, verification.md) should confirm that Claude goes quiet and back to its prompt after Esc.

A counted turn end settles doubt when it is evidence. It must come at least a second after the last Enter (`settleTurnGap`): sooner, it is more likely an interrupted turn's late `Stop`. With no input since the last Enter, an Esc before that Enter is over. If that Enter also went with the CLI at its prompt, a turn ran from it and sent what was there, so the composer is empty: an `@file` in a message and a `/compact` that ends a turn leave no doubt. So does an `@file` whose first Enter a popup took and whose second sent the line, as an earlier Enter at the prompt with a popup up, and no turn end since, counts for the Enter that sends. `@fi` and an Enter a popup took start no turn, so no turn end comes and the doubt stays. An Enter sent while a turn runs is no evidence, since it may answer an approval or queue; a queued message's text has left the composer, but one a popup took has not. What can go wrong: a turn the Enter did not start ends a second or more after a popup took it (a background task's, a scheduled prompt's), so aggy calls a composer empty that holds text, and the plain status line and its `See <CLI>'s prompt?` are all that is left before the exit command goes in with it. A turn end from elsewhere is not counted, since it must name the session on screen; one forged from the same depth can do the same, which section 11 already assumes. Nothing runs if the person does not press the switch key;
- the CLI's output has been quiet for a second;
- the user's typing has been quiet for a second;
- the vendor still passes the repo's `allowed_vendors`, its CLI is on `PATH`, and, unless `[policy] required = false`, the safety policy can reach it. That needs a probe of the CLI's help, which runs in the background for each vendor the picker offers from launch on (and again when the picker opens or a switch is asked for, if one failed), so the supervisor never stalls on it; the picker says it is checking, and nothing is offered until the probe has succeeded. A failed probe is reported and tried again on the next pick. A switch never carries `--no-policy` over: the next child gets the policy, or the switch is refused with the reason.

**Following the CLI to another session** (T6901). `/clear` and the CLI's own `/resume` put the CLI on another session id, and turn ends then name that one. The id is what keeps a nested CLI's `Stop` from counting, so it moves only on evidence, and only forward: aggy looks at `SessionStart`, and takes a move only if both hold:

- **What it says.** Its `source` is `clear`, `resume`, or `fork`, and it names another valid id. Claude's docs define those values: "`clear` after `/clear`", "`resume` for resumed sessions", "`fork` for a new session forked from an existing one", and `SessionEnd`'s reasons say the session ends on `/clear` and "via interactive `/resume`" (`hooks.md`, read 2026-11-07, doc-verified; that `session_id` is then the new session's is what `/clear` starting a new session implies, not stated, and unverified live). Codex's schema has the same values (source; which of its commands sends which is unverified). Grok records no `source`, so there any `SessionStart` from the right place counts (unverified). `startup` and `compact` never move it.
- **Where it ran.** The socket keeps the pid chain of each hook up to the CLI. The first and shallowest hook naming the on-screen session sets the baseline. A move must come from the same depth, through the same processes above the hook's own shell. A nested `claude -p` or `codex exec` runs below the agent's shell tool and has its own process, so it is deeper. So is its forged `clear`. With no baseline yet, no move is taken. A move refused is recorded as `hook.follow_refused`, and the switch then waits as before. Until a turn end naming the session on screen is counted, the list says a hook reported a move aggy could not confirm, so turn ends may not count, and gives the way out that works: picking the vendor again when a turn end has been counted since launch, else quitting the CLI by hand. A Codex session reopened with `/clear` as its first command has no baseline, so it lands here.

**Attacks on this, and what is left.** A nested CLI's real hooks, with a forged source or not, fail on depth, and its `Stop` stays foreign. A nested `claude -p --resume <the on-screen id>` names the on-screen id and is deeper, and the baseline only ever gets shallower, so it cannot lower the bar. A tool that pipes JSON straight into `aggy hook` from its shell runs as deep as a real hook, and it passes. That gives it nothing it did not have: the on-screen id is in the CLI's own arguments, so it can already forge a `Stop` naming it, and a switch still asks the user on the status line. It can also stop real turn ends counting until the person picks the vendor again, as a forged `Notification` can hold a switch today. So the follow protects against accident, not against a hostile tool in the tree, which is what section 11 already assumes. Whether real CLIs spawn every hook from one process at one depth is unverified; if not, moves are refused, which is where aggy was before this.

A move changes the id and nothing about a turn, on every vendor: Codex sends `SessionStart` inside `run_turn` (`core/src/session/turn.rs#L340` at 6aaac694, source only, not seen live), so the move can come with the first message after `/clear` already running. It settles one thing, the doubt its own command left, a leading `/` making its Enter count as maybe unsent, and only when the composer has held nothing but that command since the last clean send, with nothing typed after its Enter but the keys of a `/resume` list. Otherwise the doubt stays, until the next turn end that is evidence, or the note and a second pick (below in the unsent rule). A hold still stands, and a move does not count as a first turn end. Neither `/clear` nor `/resume` ends a turn, so after a move with no message the next turn end, or picking the vendor again, offers the switch. The list says so before that pick ("A pick that waits"), since a note here could hold a running turn's output, on Codex above all; a typed `/clear` on Claude does not wait, as a local command leaves the prompt free.

**What resume reopens.** Claude's own `--continue` opens the latest conversation, so aggy's does too: as the CLI exits, the row moves to the id it was on, with its lease, so `aggy resume`, a switch back, and a brief all see the session after the `/clear`. That id reaches a CLI's argv, so it takes more than a hook's word: its session file must be where this child's directory keeps its sessions, with no scan of other folders (Claude's project folder for the cwd, whose name is unverified, so a miss only leaves the row; Grok's encoded cwd folder), and for Codex its rollout's first line must say the TUI wrote it, in this directory (`rolloutInDir`: `source` and `cwd` of `SessionMeta`, [protocol.rs#L3275](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/protocol/src/protocol.rs#L3275)), which a nested `codex exec` never does. So a `/resume` into another repo's session leaves the row alone. This guards against a mistake, not against a tool that can write to the vendor's folder, which could as well rewrite the session aggy would resume. With no file, such as a `/clear` and no message after it, the row stays on the session with turns. An id another child holds stays off this one, so a `/resume` into a sibling leaves the row alone; its turn ends still count while it runs. So does a Codex `/resume` into a rollout dated outside the child's date window. The turns before the `/clear` stay in the vendor's own session list, and leave aggy's. Another source of evidence, such as OpenCode's (T6953), calls the same `followSession` with its own `via`; nothing does yet, and a `SessionStart` sent to OpenCode's socket moves nothing. On OpenCode a click is no typing (its plugin reports what a click answered), so it clears no hold, and one between the exit command's letters and its Enter counts as typed in that gap, so no Enter follows. An open ask comes before a hold in what a pick says, since the hold's way out, an Enter, would choose Allow once on a dialog.

**Without hooks** (T6848). When aggy has no `Stop` hook for the vendor on screen, for any aggy binary, a launch warns on one line, the list says so and names `aggy hooks install`, and an agent's `aggy switch` is refused (`switch.hooks_missing`) rather than waiting forever. A picked switch is not refused, since quitting the CLI by hand still completes it (below). A limit from a hook cannot arrive without them. Any hook that does arrive overrules the check. Hooks that call another aggy binary, or part of the set with `Stop` among them, are not refused: the launch, `aggy hooks status`, and `aggy doctor` say which it is (`installed for another aggy binary`, `partly installed`), and `aggy hooks install` fixes either. Codex's hooks also need the person's approval, which aggy cannot see, so it only warns.

**A launch that has ended no turn.** aggy does not read the screen, so it cannot tell a CLI's prompt from a dialog it shows at launch, and on such a dialog the Enter after `/exit` could answer it: Codex's update prompt defaults to "Update now" ([update_prompt.rs#L131](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/tui/src/update_prompt.rs#L131)) and its trust dialog to "Trust and continue" ([onboarding_screen.rs#L195](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/tui/src/onboarding/onboarding_screen.rs#L195), [trust_directory.rs#L87](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/tui/src/onboarding/trust_directory.rs#L87), at rust-v0.164.0; whether that Enter accepts them is not tested). So until a turn end of the on-screen child is counted since this CLI launched, aggy never types the exit command. A resumed session starts the same way. Enter does not count, since it may only have answered a dialog, and neither does a turn end that does not name the on-screen child's session, or a limit on its own (a `StopFailure` naming the child counts as the turn end it is). A notice must never hold output while a turn may be running, and without a counted turn end only a launch given no input and no brief has none. So the telling is in the list itself, which the person opened: while no turn end has been counted it says aggy will not type into a possible dialog, that to switch they quit the CLI themselves within ten minutes and it must exit cleanly, and that after a message aggy asks at that turn's end if it sees one. The reason is recorded as `switch.no_turn_yet` at the pick. Any input to the CLI counts as possibly starting a turn, so on this path no encoding of Enter (CR, `CSI 13 u`, a paste) needs recognizing, and picking the vendor again says nothing about a turn here. A terminal's own replies to the CLI are not input and do not close a note: focus events, cursor and device reports (DA1, DA2, DSR, DECRPM, the kitty keyboard query), whole OSC, DCS, and APC strings (OSC 11, XTVERSION), the mouse wheel, and a move with no button held, in SGR or X10 encoding. The key filter takes them apart from the keys around them, in one read or split across reads: a sequence that has begun and could still be one waits up to 50 ms for its next read, reaches nobody until then, and goes on as input if it never ends, so a reply's digits never pick a vendor. A lone Esc does not wait, so a split just after Esc counts as typed. A mouse click or a drag is input, since aggy cannot say what it does, but it types nothing, so it never counts as unsent text. If nothing has been sent and no brief was given, the same words also come up as a note once the CLI and the typing have been quiet for a second, for someone who picked with the number key without reading. Otherwise nothing further shows: there is no status line for this, since one on the bottom row cannot be taken back once the CLI has drawn, shares the CLI's cursor save slot, and can scroll into history. So someone who picks without reading, after typing to the CLI, sees nothing until they open the list again or a turn ends. Once told, the CLI's clean exit completes the switch, at any moment, as the list said; it does not wait for quiet or a probe. Exit code 0 with no signal aggy got is clean, and the vendor must still pass the checks that do not need a probe: a crash, a signal, even one arriving with the exit, or a vendor no longer allowed ends aggy with the CLI's code and a line saying why, and a cancel ends aggy as usual. A pick older than ten minutes also ends aggy with a line saying so, and the list says it has expired if reopened: where no turn end is ever counted nothing else ends it, and a quit long after, for another reason, should not land in another CLI. Any signal aggy has got since the CLI launched stops a switch, even one from long before, since a signal can race the key that confirms: a signal to aggy never leads to launching the next CLI. Before the exit command is typed, a note says so and the CLI keeps running; after, the exit ends aggy with a line. A session picked in the list is checked as a confirmed switch's is, and one no longer recorded ends aggy with a line saying so. A counted turn end closes the note and brings the status line that asks, and from then on the usual rule holds: a CLI that exits with nothing typed ends aggy. So someone who switches right after opening a CLI does one more step, and the list names it. Where no turn end can arrive, as on Codex until the person has approved aggy's hook (section 11), quitting by hand is the only route. A switch the agent asked for, a limit, or a tool change waits for a turn end without a note, since quitting by hand is no answer to a question the person has not been asked.

**Other notices.** The same rule holds after the first turn. A limit's note and a tool change's note wait while `atPrompt` is false or any input has gone to the CLI since its last counted turn end, in any encoding, and until the CLI is quiet; a near-limit warning under the same conditions is dropped until the next turn end. A message queued during a turn starts its own turn as that one ends, so a turn end with an Enter or a Tab with text sent while `atPrompt` is false (Tab queues on Codex: [chat_composer.rs#L3531](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/tui/src/bottom_pane/chat_composer.rs#L3531)) leaves `atPrompt` false until the next turn end. An Enter on an empty prompt does not count, since it answers an approval or a menu, and nor does one after cursor keys alone, as Down and Enter do at an approval. If that next turn end never comes (the text answered the CLI's question, so nothing was queued), ten seconds with no output and no typing releases it. That a running turn keeps drawing is unverified on all three CLIs, so one that runs silent that long can have its output held. Pressing a vendor again in the list says no turn is running, and releases it too. A limit's note that has not shown is dropped by a clean `Stop` on a vendor with a hold signal, and the switch list, where the suggested vendor is preselected, says the limit was hit; where no turn end is ever counted the note never shows, and the CLI's own limit error and that list are the signal. The unsent-text note needs input to exist at all, so it is the one that relies on recognizing Enter: CR, kitty's `CSI 13 u` and keypad `CSI 57414 u` with any modifiers, and xterm's `CSI 27 ; m ; 13 ~`. An encoding outside those, which no CLI is known to use, would let it hold. Which encodings Claude and Grok turn on is unverified.

A marked hook is still only a hint: a nested CLI's `Stop` can arrive mid-turn, and a CLI waiting on a permission prompt is quiet. So aggy then asks, on one status line on the terminal's bottom row, drawn with the cursor saved and put back (on the CLI's alternate screen the CLI repaints afterwards), so whatever the CLI shows, an approval prompt or menu included, stays in view. The line reads `aggy: <who asked>, <options> -> <vendor>. <switch key> switches, Esc stays. See <vendor on screen>'s prompt? It types /exit.`: first who or what asked (the agent, a limit, or a limit only a hook reported, labeled unverified) and the switch's options (new session, model, brief), so a narrow terminal, which cuts the end, never hides them; then the keys, then the check and what aggy will type, and whether that command is unverified. Without an origin or options the line fits 80 columns. It takes the bottom row, which may hide the CLI's footer or the last line of an approval menu while it shows (TODO(T6684)). Only the switch key confirms, never Enter, and only once 500 ms have passed since the overlay opened. Esc drops the switch, once 50 ms show it is not the start of a longer key, which is then handed on whole (so Esc pressed twice within 50 ms goes to the CLI, both presses). Any other key closes the overlay and goes to the CLI as typed, through the same key filter as other input, so a user who was typing loses nothing; the switch still waits. The same holds for aggy's notes, except that the switch key there opens the picker list, where Esc cancels a switch. Confirming types the exit command through the same input queue as the user's keys. aggy sends no Esc first to clear a menu: what Esc does at each CLI's prompt and approval menus is not in verification.md.

The exit command is `/exit` for every vendor: live on OpenCode (verification.md, "OpenCode under aggy"), unverified on Claude, Codex, and Grok (adapters.md). If the CLI has not exited 10 seconds later, aggy says so and leaves it running; it never kills it. The switch stands, so a CLI that exits later still switches, unless the user opens the picker and presses Esc. A CLI the user quit for a switch still waiting ends aggy with a line saying it did not switch, except as above. Once the CLI exits, the next vendor goes on screen through the same launch as `aggy resume`: the parent's latest interactive child of that vendor resumed, or a new one, with its own lease, the repo's `allowed_vendors`, the policy, and memory. It gets a brief, a new child, another child, or a one-launch model only when the switch asked for one (below). If that launch fails, aggy exits with the error, and the parent stays listed. aggy's terminal reader is kept across the switch, so keys typed during it reach the next CLI. So do the terminal's late replies to queries the old CLI sent (cursor position, device attributes), which the next CLI may see as stray input; known, not handled. Typing `/exit` and the quiet gap are not yet checked against each CLI (T6684).

**A CLI that never starts.** When the CLI switched to closes with no turn end counted and aggy can see where its session file would be and finds no sign of it (a new child's file not there, in a layout recorded as verified, so Claude's unverified project folders say nothing yet; a resumed session's file unchanged since the launch; for a new Codex child with no id, no new rollout at all), it never got past its launch dialogs, or was quit before its first message: the two look the same to aggy, which does not read the screen. A `SessionStart` hook is no evidence, since whether a CLI sends it before its trust dialog is unverified. Going back takes that positive evidence: a sessions folder that is not there (an unmounted disk, or a vendor's first run) says nothing, so aggy keeps the row and ends as usual. A vendor's first declined dialog can therefore end aggy; a row lost is worse. And a new child's file counts whatever its time says, since its id is new. aggy then says so on one line (`switch.never_started`), reopens the CLI before it on the same session (when aggy never learned that session's id, the line says it opens a new one of that vendor), with what that launch had (as the resume for a tool change does: its `--tool` names, model, and safe flags, not `--no-policy`), and removes the new child's row, so it never becomes the parent's latest. Going back costs one more quit if the person meant to leave; a CLI gone with no way back would lose the session on screen. A signal to aggy, or a CLI killed by a signal (exit code 128 or more), never reopens anything. A launch that was not a switch has nothing to go back to and ends aggy as usual. Separately, for `aggy resume` and `aggy --continue` a child with no session file now and none ever seen, or with no session id at all, does not count as a parent's latest, nor its parent as the directory's latest, when anything else there can be reopened; on its own it still gets the usual note. A child with no id may have had real turns, so opening an older session past it says so on one line. Whether Grok exits 0 on `n` at its dialog is not recorded, and the rule does not rest on it. `aggy doctor` warns when Codex's config records no trust level for the folder, or one other than `trusted`, from the `[projects."<path>"]` table only (a linked worktree's entry is under its main checkout, so the wording says "may"). Credentials are never read to learn it.

A `/aggy` command with no model turn opens on the alternate screen, as the picker does, and Esc returns to the CLI, so its output stays out of the conversation. Keyboard-only commands have no skill the model can call, so an agent cannot accept its own edit or widen its own permissions. Commands that change vendor config or remove things (`setup`, `unwire`, `hooks`, `policy`, `mcp`, `memory`, `attribution`, `skill`, `gc`, adding or removing a tool, and a tool's proxy) stay in a terminal, and `run` and `--direct` only make sense there. Each CLI's own commands (`/model`, `/clear`, `/compact`) stay its own, and aggy does not rename them across CLIs.

Claude and Grok turn a skill into `/name` (Claude `skills.md`; Grok `user-guide/04-slash-commands.md`, "Skills as Slash Commands", grok-build `2bdd1d6a`). Codex at rust-v0.164.0 cannot: a skill or plugin adds a `$name` entry, a plugin's `commands` are converted to skills (`core-plugins/src/command_migration.rs`), and an unknown `/name` is refused on Enter, with no prompt sent and no hook run (`tui/src/bottom_pane/slash_commands.rs`, `chat_composer/slash_input.rs`). So `$` is the form native to Codex, and `/switch` there exists only because aggy catches it first.

aggy catches these from the user's keystrokes in the pass-through (T6908, `internal/sessioncmd` parses, `catchCommand` in the supervisor catches), so a switch costs no model turn and works when a vendor is out of quota. On a command typed in full, aggy holds back the Enter, clears the composer with Ctrl+U (as CSI u, `ESC [ 117 ; 5 u`, when the terminal reported the Enter that way, and the Enter's release is dropped too), and acts; nothing reaches the CLI. Ctrl+U clearing the composer is unverified on every CLI (not yet in verification.md). "In full" is what the composer tracker knows whole: printable keys typed since an Enter that left the composer empty, with no paste, cursor key, edit, history recall, newline, or Esc among them, ended by an unmodified Enter that comes alone in its read, as a person's does; on Claude and Grok not while the CLI is on the alternate screen, where the keys go to an editor or pager it opened. So a person who runs Claude or Grok fullscreen gets the menu and hook path only, never the key catch (whether either CLI's fullscreen mode draws its composer there is unverified; TODO(T6895), a live check). When the tracker is blind or in doubt, aggy passes the Enter through. After an Enter a popup may have taken (any `/` line the CLI ran as its own command), the tracker does not know the composer is empty, so the next command typed in full goes to the CLI until a turn end settles it: a known limit. Two cases are known: a Claude command its docs list as starting no turn (`adapter.LocalCommand`, the local commands rule above), typed whole, leaves the composer empty, and a prompt aggy's hook blocked (below) leaves it empty too (unverified, as below); after either, the next command typed in full is caught. Of Claude's local commands only `/clear` counts so (T6975, `promptFree`): `commands.md` says it starts "a new conversation with empty context" and describes no dialog, while `/model` "opens a picker", `/config` and `/status` open "the Settings interface", `/permissions` "an interactive dialog", and `/memory` edits CLAUDE.md files, so a dialog may still have the keys and a caught command's Ctrl+U would go into it; `/usage`, `/cost`, `/help`, and `/context` show a panel or display whose focus after it the docs do not say, so they take the same safe side. After any of these the next command goes to the CLI until a turn end. Codex, Grok, and OpenCode have no such list recorded, so there the miss stays; a live check that a given command's Enter leaves their composer empty (type it, then `/switch` and Enter, and see no turn) would add it to `adapter.LocalCommand` (TODO(T6895)). A command's words are letters, digits, and `. _ : / + = -` only, at most 256 bytes; anything else is no command. Pasted text and terminal reports (focus events, query replies) never count as a command. The line and its Ctrl+U together typed nothing, so a caught command leaves the prompt as it was: a switch it queues at the prompt goes at once, never waiting for a turn end the command did not start. A miss must be harmless: on Codex, `/switch` gets "Unrecognized command", and a skill reached through a CLI's menu, whose inserted text aggy may not see, goes to the model, which says so and changes nothing. A skill exists mainly so the command shows in the CLI's menu (T6910: `skills/switch`, `skills/borrow`, `skills/inbox`, beside `skills/aggy`), and sets `disable-model-invocation: true`, which Claude documents as keeping the description out of the context until the person invokes it (`skills.md`) and Grok's skills guide lists with the same meaning (`user-guide/08-skills.md` at grok-build `2bdd1d6a`, read 2026-11-09, verification.md); Codex has no such key that is recorded, so there each command skill's frontmatter, kept under 80 tokens, is paid every turn while linked. `aggy skill link` links them with the aggy skill, for every session of that CLI, through the manifest, so `aggy unwire` takes them out; unlinked, nothing of them is left and they cost nothing. Grok's `[skills] ignore` holds every one of them in one list when Grok alone is unlinked (a one-line list grows and shrinks by its own entries; one written across lines is refused). Outside aggy, the switch and inbox skills tell the model to change nothing and to say a session started with `aggy` takes them; the borrow skill runs `aggy borrow`, which works anywhere. Picking from a CLI's menu is the natural way to use one, though, and those keystrokes do not spell the command. So on Claude and Grok a `UserPromptSubmit` hook is the second catch (Claude's docs also list `UserPromptExpansion`, fired when a typed command expands, with the original `prompt`; `aggy hook` handles it, and the supervisor takes a repeat of the same command for the same Enter once, but `aggy hooks install` does not install it: that Claude at the recorded version accepts that event in `settings.json` is unverified, and a settings file it rejected would break every launch, so it waits for a live check, T6895; whether a skill picked from the menu fires `UserPromptSubmit` is unverified too): `aggy hook` reads the `prompt` field (Claude `hooks.md`; Grok's field name is not in its hooks guide, so unverified), parses it as the keys would be, and for a command with no model turn hands only that line to the supervisor (`prompt-command` on the socket, from the session's process tree only), which parses it again and takes it only with the Enter it goes with (R121): the last key was an Enter at the prompt, on a line that held only a leading `/` command (what a menu's pick submits), within 10 seconds, with no key since, and only one command per Enter; and the keys before that Enter could have picked that command from the CLI's menu (T6975, the typed-prefix rule below); never over aggy's list, page, or picker already on screen, nor a switch over one waiting. Anything else is refused (`command.no_enter`) and the prompt goes on to the CLI, so another process in the tree cannot open a page that takes the person's keys, or mark the CLI at its prompt during a turn. The supervisor answers within 2 seconds, inside aggy hook's 3, or the prompt goes on. When the supervisor takes it, the hook prints `{"decision":"block", ...}` (with `suppressOriginalPrompt` on Claude), which both CLIs document as stopping the prompt before the model, its reason shown to the person and not added to the context: JSON on stdout, since aggy's hook command ends in `|| true` and no exit code survives it. A blocked prompt ends no turn, so the Enter that sent it, taken as above, leaves the CLI at its prompt again, and its line out of the composer (both CLIs document a block as stopping the prompt; that the composer is then empty is unverified, TODO(T6895)), so a fill from a list works after it. A hook can be forged by any tool process, so a switch caught this way always asks on the status line (saying `/switch via hook`); before the first turn end it only opens the picker; and the commands that change something (`accept`, `check`, `reject`, `tool`, `permissions`, `trust`) are never taken from it, so they reach the CLI and its skill. On Grok a hook that times out lets the prompt through to the skill (`10-hooks.md`: a timed-out hook fails open). Codex cannot use it while hooks run in another process, so a command picked from its `$` menu reaches the model until that is fixed. OpenCode: docs/verification.md records that it loads `~/.claude/skills` and `~/.agents/skills` (fake-model) but nothing about its commands or a prompt hook, so there aggy relies on the keystroke catch alone, and whether these skills show in its menu is unverified.

**The typed-prefix rule** (T6975, `menuPick` in the supervisor, `sessioncmd.Picked`). A pick from a CLI's menu is spelled by the text typed before the menu keys, so aggy keeps that text: the printable keys typed since the line began, until the first Up, Down, or Tab. After Up or Down only more of them, a Tab, or the Enter may come; after a Tab, the arguments as printable keys (and Backspace within them). A paste, Esc, Left or any other cursor key, Ctrl+U or another control key, a click, a newline, a Backspace anywhere but the end of what was typed, a menu key before any text (Up there recalls history) or after a space (the command word has ended), and text after Up or Down before a Tab all spoil it, and the hook's command is refused. A command the hook reports is taken only when that text is `/` and at least one letter of a command word, and the word starts the reported command's name (`/s` or `/sw` for `/switch`, `/ag` for `/aggy`, `/in` for `/inbox`); once a space ends the word, it must be the name whole, as no menu completes it then. A bare `/` followed only by arrows is refused: `/` is a prefix of every command, the person's own included, so taking it would let a forged request name any of aggy's commands after any menu pick. No two of aggy's commands share a first letter, so one typed letter names at most one of them. The arguments aggy acts on are the reported command's only when they are, word for word, what was typed (after the word's space, or after the Tab); a Tab completes the command's name, never its arguments (unverified, so a line with other arguments is refused). So `/`, `s`, Down, Down, Enter; `/sw`, Tab, `grok`, Enter; and `/in`, Tab, Enter are taken, and a forged `prompt-command` sent after the person's own `/deploy`, `/review`, `/compact`, or `/clear` names nothing they typed and is refused. What is left: a forger can still claim, within 10 seconds of that Enter, the one aggy command whose name the person's typed text starts, with the arguments they typed (after `/s`, Down, Enter on Claude's `/status`, a `/switch` that asks on the status line; after `/a` on `/agents`, `/aggy`'s list). That Up and Down in a CLI's menu move in the menu, not through history, with a `/` word typed is unverified. A switch caught from the hook still always asks on the status line.

**Models in `/switch`.** The picker groups models under each on-screen harness, and `/switch <model>` goes straight there; this chooses what a launch starts on, and a session's own model change stays with the harness. Moving to the other harness carries the brief and starts on that model: OpenCode takes `model` in `OPENCODE_CONFIG_CONTENT` for a new session (a resumed session keeps its own), alongside the policies and `--auto`, and `mini` takes `-m`. A model that is denied silently falls to another allowed one with exit 0, and aggy can only check after the first prompt, so it says if they differ; a plugin reporting the model is untried. Its list comes from `opencode models`, limited to the person's plans and keys, and that output is not documented as stable. Picking another model on the same harness points to that harness's own model command, which keeps the session; headless runs kept context going between Grok and GPT both ways. `mini` has no such command, but its Ctrl-P menu has "Switch model". Changing a running session from outside would need a server aggy owns, whose password reaches a key, so that waits. Claude Code has no known command that lists its models, so aggy keeps a short list and re-checks it with each version check (unverified).

`/vendor` was the planned switch command and was never built. What it was to do is built in the picker and in `aggy switch` (below), and `/switch` (planned, above) is to take the same options:

- Picking a vendor resumes the latest interactive child of it in this parent, or starts one, and injects nothing.
- `n` starts another child of that vendor and keeps the others listed.
- `m` takes a model for one launch and does not write config. Inside a running harness, its own `/model` still changes models.
- Several children of one vendor open a list limited to this parent.

Opening the list while a switch waits shows that switch's options, so picking it again keeps them, and a toggle there changes them. In the picker these are keys: a number (or Enter) picks a vendor; `n` toggles a new child, `b` a brief, and `m` takes a model name for this one launch (checked as a model name, at most 128 bytes, since it goes to the CLI's argv; never written to config). A vendor with more than one interactive child in the open parent then lists them (latest first, by short id, last active, and title): a number picks one, Enter the latest, `n` a new one. A linked skill may ask for a vendor, a brief, and tools only, with `aggy switch [--brief] [--tool NAME]... <vendor>`: a new session or a model is the user's choice, so `--new` and `--model` are refused, by the command and by the supervisor (O56-1). Tools (at most 8 names) are on for the next launch only, as with `aggy run --tool`; the confirmation the user answers names them ("tools a,b"), so the user takes or cancels them with the switch, and the repo's `tools_off` and a per-repo tool's scope still win at that launch (T6708). The picker has no tool toggle yet. The choice goes with the pending switch, so the status line notes it (a long model name is cut first, so the keys stay in view), and the launch after the exit applies it (the model checked again there). The picker's lists are read in the background every 2 seconds through one read-only handle on the index, held for the launch, so a child picked from them is checked again, off the main loop, once the switch is confirmed and before the exit command is typed: one no longer recorded is refused with a note (`switch.child_gone`), and the CLI stays on screen. A child removed after that check and before the launch's plan (an `aggy gc` while the CLI exits) still ends with the old CLI exited and the launch refused; that window is inherent.

**Scrollback.** Claude renders inline, and aggy launches Codex and Grok with `--no-alt-screen` (unverified for both: `docs/verification.md` has no row for it; Grok always gets it, and Codex only when a probe at launch finds it in `codex --help`), so the previous vendor's output stays in your terminal's scrollback after a switch. aggy does not redraw the thread. The transcript stays on disk for `aggy log` and later briefs.

**Terminal transparency.** The pass-through must carry window resize, bracketed paste, image paste, Shift+Enter and the kitty keyboard protocol, mouse, clipboard (OSC 52), links (OSC 8), notifications (OSC 9 and 777), truecolor and wide characters, and Ctrl+Z. A checklist covering these runs before each release in common terminals, with and without tmux. `aggy --direct <vendor>` (also `aggy run --direct <vendor>`) launches a CLI unwrapped for when the pass-through breaks something: it runs on aggy's own terminal in aggy's process group, with no pseudo-terminal, raw mode, switch key, or picker, and the same environment rules as the pass-through. The supervisor socket still listens, so the index is still updated through hooks; aggy catches Ctrl+C and `Ctrl+\` (the terminal already sent them to the CLI), passes on a TERM or HUP, and returns the CLI's exit code. Switching needs the pass-through, so a direct session cannot switch.

**How the pass-through works.** `aggy run <vendor>` starts the CLI through `internal/execrun` (`StartPTY`) in a new pseudo-terminal at the user's terminal size, puts the user's terminal in raw mode, and copies bytes both ways unchanged. aggy acts on nothing that passes through except the switch key and a command typed in full at the prompt ("Commands inside a session", below), which it holds back from the CLI; it follows the rest only to know the composer (above), and passes it on unchanged. SIGWINCH passes the new size on; SIGINT, SIGQUIT, SIGTERM, and SIGHUP sent to aggy are forwarded to the CLI's process group; the CLI's exit code (128 plus the signal number when a signal ended it) becomes aggy's. The terminal is restored on every exit, on a panic, and around a suspend. Ctrl+Z is a byte for the CLI: the CLI leads its own session in the pseudo-terminal, so its process group is orphaned and the kernel discards a SIGTSTP it sends itself, as it does for a CLI run as a tmux pane's command. If the CLI is stopped anyway (SIGSTOP), or aggy gets SIGTSTP, aggy restores the terminal and stops, and on `fg` re-enters raw mode, passes on the size, and resumes the CLI. What each CLI shows on Ctrl+Z is on the release checklist (T6684).

The CLI gets the user's whole environment, since it is the user's own session; aggy adds only `AGGY_VENDOR` (the vendor on screen), `AGGY_SOCKET` (the supervisor socket), and `AGGY_PARENT` (the parent id, which names the socket), and `StartPTY` refuses any other variable. Its allowlist is separate from the borrow runner's: an on-screen CLI never gets `AGGY_DELEGATED`, and a borrow never gets the socket. aggy never adds an API key or anything else, and adds a `*_BASE_URL` only for a local proxy tool the user turned on for that vendor, while the proxy aggy started for the session runs (T6780, section 9).

**Dependencies.** The stdlib cannot open a pseudo-terminal or set raw mode without `ioctl` calls that the `syscall` and `unsafe` bans keep out of aggy, so two pinned modules do it. `github.com/creack/pty` v1.1.24 (MIT, no dependencies, no cgo on darwin or linux, the most used Go PTY package) opens the pseudo-terminal, starts an `exec.Cmd` in it, and sets its size. It opens `/dev/ptmx` itself, outside `safefs` (section 13). `golang.org/x/term` v0.47.0 (BSD-3-Clause, Go project) sets raw mode and reads the size. `github.com/aymanbagabas/go-pty` was rejected: it wraps creack/pty on Unix and pulls in `golang.org/x/crypto` and `u-root` for its SSH support. The Windows port (after 1.0) adds a ConPTY `StartPTY` behind a build tag, through creack/pty's Windows support or a small ConPTY file; the supervisor only sees the `Child` interface.

**The supervisor socket.** Hooks (`aggy hook <event>`) and linked skills reach the supervisor at `run/<parent-id>.sock` in the state directory: a Unix socket, mode 0600, in a directory aggy keeps at 0700 and owned by the user (a looser one is tightened, another owner's refused). It speaks newline-delimited JSON, one request per line and at most 64 KiB: `ping`, `tools-changed` (from `aggy tool on|off`, accepted from any process of the user's; it only makes the session read its tools again, section 9, T6729), `hook-event` (vendor, event name, and the fields aggy keeps from the hook's JSON object), and `switch-request` (a vendor to switch to at the turn end, sent by `aggy switch <vendor>` from a linked skill; accepted only from the session, when the vendor is one the picker offers, and passes `allowed_vendors` and `PATH`; then waits for the turn end and the user's switch key like a picked switch, the status line saying the agent asked. It is refused while Codex is on screen: Codex sends no hook when it waits for an approval, so a `Stop` forged by any tool process in its tree (which passes the lineage check, and can read the session id) would be indistinguishable from a real turn end, and only the user, looking at the screen, may start a switch there (TODO(T6617)); a second request while one waits is refused, and `aggy --direct` refuses them all). Unknown fields, a second value on a line, or a bad value get an error reply and the connection is closed; so does a connection idle for 10 seconds. Each connection's peer uid and pid are read (`LOCAL_PEERCRED` and `LOCAL_PEERPID` on darwin, `SO_PEERCRED` on Linux, all taken at connect) and anything but aggy's own uid is closed unanswered; elsewhere every connection is refused. **Peer-pid lineage.** The supervisor also walks the peer's parents (sysctl `kern.proc.pid` on darwin, `/proc/<pid>/stat` through `safefs` on Linux, no cgo), at most 64 steps, looking for the on-screen CLI's own pid; a request whose sender gets there is marked as from the session. The answer is worked out once, at accept, before any request is read, and is bound to the process that connected, not just its pid: on Linux through its pidfd (`SO_PEERPIDFD`, Linux 6.5; only a kernel without the option, `ENOPROTOOPT`, falls back, and any other error, such as `EINVAL` for a peer that has exited, means not from the session), else, and on darwin, through its start time, read before the walk and checked again after it, so a pid that a process outside the tree hands on and frees, and that the CLI's next tool then gets, does not count. On the start-time path, a reuse between connect and that first read is not caught: normally microseconds, but unbounded if a process of the user's SIGSTOPs aggy. darwin's audit token (`LOCAL_PEERTOKEN`) carries a pidversion, but nothing aggy may call (no cgo, no `unsafe`) reads a live pid's pidversion to compare it with, so darwin keeps that gap. The walk pins each ancestor too: a parent must have started no later than its child (darwin `p_starttime`, Linux `/proc/<pid>/stat` field 22), so an ancestor that exits mid-walk and whose pid a newer process takes ends the walk. A connection not from the session is closed after its first request, so it cannot wait, pinging, for a pid to come round. This proves "came from this session's process tree", not "came from the CLI itself": the CLI's tools, a nested `claude -p` or `codex exec`, or the agent piping JSON into `aggy hook` are in the tree too, while a process reparented after its parent exited falls out. Any failure (no pid, no process identity, a process gone mid-walk, another OS, the CLI not started within 2 s) is "not from the session": session-id claims and switch requests then fail closed, and other hook events are still passed on, unmarked. Codex id claims are further checked against the rollout (section 4), and T6664 must treat a turn-end or limit event from the session as a hint, and act only on one marked as from the session. While the supervisor runs it holds an flock on `run/<parent-id>.lock`; a new supervisor that gets the lock knows the old one is dead (an flock cannot be fooled by pid reuse) and removes its socket, and one that cannot is refused. Since the old supervisor unlinks the lock file while holding it, a lock taken on a file no longer at the path does not count and is taken again. Anything at the socket path that is not a socket is left alone. aggy removes both files when it exits.

**Limit handoff.** When the on-screen vendor reports its limit (a recorded limit signal, section 11), aggy preselects the first vendor the picker offers (`[switch] order`, connected, allowed) that has no limit recorded (the router's skip rule); in the list it is marked `>`, Enter takes it, and the brief toggle starts on. A limit only a hook reported (`StopFailure`, which any process in the tree can send) is unverified: the status line and notes say so, it is recorded with `via` `hook-unverified`, and it gets the rules of an agent's request; Codex's rollout limit stays as it is. The preselect lasts until it is used or turned down in the list, the switch it queued is offered, or, for a vendor with a hold signal, a turn of the session ends without a limit. Where the vendor on screen has a hold signal (Claude, Grok), aggy also queues that switch, with a brief, like an agent's request: it waits for the turn end and the other conditions above and is offered on the status line, where one key, the switch key, accepts; nothing is ever confirmed for the user. Codex has no hold signal, and its limit, like an agent's request, could be forged from its tree, so there aggy only shows a note naming the vendor with quota: the switch key opens the list, Enter picks it, and the switch key confirms at the turn end. With no vendor left aggy says so. A limit on one model only is not verified, and counts for the whole vendor (TODO(T6617)).

**Near-limit warning** (T6699). Hand off before the limit, not after: at a turn end of the on-screen child (its own session id, as for a limit), aggy reads how much of the on-screen vendor's limit is used, off its main loop, and once the CLI is at its prompt and quiet, when that is `[switch] warn_at` or more (a share from 0 to 1, default 0.9; 0 turns it off and nothing is read) it shows one status line on the bottom row, drawn as the confirmation is (DECSC/DECRC, never the last column): `aggy: codex is at 92% of its limit. Ctrl+\ hands off to grok, Esc dismisses.`, naming the first vendor the picker offers that has no limit recorded (or saying none has quota). A narrower terminal gets the first shorter form that fits (`aggy: codex 92%: Ctrl+\ -> grok, Esc`, then `Ctrl+\ -> grok, Esc`, then `Ctrl+\ / Esc`): vendor and share stay in view down to 40 columns, the keys down to 13. The switch key opens the list with that vendor preselected and the brief toggle on, as after a limit; Esc dismisses; any other key closes the line and goes to the CLI. Nothing switches by itself: a pick waits for the turn end, unsent text, and the user's confirmation like any. It shows once per crossing. A crossing ends when the reset time of the window it warned about has passed, or a later reading of that same window is below `warn_at`; a lower share read from another window or another rollout does not end it. A reading of another window that resets sooner than the warned one and is at `warn_at` or more is a new crossing and warns, so a stale weekly reading (another rollout's, read before the session's own) cannot mute the 5-hour window for days; the warned reset only moves sooner, so two windows never take turns. A reading of a window of the same length whose reset is at most 60 seconds sooner is that same window read again, not a new crossing (T6811). One read runs at a time: a turn end while one is in flight reads again once it lands; a read in flight for more than 30 seconds (say, on a hung file system) is given up on, the turn end starts its own, and the old answer is dropped when it lands. An Esc still pending when the warning gives way to a limit's note does not close the note. A limit of the vendor on screen ends the warning too: one on screen gives way to the limit's note, and none follows it for that crossing (which then ends on any reading below `warn_at`). A turn started, a switch already waiting, or the picker open skips it until the next turn end. Only a vendor whose CLI writes what is left on this machine can warn (section 16, `aggy usage`): today Codex. The share comes from the same rollout read as `aggy usage`, the on-screen session's own rollout first once its thread id is known, and the rollouts' tails are parsed again only when one of those read changed. Codex's turn end is its `Stop` hook, which runs only once the user has approved aggy's hook in Codex (section 11); without it, Codex never warns.

## 6. The brief

A brief is opt-in (`--brief`). It is built without a model, because the vendor being left may be out of quota. It holds:

- the task file, if present
- the latest turns verbatim, read from the vendor's transcript on disk
- `git status` and `git diff --stat`
- tools the previous harness had that this one lacks
- the path to the full transcript, which the new child reads on its own quota if it needs more

The first visit to a child gets all of that. A return to a child gets the task file plus only the turns other vendors added since it was last closed.

Lines matching secret patterns are removed. `--brief --show` previews it. The brief is a file, never an argument: 200,000 tokens is about 800 KB, and macOS `ARG_MAX` is 1 MB including the environment.

Grok bills a whole prompt at the long-context rate once it reaches 200,000 tokens. aggy keeps a Grok brief well under that by dropping older turns (not summarizing them) and pointing to the transcript. There is no local Grok tokenizer, so the count is a conservative character estimate. A session can still grow past the threshold after launch, so the lasting guard is Grok's own compaction setting.

When an adapter cannot read a transcript, for example after a format change, the brief degrades to the task file alone, and says it could not read them. A brief never claims what aggy does not know. A child that never started (section 5) holds no turns and is passed over, for the next session that has some. A session whose id aggy never recorded, such as a Codex child whose hook is not approved, may hold real turns, so the brief names it and says they could not be read, never that no CLI ran or that there is no earlier session. `--brief --show` launches nothing, so its notes say what a launch would do.

Two common uses:

- **Quota handoff.** In the picker, Codex with `n` and `b` (a new child and a brief) continues the same work on Codex. The Claude child stays listed. (`/switch codex --new --brief` is planned, section 5.)
- **Side trip.** Grok with `n` opens a blank child for a small task. Claude with `b` returns to Claude and adds only what Grok did.

## 7. Borrows

From the on-screen agent, a linked skill runs `aggy borrow <kind> "<task>"` in the agent's own shell, in the background where the harness supports it. It is a shell command, not an MCP tool: long headless runs would hit MCP tool-call timeouts, and a shell command works the same in all three harnesses.

aggy routes the kind (section 8), runs that vendor's CLI headless (`claude -p`, `codex exec`, `grok --prompt-file`) with `AGGY_DELEGATED=1`, and returns a short report to the conversation and to `aggy inbox`.

- The borrow prompt is the task, the paths, the constraints, and today's date. It does not include the parent transcript. The child's exploration stays in that child.
- A borrow is a child, so it appears in `aggy session`, and `aggy resume <child id>` puts a review, edit, image, or video child on screen once it has ended, for a follow-up question. Research and news children are refused (`borrow.no_screen`): they never get file-reading or MCP tools, an on-screen session has them, and the transcript may hold text from the web; `aggy inbox` has the report. (Decision for the owner to review, section 21.) The others resume in their own directory, since Claude and Grok keep sessions per directory: a review's repo, an edit's worktree (refused once removed), or the empty temp dir of image and video, which ended with the borrow and is made new for the session and removed after, its files with it; a level of it already there is refused. On screen it is the person's session: the borrow's lockdown flags do not apply, what it may do is up to the CLI's own permission settings, and aggy says so at launch. An edit child's worktree loads no `.aggy/memory.md`, since no one has reviewed it, but the CLI still loads its own project files from there (`CLAUDE.md`, `AGENTS.md`, `.claude/settings.json` and its hooks; which, per CLI, in a worktree is unverified), which the child may have written, and the launch note says so; `aggy accept` refuses a worktree changed since the borrow ended, as the launch note says; and `aggy accept`, `check`, and `reject` refuse while the child's session is open, as `aggy gc` does. It takes no brief. That `codex resume` and `grok --resume` reopen a headless session on screen is unverified. The switch picker and `aggy --continue` still offer only interactive children.
- Read-only kinds (`image`, `video`, `research`, `news`, `review`) never write the repo. Every kind but `review` runs in a fresh, empty temp directory, outside any git work tree, with its CLI's lockdown flags (adapters.md). `review` runs at the root of the git work tree in plan mode: `--permission-mode plan` on Claude and Grok, `--sandbox read-only` with the full Codex lockdown on Codex, which leaves Codex no tool that reads a file. So every reviewer gets its input in the prompt: aggy runs `git diff` against the merge-base with the default branch (or `--base <ref>`) and reads the `--path` files, caps the total at 256 KiB, and fences it as data to review, not instructions. Claude keeps its read tools at the work tree root, and Grok does only outside `$HOME`: in a repo under `$HOME`, aggy's `~` denies below refuse `read_file` and `list_dir` too (live, grok 1.0.77; verification.md T6922; `grep` has the same rule, unverified), so such a review works from the diff and files in its prompt, and its report says so. It fails closed: a loss of quality, not a leak. The rules stay, since without them a spelling such as `~//.grok` reads Grok's auth file. Grok auto-allows reads in every permission mode and its `read_file` takes any absolute path, so a Grok review runs under `--sandbox strict` with aggy's `~/Library`, Grok home (where its auth file lives), and (on darwin) `/System/Volumes/Data` read denies, and is refused on a host without Grok's kernel sandbox. Those two dirs are guarded by permission rules only, which Grok matches on the path as spelled, so aggy also denies every `~` path, every path with a part that starts with a quote or white space, case-folded copies on darwin, and the dirs' physical forms. That is source only, pending a live canary check (verification.md S9). These broad denies have other false positives: a Grok reviewer cannot read a repo path with a part that starts with `~` (an Office `~$x.docx` lock file, a `~foo` dir) or with a quote or Unicode white space, and reviews such a file from the diff alone. A Grok review is also refused, and Grok passed over, when the repo holds config Grok would load and run (hooks, MCP, LSP, plugins, agents, workflows, `.envrc`), since the sandbox does not stop a hook; it is not refused for project instructions or skills (`AGENTS.md`, `CLAUDE.md`, rules and skill dirs). That refusal (C17-10) was dropped in T6742: instructions run no code, and the reads a hostile instruction could ask for are the same ones the diff under review, attacker text in any repo, could ask for. The sandbox and denies refused those under `$HOME` live (verification.md, rows S2, S4, and S5), and a gate on instruction files never closed what strict leaves readable. Symlinks stay refused, in two cases. First, when an instruction, rules, or skill file Grok would load is a symlink, sits under one, or holds one, the review is refused. Grok loads such a file with no permission check and follows the link, so `AGENTS.md -> ~/.grok/auth.json` would put the token in the prompt. Second, Grok's cursor rules (off by default) load `.md` and `.mdc` files from `<dir>/.cursor/rules` of any dir Grok reads in and follow a linked `.cursor` or `rules` dir, nested ones too, which the first check (cwd up to the root only) does not see. So a Grok review is also refused when any path with a `.cursor` part (in any case, and as `.curſor`, which APFS takes for it) is a symlink committed in the repo or its submodules (`git ls-files -s --recurse-submodules`, mode 120000), or is, or sits under, a symlink in the work tree, which is what Grok reads. The work tree candidates are those index entries plus the untracked and ignored files (`git ls-files -o`), each checked with lstat (T6751). Untracked files inside a submodule are not listed (`ls-files -o` does not recurse). When git or a check fails, Grok is refused too. Plain files pass. A review refuses `/`, a root that is or holds `$HOME`, a directory outside a git work tree, a root at, inside, or around a vendor config dir (`~/.claude`, `~/.codex`, `~/.grok`, `~/.agents`, `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `GROK_HOME`), where credentials live, and a root at, inside, or around aggy's state dir.
- `edit` gets its own git worktree and never writes the main checkout. Its diff passes `aggy check` before you see it.
  As built (M3): `aggy borrow edit "<task>"` runs in a git work tree. aggy makes a worktree at `~/.aggy/worktrees/<borrow id>` on a new branch `aggy/edit-<borrow id>` from the main checkout's HEAD commit, never inside the repo, and records its path, branch, base commit, and git admin dir on the child (schema version 12). Every git call aggy makes there takes `core.hooksPath=/dev/null`, `core.fsmonitor=false`, no pager, external diff, or textconv, and every filter driver git's config defines switched off, so checkout runs no post-checkout hook or smudge filter; later calls on the worktree name its admin dir, never the `.git` file the child could rewrite. `--path` files are given to the child relative to the worktree. The worktree is git isolation, not a sandbox: only vendors whose writing mode and sandbox are recorded may edit, which today is Codex (`--sandbox workspace-write` with `/tmp` and `$TMPDIR` excluded and the user's `config.toml` ignored, `codex.EditLockdown`); Claude and Grok are passed over as unverified. Without a trust level for its cwd, such a child would write a project entry to the user's Codex config, outside aggy's manifest, so aggy names the worktree with `-C` and gives it a session-only level. Codex then does not load `AGENTS.override.md` or `AGENTS.md` by itself, so the child's prompt tells it to read them (adapters.md, source only). A borrow that cannot start removes its worktree; one that ran keeps it, with the git tree of what the child left recorded when the borrow ended, until `aggy accept` or `aggy reject`.
  A new worktree then gets the repo config's `[worktree] copy` files from the main checkout (only there: research and news children never see one). Each must be a clean relative path with no `.git` part, a regular file of at most 16 MiB with one link, reached through no symlink in the main checkout or the worktree, not a credential file (safefs), and ignored in the worktree (`git check-ignore`), so it never lands in the diff; nothing is replaced, and a refused file is named and skipped. The repo's `[worktree] setup` command is the repo's own code, so it is shown every time and runs only when the user's own config allows that exact command for that repo (`[[worktree.allow_setup]]` with `repo` and `command`; a repo's config has no such key, and a changed command needs allowing again). It runs in the worktree through `execrun` (scrubbed environment, no stdin, 15 minutes); a failure fails the borrow and removes the worktree.
  Nothing lands on the main checkout without acceptance. `aggy accept <id> [--yes]` stages what the child left in the worktree's own index (through its admin dir), refuses a worktree whose tree no longer matches the one recorded at the borrow's end (a process the child left behind may have changed it), prints the diff stat from the base commit to that tree, and applies the binary patch to the main checkout's work tree with `git apply` (unstaged, uncommitted) only on `y` or `--yes`; without a terminal and `--yes` it applies nothing. It refuses a diff that touches a symlink or submodule, or any path `borrow.ProtectedPath` names: a `.git` part, anything under a top-level dot dir (no allowlist: hooks, CI, editor tasks, and agent config live there), and at any depth the Grok trust list plus `.husky`, `.githooks`, `.gitattributes`, `.gitmodules`, `.pre-commit-config.yaml`, lefthook's config (`lefthook.yml`, `lefthook-local.yml`, their `.yaml` and leading-dot forms), `.npmrc`, `.yarnrc`, `.yarnrc.yml`, `.pnpmfile.cjs`, `.claude`, `.grok`, `.codex`, `.cursor`, `.gemini`, `.vscode`, `.github`, `.aggy`, `GEMINI.md`, and `.cursorrules`; and anything in the repo's own `core.hooksPath` (a leading `~/` expanded with `HOME`, compared by real path, so `/tmp` and `/private/tmp` or a symlinked prefix match; a value aggy cannot resolve, such as `~user/`, refuses the accept; one set only through git's environment variables is not seen, TODO(T6748)); a main checkout with staged, unstaged, or untracked changes in the touched paths; and a patch over 1 MiB. The state moves from pending to accepted before the write, and reject moves it to rejected before removing anything, so the state is the per-record lock and only one of them acts; the worktree and branch stay for `aggy pr` and `aggy gc`. `aggy reject <id>` removes the worktree with `git worktree remove` and deletes its branch with `git update-ref -d refs/heads/<branch> <sha>`, a compare and swap on the commit it read, refusing (as `git branch -D` does) a branch checked out, or being rebased or bisected, in any worktree, and removing its `[branch]` config section; a worktree directory already gone has only its own admin entry removed (`<git-common-dir>/worktrees/<id>`, once its `gitdir` file points at aggy's path), never a repo-wide `git worktree prune`. All of this only for a record whose path is `~/.aggy/worktrees/<id>` and branch `aggy/edit-<id>`. The check gate (W-5): `aggy check <id> [--yes]` shows the same diff stat, then the check list, taken from the main checkout's `.aggy/config.toml` and never from the worktree's (which the child could have written), with a plain statement that the worktree's tests, scripts, and build files are code the child wrote and run outside its sandbox; it runs them in the worktree only on `y` or `--yes`. The result (pass, fail, or skipped when the person says no) is stored on the child (`worktree_check`, schema version 13). `aggy accept` shows it with the diff stat; on a terminal it offers to run checks not yet run, `--check` runs them without asking, and an accept without them records skipped. A failed check does not block accept, which warns. The checks run unsandboxed code, so afterwards the gate takes the worktree's tree again: a check that changed tracked or unignored files (`gofmt -w`, `go generate`, golden updates) is recorded as a failure and refused, and accept takes the diff again, so the worktree must still match its recorded tree and the main checkout must still be clean in the touched paths. The gate refuses a main checkout whose real path is under `/tmp`, `/private/tmp`, `$TMPDIR`, or the OS temp dir: `workspace-write` alone leaves those writable (verified live), and although `EditLockdown` now closes `/tmp` and `$TMPDIR` with `sandbox_workspace_write.exclude_slash_tmp` and `exclude_tmpdir_env_var`, the refusal stays as defense in depth for other temp roots and older Codex versions, since the check list there may be the child's. For the same reason accept writes its patch file in aggy's own 0700 `run` dir, not in a temp dir, and refuses up front when aggy's state dir itself is under `/tmp`, `$TMPDIR`, or the OS temp dir (by real path, case-insensitive on darwin), naming the fix: set `AGGY_HOME` outside temp dirs. `aggy accept` is Unix-only for now: that private dir is (`supervisor.PrivateDir`), so on other OSes it refuses up front with "not supported on <os> yet", and the worktree's diff is applied by hand. - Each kind has a time limit and, where the CLI supports one, a turn limit. aggy kills a borrow's whole process group when the child exits (anything it left running in the group; a `setsid` escapee is not tracked; a vendor CLI's self-updater started without `setsid` dies with it), before reaping the child, so the group id cannot have been handed to another process (Linux waits with `waitid` and `WNOWAIT`, macOS with a kqueue `NOTE_EXIT` event; other systems kill just after the reap), past its time limit, or when `aggy borrow` gets SIGINT, SIGTERM, or SIGHUP (recorded as `interrupted`), and runs at most 2 borrows per vendor and 4 in total, counted across processes through store leases.
- `--vendor <name>` replaces the routing list for one borrow; the skip rules of section 8 still apply to it. `--vendor both` asks two vendors, for research only.
- A CLI outside the versions the adapter was tested on is not refused for that alone: see "When a CLI updates" below. On-screen sessions never check it; `aggy doctor` warns.

**When a CLI updates.** All three CLIs update constantly, and a borrow must survive it without trusting it. On-screen sessions run whatever is installed; only `aggy doctor` mentions a version outside the tested range. A borrow goes by the version the probe read (`adapter.ClassifyVersion`):

| Version | What a borrow does |
| --- | --- |
| In the tested range | Runs. |
| Below Min, a new major version, or unreadable | Refused (`lockdown.untested_version`), and routing falls through. |
| Above Max, same major version | Runs once the checks below pass on this machine. A failure passes the vendor over with the reason (`lockdown.version_check_failed`), and routing falls through. |

`--allow-untested` skips all of it, and the report says the version was not checked. A pass prints one line the first time, and the report and short report name the version as checked here, not verified by a release. Results are in the store's `version_checks`, per vendor and version, stamped with what they were checked against, so an aggy release that changes the lockdown checks again.

1. **Help, no quota.** Every flag the kind's lockdown needs (`Adapter.LockdownCaps`) must be in the CLI's help. It reads the probe, which caches per version, so it is free and runs per borrow: kinds need different flags. A failed help run does not count against the version.
2. **Features, no quota, Codex only.** See below.
3. **Self-test, one small real run.** Through the vendor's CLI, under the lockdown of one kind (`Adapter.SelfTestKind`: Claude and Codex review, Grok research), in a fresh empty dir with a random token planted just above it, the child is asked to read `../canary.txt` and to reply exactly `NO ACCESS` if it cannot. A pass is that reply starting a line of text, in quotes, markup, a code fence, a list or heading marker, or after `Result:`; text above it and after it may only be an explanation in plain English that says why the file cannot be read and does not go back on it, read on whole words, with no word that looks encoded (a path or a `key=value` setting is not); or Grok's own stderr line that it stopped the tool at a permission prompt a headless run cannot answer (`borrow.permission_prompt`), since the read then did not happen. An empty or other reply is not a pass. The token in any output is a final failure, as is the token in the reply in another case or broken up by markup, a rejected flag, a record of a tool the lockdown should have removed, or a Codex patch that went through under the read-only sandbox (a failed one is expected: `apply_patch` cannot be turned off). What the record is differs: Codex's `exec --json` stream shows each tool call; Grok's `--output-format json` does not, so aggy reads the session's `chat_history.jsonl`, under the cwd's encoded name or else any other (both source only), whose tool results would hold the token; a file it cannot read whole, such as one over the 16 MiB cap, is not a pass and waits, and a missing one leaves the reply to decide, which the diagnostic log notes; Claude's JSON holds only the final result, so there the reply is all there is. **So this shows a child reported it could not read the file, not that it could not: a child that read it and lied passes where no record catches it. A reply that admits the read in words aggy knows is no pass, but a word list only narrows the rest, and a child that denies it cannot be caught this way.** A limit, sign-in, billing, or outage spends nothing: the vendor is passed over, nothing is kept, the next borrow tries again, and a limit also goes to the router's skip rule. A run that spent quota and showed nothing (a timeout, unreadable output, an unclear reply) passes the vendor over for six hours, at most four tries a day, so a changed output format does not cost quota on every borrow; a wait dated ahead of the clock (the clock moved back) does not hold. On Claude a review loads the user's own settings (`--setting-sources user`), so a `Read` allow rule or `permissions.additionalDirectories` reaching outside the working directory would make the child read the file: a final failure, whose message says so. Changing that file tests again, one run per change whatever the change, since its hash is part of the result's stamp: telling a harmless key from one that reaches a read would be a list that can go stale, and a stale list would weaken the check. It runs after the adapter and gates, so a borrow they refuse spends nothing; the concurrency caps are checked after it, so a borrow they refuse has spent it. It is part of the borrow the person started: nothing runs in the background. It holds no borrow lease, so it does not count against the concurrency caps, and two first uses at once may both run it. `[versions] self_test = false` in `~/.aggy/config.toml` turns it off (a repo's config has no such key); the report then says so, and a failure already recorded still passes the vendor over. One test per version does not prove every kind: a Codex edit child keeps its shell and reads anywhere by design, so its write boundary is not exercised, only the flags it shares with the review lockdown.

Runtime fail-closed is unchanged and is what catches the rest: `adapter.CheckLockdown`, Codex `--strict-config`, Grok's `name no tool`.

**What a check cannot see, per vendor.** Claude and Grok pass a `--tools` allowlist, so a tool new in a later CLI stays out unless the allowlist itself breaks, which is what `name no tool` and the self-test watch. Codex's lockdown is a `--disable` list, so a new tool is on until aggy knows about it, and a canary does not show that: a tool can be unable to read a file and still reach something else. So a Codex above Max has a stricter rule. `codex features list` prints each feature's stage and state after loading config only, with no model call (source, not yet run live; verification.md, T6929), and any feature on that was not on by default at the tested tag, new or flipped, passes Codex over, naming it. That is how a new tool usually rolls out. A pass is kept; a refusal is not, since the check is free.

The remaining Codex risk is accepted, plainly: **a new tool is on in a borrow child and no check sees it when it sits behind no feature flag, as `apply_patch` does today, or under a feature already on that the lockdown leaves on.** Many are: `multi_agent`, `computer_use`, `browser_use`, and the rest of `codex.featuresOn` outside `codex.Lockdown`'s eight. Such a feature can gain a tool in any update, with nothing in the list changing, and the self-test sees only a read of the canary. The list also reflects the user's own config, since the command takes no `--ignore-user-config` while the child does: a feature the person turned on fails the check (the reason says so; `--allow-untested` overrides), and a new default-on feature the person turned off is missed. Refusing every new Codex version would close this and bring back the problem this section exists to solve, so aggy does not; a release that raises `Tested` is still the only review of Codex's tool list.

**What else an update can break, and how it fails.** None of these hangs or passes silently:

| What changes | How it fails |
| --- | --- |
| A lockdown flag | Above: help check, then `lockdown.rejected` at run time. The run is discarded, never retried without the flag. |
| Headless output format | `ParseHeadless` returns `ErrUnparsed`: the borrow is `failed`, with the error in its report, and is not retried. The self-test usually sees it first, and the vendor is passed over with six hours between tries. |
| Transcript format | `adapter.ErrNoTranscript`: the brief degrades to the task file and git state. A switch still works. |
| Hook payloads | A turn-end hook aggy no longer recognizes is no turn end, so a switch waits. The picker says it is waiting, and Esc cancels; picking again says no turn is running. Never typed into a running turn. |
| `/exit` | Past `exitWait` (10 s), aggy says the CLI has not exited and is still running (`CodeExitTimeout`). Nothing is lost, and nothing is forced. |
| Codex's config file | An edit compares `config.toml` around the run and warns in the result and report if it changed; a concurrent Codex of the person's own looks the same. |
| Codex's app-server daemon | It updates separately from `codex --version`, which is what the probe reads, and has its own `codex app-server daemon version` ([main.rs#L2441](https://github.com/openai/codex/blob/6aaac694803004a63c6f393d153c96d22521a6b9/codex-rs/cli/src/main.rs#L2441)). `codex exec` runs thread/start in process, so a borrow is not affected. An on-screen session may talk to a daemon older or newer than the version aggy shows; aggy does not check it, and what breaks shows up as the rows above. |

**One hop.** The parent's `aggy borrow` works and the child's copy refuses. A child with a shell could still run `claude -p`, `codex exec`, or `grok -p`/`--prompt-file` directly. Delegated children get a `PreToolUse` hook that denies commands calling those or `aggy borrow`. It catches accidents. It is documented as not a security boundary.

**Image and video.** `aggy image` and `aggy video` are `aggy borrow image|video` with file arguments:

```
aggy image "<brief>" --out public/hero.png [--vendor codex|grok] [--ref style.png] [--n 3]
aggy image --edit public/hero.png "darker background, keep the logo"
aggy video "<brief>" --out public/intro.mp4
```

The on-screen agent writes the brief (purpose, size, exact text, style references, target path). aggy runs the vendor read-only with any reference images, copies the result to `--out`, and writes a sidecar with the prompt, vendor, child session id, and the model when one was set (none when the vendor's default was used). The agent checks the image and accepts it or asks for an edit. `--edit` resumes the same child, so the vendor keeps its context. Image MCP servers are out, because nearly all of them call an API with a key.

As built (M1): `--out` is a `.png`, `.jpg`, or `.jpeg` file (`.mp4` for video) inside the repo, outside its `.git` and `.aggy` (compared case-insensitively). A cloned repo can plant symlinks, so aggy never writes through one: it resolves the deepest existing folder on the way, refuses it outside the repo or in `.git` (or in `.aggy`, except for sidecars), makes only the missing folders one at a time, and writes pinned to that folder's identity (`safefs.WriteFileNoFollowIn`), replacing only a regular file and never a symlink. Each file the child left passes the artifact gate (section 13) and is copied by aggy: the first to `--out`, the next to `<name>-2`, `<name>-3`, with the extension changed when the vendor made another type (Grok makes JPEGs). Only `--out` itself may replace a file; every other name is created exclusively, taking the next free one. Each copy gets a sidecar at `.aggy/assets/<path>.json` holding the prompt, kind, vendor, child session id, borrow id, and time, and the model only when one was set (with the vendor's default it is left out). The `assets` folder holds a `.gitignore` of `*`, as the briefs folder does, so sidecars stay out of git (T6926). `--ref` images pass the same gate (any age) and the CLI gets aggy's copy in the run dir; only Codex takes them (`-i`), so Grok is passed over. `--n` (1 to 4) asks for variants in the prompt. Every file the child left counts as made (the borrow's image count, the report, and the summary line "N files made, M kept"), and at most 4 are kept and copied per borrow, since image turns use plan limits faster. A child that left no file fails the borrow with outcome `unknown`, and since only the child knows why (on an account with zero data retention, `image_to_video` fails), the start of its reply follows the error in the short report and the inbox report, labelled as its words: at most 4 lines, control characters escaped, and any line holding a secret dropped (`internal/redact`). It goes nowhere else: not the diagnostic log, the index, `aggy doctor --report`, or `aggy diag bundle`. `--edit <path>` reads the path's sidecar (a known vendor, a valid session id, an image), accepts the session only if aggy's own store recorded it for an image or video borrow on that vendor (a sidecar in a cloned repo could name any of the user's sessions), and resumes it on that vendor, writing over the path or to `--out`; files the session made in earlier runs are skipped, not counted. An image Grok made is refused (`borrow.grok_edit`) before routing, whatever `grok_file_tools` says, with a reason that names what works (a new image, or one made on Codex): Grok keeps a session under its working directory, and the first run's temp dir is gone, so a resumed child failed in a second on 0 tokens (2026-11-06 agent audit, grok 1.0.77; the exact cause is partly inferred, verification.md T6923). Only that vendor holds the session, so nothing falls through to another. Keeping run dirs would change the borrow lockdown, so aggy does not. Unverified: whether Codex keeps a resumed thread's images in the same folder.

- Grok: `image_gen` is verified headless on the plan with `grok -p --tools image_gen --output-format json`. `image_edit` exists but is unverified headless. There is no `video_gen` tool: a video borrow gets `image_gen` and `image_to_video`, unverified headless. All three sit behind `features.image_gen` and `features.video_gen`. Images land in `~/.grok/sessions/<url-encoded cwd>/<sessionId>/images/`, and the reply gives the path relative to the session folder; videos land in the same session folder's `videos/<n>.mp4` (source: grok-build 2bdd1d6a, `video_gen/mod.rs`; not seen live). `image_edit`, `image_to_video`, and `reference_to_video` each read a local image at any absolute path the model names and upload it to xAI, and there is no text-to-video tool (source, [verification.md](verification.md)). So they are off by default: `aggy video` refuses unless the user sets `grok_file_tools = true` under `[media]` in `~/.aggy/config.toml`, a key a repo's config cannot set. With it on, a brief or steered child can send any local image to xAI. A Grok image generation runs under `--sandbox strict` with one allow rule, `--allow image_gen`. Under strict without it, `image_gen` asked for permission, which a headless run cannot give, and made no image (live, 2026-10-29, grok 1.0.70); with the rule it made the image, and so did aggy's own argv (the smoke's `GROK_IMAGE_ARGS`) run directly; the full `aggy image` borrow path has not been re-run. A run whose stderr says a tool "was not run, as a headless run cannot ask for approval" fails as `borrow.permission_prompt`. Video does not run under strict until a live check shows it works there (TODO(T6821)). Video is untested (the test account's zero data retention). They keep review's read denies (`~/Library`, the Grok home, the darwin firmlink), which are permission rules, not part of the sandbox; Grok checks the media tools as generic tool calls, not reads, so those rules match none of them today. So with `grok_file_tools` on, `image_edit` and `image_to_video` can still read any local image path the model names. Grok has no path rule for them: a rule's tool is Bash, Read, Edit, Grep, MCP, WebFetch, WebSearch, or AgentMessage, and any other name makes a tool-wide rule matched against the tool's name, so `--deny image_edit` can only remove the whole tool (T6751, verification.md "Grok media tools and local files"). What keeps the Grok home's auth file, which is JSON, off the wire is that both tools refuse bytes that are not an image before they upload: `image_to_video` decodes the whole file against an image allow-list, and `image_edit` passes a small file as is only when its magic bytes say PNG or JPEG, and otherwise must decode it. The extension is never looked at. So the opt-in stays as it is, and its risk is the user's own images, as its text says.

**Research and news.** The child gets the question, today's date, and any versions that matter. `--path` is refused for both: the child cannot read files, and a local path must not reach a web query. The child is asked for a summary of at most eight lines first, then findings, sources (each with its URL and publish date), what its sources are as of, and open questions. aggy writes the report to `.aggy/research/<date>-<slug>.md` at the git work tree root (in the state dir's `research/` outside a work tree; a `.aggy` or `research` that is not a real directory is refused; in a repo the folder holds a `.gitignore` of `*`, so reports stay out of git, and one there that is not `*` is kept with a warning, T6926), headed by the question, the constraints, the vendor, and the time it was asked, and with the child's text marked as data. A second report on the same question that day gets the borrow id in its name. The parent gets about ten lines and the path. The same question (the kind, the task, and the constraints, compared without case or extra whitespace) reuses a cached report for a day (news) or a week (research), without running a child, when the vendor that wrote it is still the first one routing picks and its configured model is unchanged; the parent sees when it was made. `--fresh` skips the cache. Cache entries live in the state dir's `research/cache/`, never in the repo, so a checked-in file cannot pose as one; the repo's Markdown copy is written from the entry. The report is data, and the parent treats it as information, not instructions.

Research takes in untrusted web content and sends queries out. If it could also read files, a planted instruction on a page could put a secret into a query. So research and news children run in an empty temp directory with file and shell tools removed:

- Grok runs with `--tools web_search --no-subagents` and `--disallowed-tools` naming the file, shell, and fetch tools (`read_file,grep,list_dir,write,search_replace,run_terminal_cmd,web_fetch,Agent`), the media and workflow tools, and the MCP meta-tools `search_tool` and `use_tool`. In a live check (2026-10-28) the model then reported only `web_search` and its browse helpers `open_page` and `open_page_with_find`, for research and news alike; that is the model's own one-turn tool list, not a wire dump, and the run also named the two `open_page*` tools in `--disallowed-tools`, which Grok ignored with a warning, so the exact set above has not been run live yet. Grok has no `x_keyword_search` or `x_semantic_search` tool; news uses `web_search`. An unknown name in `--tools` makes Grok ignore the whole allowlist with only a warning, so the list must name real tools.
- Codex research and news are unsupported for now. With `--ignore-user-config --sandbox read-only --disable shell_tool --disable unified_exec --disable view_image --disable apps --disable plugins --disable goals --disable image_generation --disable sleep_tool -c 'web_search="live"'`, a Codex child has no tool that reads a file, and live checks found no direct read. But its `apply_patch` tool, which no flag removes, answers a right guess of a line in a file at a known path differently from a wrong one, so a child can confirm guessed contents. The Codex adapter refuses both kinds until that is closed (T6638); an OS sandbox around the child closes the content oracle but not path existence, and is backlogged (section 21). Details are in [verification.md](verification.md).

Tool deny-lists only cover the vendor's built-in tools. On Grok, denying `search_tool` and `use_tool` cuts off MCP servers too; on Claude, `--strict-mcp-config` with an empty `--mcp-config` leaves no MCP or connector tool (verified live).

## 8. Routing

The on-screen agent is a model already in a turn, so it makes the judgment call: which kind of task this is. The skill lists the kinds and when to use each, for example that anything that may have changed since the model's training data goes to `research` or `news`. aggy then makes the policy call from the routing table. Changing which vendor handles a kind is a config edit; the skill does not change. aggy has no model-based router.

Defaults, chosen from what each CLI has built in, not from benchmarks:

| Kind | Order | Why | Time limit |
| --- | --- | --- | --- |
| `news` | Grok | Web search built in, and a flag set that leaves only web tools (section 7). | 5 min, 15 turns |
| `research` | Grok | Web search with sources, with the same clean flag set. | 10 min, 30 turns |
| `image` | Codex, Grok | Built-in image generation. | 5 min |
| `video` | Grok | Only Grok has video tools. | 10 min |
| `review` | Claude, Codex, Grok | Any connected vendor, Claude first by default; the vendor on screen included, since a review is a fresh session with its own context. Opt-in `not-author`, or `review_skip_on_screen` (section 9). | 15 min |
| `edit` | Codex, Grok | Moves edit work off the on-screen vendor. Grok is passed over until its writing mode is verified (section 7). | 45 min |

A review on the vendor on screen is live-confirmed only for Claude under Claude ([verification.md](verification.md), "Same-vendor nested review"). Codex under Codex and Grok under Grok are unverified: the default route reaches them only when Claude is limited, disconnected, or not allowed, and Grok's `--sandbox strict` is known to refuse to start inside another sandbox (verification.md, S6), so a nested Grok review may fail closed. A smoke check for both is TODO(T6779).

Codex is deliberately not in the `news` and `research` defaults. Its `apply_patch` tool cannot be turned off, and its error text tells a right guess of a line in a file at a known path from a wrong one, so a research child could confirm file contents by guessing ([verification.md](verification.md), 2026-10-28). Until that oracle is closed (T6638), the Codex adapter refuses both kinds. A user config may still list `codex` for them: the router keeps it in the list with a note naming the reason, and the adapter refuses it with `ErrUnsupported`.

aggy walks the list for the kind (or the one `--vendor` named) and skips, checking in this order:

- the vendor the parent is on, which should use its own tools instead; for `review` only with `[routing] review_skip_on_screen = true` or a `"not-author"` route, since by default a review is a fresh session and the same vendor may run it
- for a `"not-author"` review route only, the vendors named by the `Aggy-Vendor` trailers (section 16) of the commits in the reviewed range (`<base>..HEAD`, at most 1,000 commits, read with `git log` under the same safe options as the diff and no signature check); a value that is not a vendor is ignored, and a git failure means no authors. Trailers are best-effort and forgeable: anyone can commit with `AGGY_VENDOR` set, or skip the hook (`--no-verify`) and write one by hand, and so steer a review back to the real author; they can never get a vendor past `allowed_vendors` or any other rule. So they only steer: when skipping the authors would leave no vendor, they are kept and `aggy borrow` prints a warning naming them. Any other review route never reads the trailers (no `git log` runs). Routing on aggy's own record of which vendor made an edit is a follow-up (T6747). The other rules below still apply to them
- vendors that are not connected, or that `aggy setup` never recorded, in the `vendors` table; an `unknown` sign-in status counts as usable, and aggy says so
- vendors outside the repo's `allowed_vendors`
- vendors that hit their limit recently (section 11, "Recording limits"); a limit only a hook reported never leaves the list empty: when every vendor would be skipped, those vendors are kept and `aggy borrow` prints a warning naming them

The rest are tried in order. A candidate whose CLI is missing, whose adapter refuses the kind, or whose version the lockdown was not verified on is passed over before anything runs, and the report names it and why; a borrow that started and then failed is the result, with no second vendor. When none is left, the error names each vendor and why it was skipped, for example `no vendor available for research: grok: the parent is on grok; codex: not connected`.

Every borrow is logged with its kind, vendor, model, tokens, time, and outcome. A redo, or the same question re-asked of another vendor, counts against the first. `aggy stats` shows results per kind, and you reorder the table. The switch picker uses the same signals.

As built (M4, T6701), a redo is read from what the borrows table already holds, and nothing new is stored for it. A borrow that ended `ok` is *redone* when a later borrow of the same kind, under the same parent, started after it ended and at most 24 hours later, and either:

- has the same task hash: the same task on the same input, re-asked of any vendor (a `--fresh` re-ask included). The task hash is one SHA-256 over what the borrow was asked and what it worked on: the kind; the task text and each constraint, lowercased with whitespace collapsed (constraints sorted); the cleaned `--path` paths; for a review, the base it diffs against and the diff and file contents it was given; for an edit, the commit its worktree was made from; for an image or video, `--out`, the `--ref` paths, `--n`, and the session an `--edit` resumes. So the same review text after another commit, the same edit text on a new base, or the same question under another constraint is a new task, not a redo. This is stricter than the research cache's key (kind, task, and constraints in order), which only decides when a stored report can answer again. Borrows from before this rule hashed the raw task text alone, so a pair that spans the upgrade never matches. Or
- the first is an `edit` whose worktree was rejected (`aggy reject`), and the later one is another edit, whatever its text.

A redo counts against the borrow redone, so against its vendor, never against the one asked next. In a chain of re-asks each attempt but the last is redone. The borrows of one `--vendor both` run are one question asked of two vendors on purpose, not a redo of each other: aggy marks them with a shared `group` in their borrow events, and the rule skips a pair from the same group (runs from before the marker have none and count as redone). A failed or killed borrow is never redone, since it already counts as not `ok`. A cached research or news answer runs no borrow and records none. A borrow whose parent is unknown is never matched. The window and the matching are aggy's own record of what was asked again, not a judgment of the answer: a person who re-asks for another reason still counts, and one who rephrases a question does not. Neither the task text nor a review's material is stored, only the one hash over them, in the local index; `aggy stats` prints no hash.

## 9. Configuration

User config is `~/.aggy/config.toml` (or `$AGGY_HOME/config.toml`). Unset keys take the defaults, and unknown keys are an error.

An illustrative override (the values are examples, not recommendations):

```toml
default_vendor = "codex"    # unset means the first connected vendor

[vendors.grok]
model = "<model-id>"        # passed to the CLI unchanged

[switch]
order = ["grok", "codex", "claude"]
warn_at = 0.9               # near-limit warning at 90% used; 0 turns it off

[routing]
image = ["grok", "codex"]
review = ["grok", "claude"]  # default claude, codex, grok; or "not-author": codex, grok, claude minus the parent's vendor and the trailer authors
review_skip_on_screen = true  # a review skips the vendor on screen too (default false)
edit_tools = ["context7"]     # managed tools an edit child gets (default none)

[budgets]
research = { minutes = 15, turns = 40 }
```

Per repo, `<repo>/.aggy/config.toml` holds `allowed_vendors`, `tools_off` (tools this repo turns off; a repo cannot turn any on), the commands `aggy check` runs, the ignored files a new worktree copies (such as `.env`), and a worktree setup command. `allowed_vendors` names the vendors that may see the repo: borrows skip the others (section 8), `aggy brief --to` and the brief a launch writes for its child refuse them, and every launch (`aggy`, `aggy run`, `aggy new`, `aggy resume`, `--direct`) refuses to start or resume a session in the repo on one of them, takes the default vendor from the allowed ones, and offers only allowed vendors in the switch picker. The repo of the child's own directory decides, and a repo config that cannot be read refuses rather than allowing. A repo only narrows: the picker keeps the user's `switch.order` minus what the repo leaves out, and never adds a vendor.

`[gc]` (user config only) sets how many days `aggy gc` keeps a pending edit worktree, an accepted one, a closed borrow child, and an inbox report (section 16).

Defaults are generic. No model is set for any vendor, so each CLI uses its own default. `switch.order` defaults to claude, codex, grok, and the picker skips the vendor on screen. Routing and budgets default to the table in section 8, and no tool is wired in.

`[routing]` takes one key per kind (`news`, `research`, `image`, `video`, `review`, `edit`), each an ordered vendor list; an empty list turns the kind off, and `review` also takes `"not-author"` (opt-in: skip the parent's vendor and the vendors the reviewed commits' trailers name). `review_skip_on_screen` (a boolean, default false) makes a review skip the parent's vendor, as every other kind does; it applies to `--vendor` too. `edit_tools` (up to 8 tool names, default none) are the managed tools an edit borrow's child gets, and the only ones `aggy borrow edit --tool` may pick (section 9, T6709). A tool whose definition says `network = true` (Context7, Playwright, Headroom), and a user tool whose definition does not say `network = false` (the flag is self-declared, so a missing key counts as true, and `aggy tool add` shows the setting; R80-2), is refused there (`tool.borrow_network`) unless `edit_network_tools = true` too: a tool's server runs outside the CLI's sandbox (Codex starts MCP servers outside its no-network sandbox, and `claude -p` has no network tool of its own otherwise), so a child steered by a prompt injection in the repo could read a `.env` and send it out through one (M78-2). A repo config cannot set routing; its `allowed_vendors` only narrows it. An unknown routing key or vendor is an error that names the key, and a vendor listed twice keeps its first place. A setting replaces that kind's default list; it is not merged with it. Listing `codex` for `research` or `news` is accepted, but the Codex adapter refuses those kinds for now (section 8).

**Upgrade note (T6779).** Before T6779 every review route, an explicit `review = [...]` list included, skipped the vendor on screen and the vendors the reviewed commits' trailers name. Now only `"not-author"` does both, and an explicit list is walked as written. To keep the old behaviour, set `review_skip_on_screen = true` or `review = "not-author"`.

**Tools.** Every tool, plugin, skill, and MCP server aggy manages, aggy's own skill included, can be turned off cleanly per vendor, and off costs zero tokens: an off tool leaves no MCP entry, no skill link, no hook that injects text, and no line in memory, the brief, or the missing-tools list, and a CLI that scans shared skill folders (Grok scans `~/.claude/skills` and `~/.agents/skills`) gets the skill on its ignore list. A test proves it per vendor. `aggy tool list` and `aggy doctor` show each tool's estimated token cost per vendor. Tools are installed once at a pinned version, with any index built ahead of time, and stay ready while off, so `on` and `off` only rewire: the next session aggy launches or resumes gets the new set on its command line, and a config edit through the manifest is made only for a CLI without a launch flag (below). A switch reaches a running session at its next turn end, where aggy offers to resume that harness on the same session, and never interrupts a turn (T6729, "Applying a switch to a running session" below).

**The helper** (T6911). aggy's own skill is also the built-in helper, `/aggy` on Claude and Grok and `$aggy` on Codex, as one skill, so no second description sits in the context. With nothing after it, aggy itself lists every command at no model turn (section 5); with a question ("why didn't my switch go?"), the model answers from `aggy <command> --help` and `aggy diag`. It reads commands' help rather than copying them, so it stays current, which needs every command's `--help` to work. It changes nothing unless asked, and never runs `aggy unwire` or turns on a tool's proxy on its own. It spends a model turn, so at a plan limit `/switch` and `aggy help` in a terminal are the way out. The skill's switching section names `/switch`, `$switch`, `Ctrl+\`, and `/inbox`, and says that one of them reaching the model means aggy missed it, so the model changes nothing. `aggy setup` offers to link it (above). An upgraded aggy refreshes the installed copy: at each launch and in `aggy setup`, every one of aggy's own skills linked into any CLI whose installed `SKILL.md` differs from the one the binary carries is rewritten through the manifest (`refreshSkills`, one run id, a line on stderr naming it, so `aggy unwire --run <id>` puts the old text back), and nothing is written when all are current or none is linked. Only a file whose content is what aggy itself last wrote there, by the manifest's change rows, is rewritten: a launch never changes a file aggy did not write. A copy the person edited by hand is left, with a note (once) to move it away and run `aggy skill link`; and a folder under one of aggy's names that aggy never wrote, or that a tool of the person's names (`aggy skill add` took `switch`, `borrow`, and `inbox` before T6910), stays theirs: aggy's command skill of that name is not written, linked, or unlinked by `aggy skill link`, setup, or a launch, the note says so once, and `aggy skill remove` still removes theirs; only a new `aggy skill add` is refused those names (R121). Setup's question counts what each CLI would pay every turn: the aggy skill's frontmatter, plus on Codex the command skills' (about 40 to 60 tokens each, `ownSkillCost`). It never links a skill that was not linked, so a skill added in a newer aggy (the command skills) waits for `aggy skill link` or setup's question.

**aggy's own skill.** `aggy skill link [--vendor v]` writes the skill once, to `~/.aggy/skills/aggy/SKILL.md`, and links that folder into each vendor's user skill folder: `~/.claude/skills/aggy` for Claude, `~/.agents/skills/aggy` for Codex (its documented user folder), and `~/.grok/skills/aggy` (or under `$GROK_HOME`) for Grok. It is `/aggy` in Claude and Grok and `$aggy` in Codex. Every write and link is a manifest change, so `aggy unwire` undoes it; `aggy setup` links it, with the command skills, only on a `y` at a terminal (T6911; default no, since it costs context every turn), and with `--yes` or no terminal only says how. The layout loads the skill exactly once per linked CLI: Claude scans only `~/.claude/skills` and Codex only `~/.agents/skills` among these, so each sees one link. Grok scans all three folders, so with every vendor linked it reaches the skill three times, but all three links resolve to the one installed folder and Grok drops a skill whose canonical path it has already seen (verification.md, "Skill folders"), so it loads once. A per-vendor link is what keeps vendors independent: unlinking Codex must not take the skill from Grok, which a Grok that relied on `~/.agents/skills` would lose. `aggy skill unlink [--vendor v]` removes that vendor's link (a removal change, also undone by unwire). For Grok it also adds the installed folder to `[skills] ignore` in Grok's `config.toml` whenever Claude's or Codex's link is still in a folder Grok scans; Grok compares ignore entries with canonical paths, so the one entry hides the skill through every link. Linking Grok again takes the entry out, and with no other link left none is needed. A test proves, per vendor, that after unlink no folder that vendor scans gives it the skill. The skill's cost is estimated offline as bytes / 4: about 75 tokens every turn for the frontmatter and about 1,440 on invoke (with the helper, T6911), held by a test under 150 and 1,500 and shown by `aggy skill status`. Limits: the ignore entry is written only when a Grok home exists, so a Grok installed later sees a Claude or Codex link until `aggy skill unlink --vendor grok` is run (`aggy skill status` says so); and an existing `[skills] ignore` list written across lines is refused, not extended (a one-line list is extended, T6910).

Whether a tool is on is set per vendor and per repo, in aggy's state in `~/.aggy`. A repo can never turn a tool on: a checked-in `.aggy/config.toml` may only turn tools off, so cloning a repo cannot start an MCP server. Every session aggy launches (the on-screen session, a handoff or resume, a borrow child) gets the tools that are on for its vendor and repo on its command line, verified live: Claude `--mcp-config` (with `--strict-mcp-config`), which is not stored with the session and must be passed again on every resume; Codex `-c mcp_servers.<name>.command=…` and `.args=…`, plus `-c mcp_servers.<name>.default_tools_approval_mode="approve"`, because `codex exec` otherwise denies every MCP call; and Grok, which has no per-session MCP flag, through `--agent <file>` whose frontmatter lists `mcpServers` (whether it must be passed again on resume is open, section 21). A CLI without any of these falls back to a config edit through the manifest. `aggy switch <vendor> --tool <name>` (or a toggle in the switch picker) and `aggy borrow <kind> "<task>" --tool <name>` turn a tool on for that one session without changing any setting, and routing can give each borrow kind default tools; research, news, image, and video borrows refuse file-reading tools such as CodeGraph. As built (T6709), only an edit child gets tools: aggy cannot tell which tools read files or write, and no tool definition says it is read-only yet, so a review stays read-only and `--tool` for any kind but edit is refused (`tool.borrow_kind`). An edit child gets `routing.edit_tools` from the user's config, or the `--tool` names, each of which that list must name (`tool.borrow_unlisted`), since an agent runs `aggy borrow`. The checks are the launch's (the Grok gate, Codex's `-c`, the `aggy tool add` file check, `tools_off`, a per-repo tool's scope, and for Codex the fail-closed name clash check, over every config layer but the user's `config.toml`, which the child's `--ignore-user-config` drops (R80-4; which project layers it still reads is unverified, so they all count. In a repo whose tree holds `$HOME`, the `.codex` folder that is `$CODEX_HOME` is that user layer, not a project one, as Codex skips it; whether Codex loads it as a project layer under `--ignore-user-config` is unverified, and aggy does not count it)); any refusal passes the borrow to the next vendor rather than run the child without its tools. Each server starts through `aggy tool exec` in a private `~/.aggy/run/borrow-<nonce>.tools` folder removed when the child exits. Claude gets them in its strict MCP config with an `--allowedTools mcp__<name>` rule per server; Codex as `-c mcp_servers.<name>.*` with `default_tools_approval_mode="approve"`; Grok none (gated). A tool that reaches the network (`network = true`) needs `routing.edit_network_tools` (M78-2, above). Claude's child reads no MCP config but aggy's, so its clash check is the managed-mcp.json only (M78-3). Follow-ups (T6709): a `read_only` key in a tool definition, so a review can get the tools that set it; and a sweep for the folder of a borrow killed before its cleanup. Subagents a vendor CLI starts itself get whatever tools their parent session has. Claude subagents and Grok user agents can declare inline `mcpServers` of their own, and Codex roles cannot; aggy does not use subagent-only servers yet.

The CodeGraph index is built lazily the first time CodeGraph is turned on for a repo, then refreshed incrementally. Worktrees do not share it: a worktree gets a copy of the main checkout's index only when a session aggy launches there has CodeGraph on, the copy is refreshed for its branch, and `aggy gc` removes it with the worktree.

As built (T6711). aggy never installs CodeGraph: it is installed once, at the pinned version (`npm install -g @colbymchenry/codegraph@1.6.2`), and while it is off no agent sees it (no MCP entry, no skill, no brief line). Its definition is `scope = "repo"`, so `aggy tool on codegraph` needs `--repo DIR`, and the setting is in `~/.aggy` (a repo's `tools_off` can only keep it off). That `on` is where the index is built. The main checkout's `.codegraph` must be absent or a real folder (a symlink is refused, and nothing runs through it). It counts as indexed only with its database and aggy's own marker, `.codegraph/.aggy-indexed`, written once init exits 0; a database without the marker (an init cut short) is built again: `codegraph init` would only say "already initialized" and exit 0 over it, so aggy runs the definition's `install.rebuild` (`codegraph index {repo}`, a full rebuild) instead, and init only if that fails (a database without the schema, which only init rebuilds). Otherwise aggy asks at a terminal ("Index <repo> with codegraph?"; no leaves nothing turned on), nudges an agent with no terminal (`AGGY_VENDOR` set, as in a session aggy started) to leave the first index to the person (a nudge, not a security boundary: anything that clears the variable gets past it), adds `.codegraph/` to the repo's git exclude file (`info/exclude`, shared by its worktrees; through the manifest, so `aggy unwire` removes it), and runs the definition's `install.prebuild` (`codegraph init {repo}`) once, in the main checkout, the way the shim starts a server: the pinned argv with `{repo}` filled in, through `execrun` with an environment built from scratch (plus the variables the tool's servers declare, `DO_NOT_TRACK` and `CODEGRAPH_TELEMETRY`, with aggy's telemetry opt-outs over them: `DO_NOT_TRACK=1` and `CODEGRAPH_TELEMETRY=0`, unless the user config allows telemetry; see "What aggy never sends"), no stdin, a private empty working folder, a program that must be a regular executable on `PATH`, and a 30-minute limit. It says the index may take a while; Ctrl-C, SIGTERM, or SIGHUP ends it and kills init's process group. A missing program, a failed, interrupted, or timed-out init, or one that leaves no database refuses the `on` (`tool.index_failed`) and records nothing; the message, and `aggy doctor` for a wired tool, says how to install the pinned version. A repo it is never turned on for, or that turns it off, is never indexed. CodeGraph's own `.codegraph/.gitignore` ignores everything but itself, so the exclude line is what keeps `git status` clean; `codegraph uninit` removes the folder. CodeGraph's npm launcher may download its platform bundle into `~/.codegraph` when the npm package's own is missing (its `npm-shim.js`). After that the server keeps the index fresh itself: `codegraph serve --mcp` watches the tree and catches up on connect (verification.md, "Managed tools"). Every launch (the on-screen session, a handoff or resume, and an edit borrow's child, which gets CodeGraph through `routing.edit_tools`) wires `codegraph serve --mcp --path {repo}` through the shim; review, research, news, image, and video children get no tool (T6709). When that launch is in one of aggy's own edit worktrees (`~/.aggy/worktrees/<id>`, which `aggy gc` removes) whose `.codegraph` has no database, and CodeGraph was wired, aggy copies the main checkout's finished index there before the CLI starts: only `codegraph.db` and `codegraph.db-wal` (never the main server's `daemon.pid` or locks), through safefs, refusing the copy when the folder or anything in it is a symlink, a file to copy is not a regular file with one link, the files are over 1 GiB in all, or any source changed between the first look and the end of the copy (all are checked again together, so a checkpoint cannot pair a new database with an old WAL). The folder's `.gitignore` (`*`) is written first unless one is there (a committed one is kept), each file is copied under a temp name and renamed into place, the database last, then aggy's marker; a refused or cut-short copy leaves no database, so the next launch copies again, and it is a `tool.index_copy_refused` warning: the session starts without it. The exclude line and the `.gitignore` keep it out of an edit's diff; the server's catch-up refreshes it for the worktree's branch; and `aggy gc` removes it with the worktree (`git worktree remove --force`). A worktree where CodeGraph is off, and a worktree of the person's own, never gets one.

**Tool definitions** (T6752, `internal/tooldef`). Every managed tool is described by one definition, and the switchboard works only from definitions. aggy's built-ins (CodeGraph, RTK, Headroom, Context7, Caveman, Playwright) are definitions embedded in aggy (what each wires, per vendor, is in [tools.md](tools.md)), plus a Go lifecycle hook where a tool needs one; a user adds their own as `~/.aggy/tools/<name>.toml`, and a good one can be proposed for the built-in set (CONTRIBUTING). A definition is TOML; keys are lower case, and `mcp`, `skill`, `hook`, and `init` are arrays of tables, each entry listing the vendors it supports:

```toml
name = "demo"                       # a-z, 0-9, -; the file is <name>.toml
description = "What the tool does, in one line"
homepage = "https://example.com/demo"   # optional; https, no user info
version = "1.4.2"                   # pinned; a user tool's starts with a digit
default = false                     # user tools are always off
scope = "repo"                      # "global", or "repo"
when = "has-ui"                     # repo scope only: a label shown on add and on, never checked
network = true                      # its servers reach the network (an edit borrow needs edit_network_tools); a user tool without the key counts as true
unverified = ["mcp", "install"]     # keys whose vendor facts are not yet in verification.md
telemetry_env = ["DEMO_TELEMETRY=0"]   # built-ins only: the tool's own telemetry opt-out, NAME=VALUE (T6822); aggy sets it with DO_NOT_TRACK=1

[install]                           # nothing here runs while the tool is off
check = ["demo", "--version"]       # presence and version
check_pattern = 'demo (\d+\.\d+\.\d+)'   # finds the version; exactly one capture group
install = ["/usr/local/bin/demo-install", "1.4.2"]   # only on aggy tool install, after asking
prebuild = ["demo", "index", "{repo}"]               # built-in per-repo tools only: once per repo, on aggy tool on --repo
hint = "npm i -g demo@1.4.2"        # how to install it by hand: shown when the program is missing, never run

[[mcp]]                             # a stdio MCP server; a vendor is in one entry at most
vendors = ["claude", "codex", "grok"]
argv = ["demo", "serve", "--root", "{repo}"]   # the program and its arguments
env = ["DEMO_HOME"]                 # names passed through from the environment; never values

[[skill]]                           # a folder holding SKILL.md, linked per vendor
vendors = ["claude", "grok"]
path = "~/.aggy/skills/demo"        # a user tool's lives here

[[hook]]
vendors = ["grok"]
event = "PostToolUse"               # from that vendor's event list
matcher = "run_terminal_cmd"        # optional tool-name pattern
timeout = 10                        # optional, seconds, at most 600
# rewrites = true                   # built-in deciding hooks only: may answer updatedInput
# rewrite_prefix = "rtk "           # what a rewritten command starts with (required with rewrites)
argv = ["demo", "hook"]

[proxy]                             # a local proxy (T6780): off until turned on for a named vendor, with a typed confirmation
vendors = ["claude"]                # the vendors it supports; each needs its variable below
argv = ["demo", "proxy", "--port", "8787"]   # runs in the foreground; never {repo}
listen = "127.0.0.1:8787"           # 127.0.0.1 or ::1 only, port 1024 to 65535
health = "/health"                  # a GET answers 2xx once it is ready
[proxy.env]
claude = "ANTHROPIC_BASE_URL"       # the vendor's own variable, from the allowlist only

[cost]
method = "static"                   # mcp-schema, skill-md, static, or none
tokens = 400                        # static: one estimate for every vendor...
[cost.vendor]
grok = 650                          # ...or per vendor

[[init]]                            # built-ins only: a vendor-specific setup step
vendors = ["claude"]
argv = ["demo", "init"]
undo = ["demo", "uninit"]           # required: the command that reverses it
writes = ["~/.claude/settings.json: hooks.PreToolUse"]   # required: what it changes
```

A tool has at least one part. `install.check` is required unless the tool is only a skill. `{repo}` is the one placeholder an argument may hold: the repo or worktree the session runs in, filled in at wiring; any other `{` or `}` is refused. `{repo}` is never the program (the repo's own code would run as the tool): not the program word, not any word after a wrapper (a shortcut: after a wrapper every word may be the program it runs), not an interpreter's script or a module it loads first (`--require`, `--import`, `-r`, `-I`, `-M`, python `-m`), and not `--exec-path`. Nor is it ever in a hook (a repo path may hold characters no one quoting makes safe for every shell a CLI runs hooks in). `lifecycle = ["worktree-copy", "gc", "refresh"]` names the Go hooks of a built-in. The registry gives the switchboard each tool, whether it is built-in or user, its source file, and its parts for one vendor.

Hook events are checked against each vendor's list: Claude's from its hooks docs; Codex's from `hook_config.rs` (verification.md, "Codex hooks"); Grok's `SessionStart`, `Stop`, `StopFailure`, `StopCancelled`, `Notification`, and a live-checked `PreToolUse`, plus an unverified `PostToolUse`. `PreToolUse` and `PermissionRequest` hooks can allow or deny an action: a user tool may not hook them, and a built-in must say `decides = true`. Codex's `PreModelRequest` and `PostModelRequest` are treated the same way, since what their output can do is unverified. A deciding hook may only rewrite or deny, never approve: wiring strips any `permissionDecision: "allow"` from a hook's answer (`aggy hook-tool`, "Launch wiring" below), and a hook that says `approves = true` (only with `decides`), or is verified to approve, is not wired at all (RTK's Codex hook, verification.md "Managed tools"). Every CLI runs a hook command through a shell (Claude `sh -c`, Codex `$SHELL -lc`, Grok inline), so each word of a hook's argv may hold only letters, digits, and `/ . _ + @ -`.

Trust rules. A definition is untrusted input, validated like the `check` list, and a built-in passes the same validator (a test fails otherwise):

- **A program is arbitrary code.** Whatever its name, a tool's program runs with the user's rights once the tool is on. The real gate is the preview on `aggy tool add` and the user turning the tool on; the program checks below are defence in depth against an argv that is really a shell string.
- **Nothing runs while a tool is off.** No argv of a user tool (check, install, MCP server, hook) runs on add, list, or remove. `check` runs on an explicit `aggy tool install` or `aggy tool check`, or once the tool is on; `install` runs only on an explicit `aggy tool install`, after asking. A `prebuild` is a built-in per-repo tool's only and names the repo as `{repo}`: it runs once per repo, on the `aggy tool on --repo` that finds no index there (T6711, CodeGraph above).
- Definitions come only from aggy itself and from `~/.aggy/tools/` (under `$AGGY_HOME` when set), never from a repo or the working directory. A repo's `.aggy/config.toml` can still only turn tools off.
- A user file must be a regular file, not a symlink, owned by the user, and writable by neither group nor others, in a tools folder that passes the same checks, in a state directory owned by the user and writable by neither group nor others. It is read through one no-follow descriptor whose owner and mode are checked on the descriptor itself, and `aggy tool add` creates it with `O_EXCL`, so a file or symlink put there after the checks is never read or written through.
- At most 64 KB of UTF-8, with no control, format, line-separator, or paragraph-separator character anywhere, comments included (a TOML escape in a value is refused too). Unknown keys, and keys not spelled with `a-z` and `_` only, are errors (the decoder folds case, `ſ` to `s` included). Names, versions, text, argument lists (64 arguments of 4 KB), env names (16), entries per part (4), hooks (8), and init steps (8) are bounded.
- Commands are argv only, never a shell string: the program is one ASCII word, a bare name found on `PATH` or a clean absolute path. Compared after Unicode case folding and without `.exe`, it is never a shell (any `sh`, `bash*`, `zsh*`, `fish`, `pwsh`, `rbash`, ...), `env`, `sudo`, `ssh`, `toybox`, or another runner of a string, nor a program that runs commands from its arguments (`sed`, `awk`, `vim`, `lldb`, `gdb`, `expect`, `tmux`, `screen`, `launchctl`, `sandbox-exec`, `xcrun`, `find -exec`, `git -c`, `flock -c`); a wrapper such as `nice`, `timeout`, `xargs`, `chrt`, `taskset`, `ionice`, `caffeinate`, `arch`, or `unbuffer` is checked through to what it runs; and an interpreter (`python`, `node`, `perl`, `osascript`, ...) is never given inline code with `-c`, `-e`, `-E` (alone or as a flag in a short cluster such as `-Ic`, not inside another flag's value such as `-Wignore`), `--eval`, or the like. A package runner (`npx`, `uvx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `uv tool run`, `pipx run`) takes only the flags aggy lists for it (S63-12): a few boolean ones (`-q`, `--offline`, ...) and the ones that name the package or the Python (`-p`, `--package`, `--from`, `--with`, `--python`, `--spec`); any other flag is refused, since an unknown one may take a value that swallows the pin (`--node-options`, `--globalconfig`, `--before`), install without asking (`-y`), or fetch from another index (`--allow-insecure-host`). No flag value holds `{repo}`. Its package is a plain name pinned to an exact version (`name@1.2.3`, `name==1.2.3-beta.1`; never a tag, a range, a URL, `git+`, or a path), so a launch never fetches new code, and with the package named by a flag the command it runs is a bare name from the package, never a path (`npx -p x@1.0.0 -- {repo}/evil`). A package manager (`npm`, `pnpm`, `yarn`, `pip`, `pipx`, `uv`, `cargo`, `go`) is allowed only as one of those runners, or with no subcommand and only `--version` or `--help` (S63-13): every other subcommand is refused, since a list of the bad ones always misses one (`uv pip install`, `uv tool install`, `npm init`, `pnpm create`, `pip wheel`, `npm restart`, `cargo build` through `build.rs`, `go generate`, `pnpm exec`, which runs the repo's `node_modules/.bin`). An interpreter's script is an absolute path, and `{repo}` appears only among the script's own arguments, never before it (`ruby -C {repo}`, `perl -I{repo}`, `deno run {repo}/x.ts`); `python -m` needs `-I` or `-P`, and a module node, deno, or bun loads first (`--require`, `--import`, `-r`) is an absolute path: Claude starts an MCP server in the session's directory, the repo, where a relative script, the first `sys.path` entry, and a bare module name all resolve to the repo's own code (S63-14). `git --exec-path` never takes `{repo}`, in its own word or the next.
- The env allowlist holds names only. A user tool may name only its own variables, starting with its upper-cased name (`DEMO_` for `demo`). Every tool is refused base URLs, proxies, keys, tokens, secrets, passwords, credentials, DSNs, cookies, loader and runtime injection (`LD_*`, `DYLD_*`, `NODE_OPTIONS`, `PYTHON*`, `GIT_*`, ...), and the vendor CLIs', clouds', and aggy's own variables.
- A user tool's skill lives under `~/.aggy/skills/<name>`. A built-in's is under `~/`, but not in a dot folder (vendor homes, `~/.ssh`) or in `~/.aggy` outside `skills/`. The resolved path is checked again when it is linked (T6708).
- Init steps, prebuilds, lifecycle hooks, `default = true`, and an unpinned version are for built-ins only, and a release fails on an unpinned built-in (`AGGY_RELEASE=1`).
- A name may not collide: a user tool never shadows a built-in, and the file must be named after the tool.

An invalid or untrusted file is refused with the file and the key named, and the rest still load. `aggy tool add <file>` validates a file, prints exactly what would run and be wired per vendor, and copies it into `~/.aggy/tools` (mode 0600) only after a yes at a terminal; `--yes` skips the question there and never works without one. `aggy tool remove <name>` deletes a user definition, a refused one included (even one named like a built-in), refuses a built-in and a tool that is still on anywhere, and never deletes through a symlinked or shared tools folder. `aggy tool list` shows each tool's name, built-in or user, default, estimated cost per vendor here, source file, and description, and `aggy doctor` shows the cost of each tool that is on (T6728). The cost is estimated offline from `[cost]`: a skill counted where the setting for every repo has it on (it is linked for every repo, whatever the repo's `tools_off`) and servers and hooks where the switches in this repo have them on (M83-4); `0` where nothing of it reaches the vendor (Grok's MCP servers and hooks, while gated); `static` is its tokens for that vendor (`[cost.vendor]`) or for all; `skill-md` counts the installed `SKILL.md` as aggy's own skill is counted (bytes / 4, `~N +M`: the frontmatter every turn, the body more on invoke), with `+unknown` when an MCP server or hook is wired too; `mcp-schema` and `none` are `unknown`, since aggy never starts a server to count its schemas. The built-ins declare no static numbers, since none is measured yet. A borrow child cannot add, remove, or switch tools (the PreToolUse guard denies `aggy tool add`, `remove`, `on`, and `off` too). Every vendor fact in the built-ins is marked unverified until its tool's task checks it; RTK is wired as a declared `PreToolUse` hook, never through `rtk init`.

**The switchboard** (T6708, `internal/switchboard`). `aggy tool on|off <name> [--vendor V] [--repo DIR]` records a setting in the index (`tool_switches`): for every vendor or one, in every repo or one. A repo is its main checkout, found from git's common dir without running git, by canonical path, so a setting follows the repo into its linked worktrees. Only git's own link counts (S63-11): a `.git` file must name `<main>/.git/worktrees/<name>`, whose `gitdir` file names the work tree's `.git` back, with `<main>/.git` a real folder; anything else (a crafted `.git` file or folder naming another repo, a submodule) is keyed by its own root, so another repo's settings and `tools_off` never apply to it. A `.git` that cannot be read refuses `on --repo`; `off` and `status` key it by its root (S63-17). `aggy tool add` records the sha256 of the file it showed, and `on` refuses a user file that is no longer that one (`tool.changed_since_add`, S63-16); a definition put in `~/.aggy/tools` by hand has no record, and `on` refuses it too: it must go through `aggy tool add` (moved out of the folder, then added), as a session's `--tool` requires (R76-F1); an "on" recorded for one before that is off at launch, in status, and everywhere the settings are read ("off: aggy tool add has no record of its file; move it out of the tools folder, then aggy tool add it and aggy tool on it"), and a launch says so (`tool.changed_since_add`). An "on" for a built-in records `built-in` rather than a digest, and an "on" that holds a user file's digest never turns on a built-in that a later release gives the same name (S63-18). The newest setting replaces every narrower one it covers, so `aggy tool off demo` turns demo off everywhere. An "on" for a user tool holds the sha256 of its definition: once the file is edited, replaced, or refused, the tool is off ("the definition changed since it was turned on") until turned on again; `aggy tool add` and `remove` clear a name's settings, `off` takes any tool name, loaded or not, and `remove` works on a refused definition. Whether a tool is on for a vendor in a repo is decided from the definitions, these settings, the tools turned on for one session (`--tool`, T6708 wiring), and the repo's `tools_off` only, in this order: a tool with no part for the vendor is off; the repo's `tools_off` (the union of the main checkout's and, in a linked worktree, the worktree's own) turns it off, over any setting of the person's and any session's; a per-repo tool (`scope = "repo"`) is off outside a repo and takes no "on" from a setting for every repo, so it is turned on only with `--repo`; a tool turned on for the session is on; then the most specific setting wins (this repo and vendor, this repo, this vendor, every repo); with none, a built-in takes its `default` and a user tool is off. A repo config has no key that turns a tool on. One that cannot be read refuses `on --repo`, never `off`; `aggy tool status` warns and shows every tool off in that repo, as a launch treats it. `aggy tool status [<name>] [--vendor V] [--repo DIR]` shows the result per vendor and why, and writes nothing. It also shows each tool's state (T6726), read only, with no download and no index build: **installed** when every program it runs (its `install.check`, MCP servers, and hooks) is on `PATH` as a regular executable and its skill folder is in place and checks out; **ready** when its skill folder still hashes to its pin (`pin ok`, `pin changed`, `no pin`) and, for a tool with a prebuild step, the main checkout has its finished per-repo index, its database and aggy's `.codegraph/.aggy-indexed` marker (`indexed`, `not indexed`, or `index n/a outside a repo`; when git tracks either file and aggy's own record of its last build there, `~/.aggy/indexes/<tool>-<repo hash>` holding the database's device and inode, does not match, the repo committed it and aggy never built it, so status shows `index committed in the repo (not built by aggy)` and `aggy tool on --repo` indexes it once, as a first index; when git cannot answer, status shows `indexed (git could not check)`, T6820); and **wired**, per vendor it is on for, from the checks `aggy doctor` runs (the vendor, or the vendor with the reason code that keeps it from being wired). A tool stays installed and ready while off: on and off only rewire. Turning a tool on or off runs none of its commands and changes no CLI's config: wiring is built at launch from the tools that are on, and an off tool contributes nothing to any CLI, brief, or memory (T6708 wiring, T6709, T6727). A switch takes effect at the next launch, and a running session it reaches offers a resume at its turn end (T6729, below).

**Local proxy tools** (T6780). A definition, a built-in's or a user's, may declare one `[proxy]`, checked by the same validator: the argv that starts it (no `{repo}`), a listen address that is `127.0.0.1:<port>` or `[::1]:<port>` and nothing else, an HTTP health path, an optional `health_timeout`, the vendors it supports, and per vendor the one variable the allowlist gives that vendor: Claude `ANTHROPIC_BASE_URL`, Grok `GROK_MODELS_BASE_URL`, and none for Codex, which reads no base-URL variable (verification.md). Headroom is the first built-in user (`headroom proxy --host 127.0.0.1 --port 8787 --no-subscription-tracking`, with `HEADROOM_UPDATE_CHECK=off`, claude only; its flags, `/health`, and the beacon's `DO_NOT_TRACK` opt-out were checked live on 2026-10-29 at 0.42.0, and with `--no-subscription-tracking` the proxy's log showed subscription tracking disabled (verification.md); Codex and Grok stay unsupported, and the proxy stays `unverified` until a Claude turn through it is run live, TODO(T6780)). Until then it is experimental: for any tool whose definition lists `proxy` in `unverified`, `aggy tool status` says "proxy on (experimental: not verified live)" and the `--proxy` warning adds "This proxy is experimental: no live run has yet sent a session's requests through <tool>'s proxy."; both go when the live check (docs/verification.md) removes it from the list.

- *Turning it on.* `aggy tool on <name> --vendor <vendor> --proxy` is the only way. Without `--proxy`, `aggy tool on` turns on the tool's other parts and says its proxy stays off and how to add it; it shows no warning and asks nothing. `--proxy` needs `--vendor`, so no vendor is added silently (`tool.proxy_vendor_needed`), a tool with a proxy and a vendor it supports (`tool.not_applicable`), and is a usage error on any other command; `--repo` scopes it further, as for any tool. It prints a warning (every request of that CLI, the login token and all prompts, code, and replies included, passes through this local process; it is third-party code with its own network access that forwards that traffic to the vendor; it rewrites what the model sees; every process the CLI starts inherits the variable too, so the user's own scripts that call the vendor's API with a key go through it as well; a session stops working if the proxy does) and asks the person to type `<name> <vendor>`, before aggy builds anything else. No terminal, a wrong answer, `--yes`, a borrow child (`AGGY_DELEGATED`), or a run inside an aggy session (`AGGY_SOCKET` or `AGGY_PARENT` set) is refused (`tool.proxy_not_confirmed`, `tool.delegated`, `cli.usage`). The confirmation guards against mistakes, an agent's included: it is not a boundary against an agent that runs as the same user and works around it (unsetting those variables, a `script` or pty wrapper, or editing aggy's index); the skill forbids each of those, and the warning names what the person agrees to. What was confirmed is kept on that one setting as a digest (`tool_switches.proxy_digest`, index version 19): SHA-256 of the vendor, the argv, the listen address, the health path, and the variable (`tooldef.ProxyDigest`). A launch starts the proxy only while the definition still has that digest; a changed built-in or user definition (another argv, port, or path) turns it off, and `aggy tool status` and `aggy doctor` say "proxy off: its definition changed since you confirmed; aggy tool on <name> --vendor <vendor> --proxy asks again". An "on" for every vendor, a session's `--tool`, a plain `aggy tool on` that replaces the setting, or a setting made before T6780 never starts a proxy, though the tool's other parts follow it.
- *Where it runs.* On-screen sessions only (`aggy`, `run`, `resume`, a switch, `--direct`). The launch starts the proxy in the launch's private folder, in its own session and process group (`Setsid`; on Linux it also gets SIGTERM if aggy dies, `Pdeathsig`), with an environment built from scratch: `HOME`, `USER`, `LOGNAME`, `PATH`, `TMPDIR`, the locale, and `DO_NOT_TRACK=1` (with `[tools] allow_telemetry`, the person's own instead, T6822), never an `AGGY_*` variable, a key, or another base URL. Its output is kept only as a 4 KiB tail, shown through termsafe when it fails to come up. Borrow children never get one: their environment allowlist refuses every base-URL variable.
- *Lifecycle.* aggy connects only to the loopback address in the definition; the program's own flags decide where it binds. If the environment names an HTTP proxy (`HTTP_PROXY`, `http_proxy`, `ALL_PROXY`, `all_proxy`) that `NO_PROXY`/`no_proxy` does not bypass for that address, the session starts without it (`tool.proxy_env_proxy`): the CLI could send its traffic to that proxy instead (live, 2026-10-29: without `NO_PROXY`, Claude sent the request for a loopback base URL through `HTTP_PROXY`, credentials included; with it, direct). Before starting it, aggy connects to the address; if anything answers, it refuses (`tool.proxy_port_taken`): it never points a CLI at a process it did not start. It then GETs the health path on that loopback address only (no name lookup, no HTTP proxy from the environment, no redirect followed, one second per try) until a 2xx, for at most the definition's `health_timeout` (whole seconds, 1 to 120, default 15; Headroom's is 90, since its cold start took 25 to 81 s live), printing one line if it waits more than 2 seconds, and checks the listener on that address belongs to the proxy's own process group: on Linux every listening socket for the address in `/proc/<aggy>/net/tcp` or `tcp6` (aggy's network namespace) must be a socket some process of that group holds open (`/proc/<pid>/fd`); on macOS `/usr/sbin/lsof -nP -a -iTCP@<addr> -sTCP:LISTEN -Fpg`, run through `execrun`, must list at least one listener and every one in that group; on other systems the check is not built and the proxy is refused (TODO(T6780)). Otherwise it is stopped (`tool.proxy_not_owned`). It then checks the proxy did not exit just after. A Ctrl-C, SIGTERM, or SIGHUP during the wait stops it and ends aggy ("interrupted; nothing started"): no CLI starts. A proxy that fails, exits, or answers otherwise is stopped, and the CLI starts without it, talking to its vendor directly, with a warning (`tool.proxy_unhealthy`). When the CLI exits, aggy stops the proxy's whole process group (SIGTERM, then SIGKILL after two seconds) before a switch or resume launches the next CLI. If the proxy exits while the CLI runs, the kernel frees its port at once, so the moment aggy sees the leader exit, before it kills the rest of the group or reaps it, aggy listens on that address itself, accepting and closing each connection without reading it, until the CLI exits. No other process can then take the port the CLI still sends to, and the CLI's requests fail instead. aggy records `tool.proxy.exited`, offers a resume of the same session without the proxy at the next turn end (T6729), and says so when the CLI exits. If that first take fails for any reason, another process may have the address (one retrying bind() wins that race often), or the CLI would point at a free port, so aggy kills the CLI then, before any retry (SIGKILL to its process group; under `--direct`, which shares aggy's group, the CLI alone): its SDK retries a failed request within about half a second. It then kills the rest of the proxy's group, whose own workers may be what held the address, and retries for half a second so the placeholder still lands; it records `tool.proxy_hold_failed`, and prints a warning as the session ends: the proxy stopped, another process took its address, aggy stopped the CLI so it would not send the login there, and `aggy resume` resumes it (TODO(T6780): a request the CLI sends between the proxy's exit and aggy's take can still reach that process; stopping the CLI first with SIGSTOP would close that gap, but the supervisor treats a stopped CLI as Ctrl+Z and suspends aggy). More than one proxy on for a vendor starts none (`tool.proxy_conflict`), and `aggy doctor` warns about it. Limits: on macOS, `lsof` without root sees only the user's own processes, so another user's socket on the same port (`SO_REUSEPORT`) is not seen; a same-user process that shares the port with the proxy (`SO_REUSEPORT`) after the check is not seen either; if aggy itself is killed with SIGKILL, the proxy outlives it on macOS (on Linux `Pdeathsig` stops it), so the next launch finds its port taken and starts without it. On Windows a session starts without its proxy.
- *execrun's exception.* `PTYEnv` passes a base-URL variable only while a proxy `StartProxy` started is running for the vendor the CLI's `AGGY_VENDOR` names, and only that proxy's own variable with exactly its `http://<listen>` URL. Every other block stays. In a nested session (the inherited environment has `AGGY_SOCKET` or `AGGY_PARENT`), an inherited `ANTHROPIC_BASE_URL` or `GROK_MODELS_BASE_URL` that points at a loopback or `localhost` address no running proxy of this aggy was given is dropped from the CLI's environment: an outer session's proxy. Outside one it is the user's own (a local gateway such as LiteLLM) and passes as before; when a proxy tool is on for that vendor too, the proxy's URL replaces it for that session, and the launch says so in one line. Every process the CLI starts inherits the variable, which the warning says.
- *Turning it off* takes effect at the next launch. A running session keeps the environment it started with, and is offered a resume of the same session at a turn end (T6729, below: a proxy counts as a part).
- *Visibility.* `aggy tool add` shows a definition's proxy argv, variable, address, and health path; `aggy tool on` and `aggy tool status` say `proxy on` per vendor, or why it is off (its definition changed, its program is missing, or another proxy is on for that vendor); `aggy doctor` lists each proxy that is on (`tool-proxy-on`), checks its program, and warns about a conflict; the launch prints a line naming the proxy and its variable before the CLI starts, and the T6729 status line names a proxy that changed. The records `tool.proxy.started`, `tool.proxy.refused`, `tool.proxy.exited`, and `tool.proxy.stopped` carry the tool name and the registry's fixed text only.

**Launch wiring** (T6708, `internal/toolwire`). Every on-screen session aggy starts or resumes (`aggy`, `aggy <vendor>`, `aggy run`, `aggy new`, `aggy resume`, and each switch, whose child is wired for its own vendor) gets the MCP servers of the tools on for its vendor and repo, for that session only, on its command line or in a file in the launch's private folder under `~/.aggy/run`, which is removed when the CLI exits. That folder must be aggy's own, a 0700 directory of the user's that is not a symlink, and the file is written into the folder checked (W71-10). The user's vendor config is never written.

- *The shim.* No vendor CLI starts a tool's program directly. Each server's command is aggy itself: `aggy tool exec <launch folder> <name> <digest> <repo> -- <argv...>` (W71-2). It refuses (`tool.exec_refused`) unless the folder is a 0700 folder of the user's directly in a 0700 `run` folder, the tool's definition loads from that state dir with tooldef's owner and mode checks and its digest still starts with the one wired, and the argv is one of the definition's servers with `{repo}` filled in from `<repo>`. It then moves to the launch folder, opened without following a symlink and checked against its first look, so a folder swapped in between is refused (F74-1), and execs the program, which keeps the pid and stdio the CLI started. Its refusals are logged in the state dir the launch folder is in, also under Codex, which passes no `AGGY_HOME` (F74-4). The shim does not read the switchboard: a tool turned off while a session runs can still be started, or restarted by the CLI, in that session until it ends or resumes through the tools-changed offer below (T6729); an off setting takes effect at the next launch (F74-5). The environment is built from scratch: `HOME`, `USER`, `LOGNAME`, `PATH` (absolute entries only, and none under the work tree or its main checkout, whose `.envrc` a worktree nested in it inherits, or, outside a repo, under the folder the CLI runs in unless that is the home folder or above it; compared as written and through symlinks, so a direnv `PATH_add` or a project's `env.PATH` cannot pick the program; the same PATH is used for a tool's hooks (`aggy hook-tool`, which runs nothing when it cannot place its folder) and its proxy, F74-2), `TMPDIR`, `LANG`, `LC_ALL`, `LC_CTYPE`, and the variables the definition declares (a user tool's own `<NAME>_...`), read from the CLI's environment at that moment and never written to a file, then the telemetry opt-outs (`DO_NOT_TRACK=1` and the definition's `telemetry_env`, T6822; see "What aggy never sends"). No `npm_config_*`, uv, or pip variable is set or passed: a package runner reads the person's own config through `HOME` and finds no project config in the launch folder. So a server never runs in the repo and never sees the rest of the CLI's environment, whatever each CLI does with a working directory or its environment.
- *Per vendor.* Claude gets `--mcp-config <file>` before every other flag, and `--` before the brief prompt: Claude's `--mcp-config <configs...>` is variadic and would take the prompt as one more config (W71-1). `claude --mcp-config <file> -- "<prompt>"` works interactively (live, 2026-10-29, claude 2.1.312). It never gets `--strict-mcp-config`, which would drop the person's own servers and claude.ai connectors. Codex gets `-c mcp_servers.<name>.command`, `.args`, `.cwd`, and `.env_vars` (the names of the declared variables, which Codex passes to the shim). It gets no approval mode, so the person approves calls as Codex asks; without `-c` in its `--help` nothing is wired (`tool.no_launch_flag`). Grok gets nothing, and `aggy tool on --vendor grok` refuses (W71-4, `tool.vendor_unverified`). Its only per-session form is `--agent <file>`, which a resume must pass again: `grok -r <id>` without it lost the agent's server (live, 2026-10-29, grok 1.0.70); a resume is wired again like any launch, so the adapter passes it. These are unverified: what an agent changes besides `mcpServers` (the `[agent]` settings the person set, the system prompt, the model), and which project MCP sources Grok reads, which the clash check would have to read (`.mcp.json` and `.grok/config.toml` from cwd up to the git root, `.cursor/mcp.json`, `.grok/agents`). The `--agent` code stays behind that gate (TODO(T6708)).
- *Name clashes.* A tool whose name is already a server the CLI loads is not wired (`tool.name_clash`), and the warning names the file it is set in (W71-9). aggy never replaces a server or merges into one, which a Codex `-c` override of an existing name would do. For Claude, the names come from `~/.claude.json`'s user scope, the local scope of every project it lists (a session can match a project key by its canonical path, a symlinked one, or the main checkout's), and each `.mcp.json` from the session's directory up to `/` (W71-5). For Codex, they come from every config layer: `/etc/codex`, the user's, a selected profile file, and each project `.codex/config.toml` from the project root down to the session's directory. Servers set `enabled = false` count, since another layer may turn one back on, and so do those under `[profiles.*]` (W71-3). A file that cannot be read or parsed refuses every tool for that launch (`tool.wire_failed`): the check fails closed. The one exception is a `.mcp.json` above the repo that the user cannot read (a shared `/home`), which holds nothing aggy can see and counts as absent. Claude's managed `managed-mcp.json` and plugin servers are not read (TODO(T6708)).
- *`{repo}`* becomes the work tree the session runs in, as an argv word, never in a shell string. A tool whose arguments hold it is not wired outside a repo, or when the repo's path holds a character outside `[A-Za-z0-9/._+@-]` (`tool.repo_path`, F-3).
- *Limits left* (W71-7). The shim fixes the working directory and the environment. The validator refuses what would load code or config by a relative path: scripts, `node -r`/`--import`, deno and bun `--config`/`--import-map`, `uvx`/`pipx` `--python`, `lua -l`, `perl -d:`, and `java -jar` or a bare class name. It also refuses anything that would load from the repo (`{repo}` anywhere but the program's own arguments). What is left: a program still reads the person's own config under `HOME` (`~/.npmrc`, `~/.config/uv`, and the like), and a package runner may look for project config in the launch folder's parents, which are aggy's state dir and the home folder. A tool's own code is as trusted as the definition the person read and turned on.
- *Refusals.* Every refusal is a warning on the terminal and a `tool.wire.refused` record. The record's message is the code's registry text, and its `class` attribute names the step (W71-11). The session starts without that tool. With no tool on, the CLI gets no flag and no file. Borrow children get no MCP server or hook but an edit child's `routing.edit_tools` (T6709, section 9 above); a linked skill still reaches them, as above.
- *One session.* `aggy run --tool <name>` (repeatable) turns a tool on for that one session (`Board.Session`): no setting is written, the repo's `tools_off` and a per-repo tool's scope still win, an unknown name is a `tool.unknown` warning, and a switch to another vendor does not carry it (a resume of the same session for a tool change does, T6729); a switch gets its own with `aggy switch --tool <name>`, which the user confirms with the switch. A user tool turns on that way only while its file is the one `aggy tool add` showed and recorded, as `on` checks (S63-16, W76-1): an edited file, or one put in `~/.aggy/tools` by hand, is a `tool.changed_since_add` warning and stays off. A name the board keeps off (no part for the vendor, a per-repo tool outside a repo, the repo's `tools_off`) or with no MCP server or hook for the vendor is a warning too: a session wires only those, and a skill follows `aggy tool on` (W76-3).

Hooks (T6708). A tool's hook is wired only into Claude, in the session's inline `--settings` layer next to the safety policy's deny rules (the layer the borrow guard already uses), never into `~/.claude/settings.json`, so it is per session and an off tool leaves no trace. Codex and Grok keep their hooks in global config (and Codex runs one only once trusted by hand), so a tool's hook for them is refused (`tool.no_launch_flag`). The entry runs `test -x <aggy> && <aggy> hook-tool --vendor claude <tool> <hook index> <digest> || true`, built as aggy's own hook entries are (`hook.CheckBin`; every other word is a name, a number, or 16 hex digits). `aggy hook-tool` runs nothing unless the definition still has that digest and hook; it runs the hook's argv through `execrun` with the payload as a file on stdin, a private empty working directory, an environment built from scratch with no vendor home (`ToolEnv`'s, L78-7) plus the telemetry opt-outs (T6822), and the hook's timeout (8 seconds when unset; the entry's is 2 longer), and prints only what `hook.FilterToolOutput` passes: for `PreToolUse`, `hookSpecificOutput` with `hookEventName`, `permissionDecision` when it is `deny` or `ask`, `permissionDecisionReason` (a string of at most 1 KiB, which Claude shows the model for a deny, so this text does reach the model's context), and `updatedInput` (an object, and only from a hook whose definition says `rewrites = true`; H78-1, L78-6). A rewrite passes only in one form, checked against the hook's own payload (R80-1): a `Bash` call whose `updatedInput` has only keys of the original `tool_input`, each but `command` equal to the original's, and `command` exactly `rewrite_prefix` plus the original command. Anything else (`rtk proxy …`, `rtk -v …`, `/opt/homebrew/bin/rtk …`, `FOO=1 rtk …`, an added `dangerouslyDisableSandbox`, or a rewrite of each part of `a && b`) is dropped as `updatedInput_unexpected`, and the permission part of the answer passes as before (TODO(T6813): per-segment rewrites, which need a tokenizer that splits a command as Claude does). An `allow` is dropped, so a tool's hook never approves an action the person would have been asked about, and every other key (`continue`, `stopReason`, `systemMessage`, `additionalContext`, ...) is dropped, so a hook cannot stop the session or add text to the model's context; another event's output passes nothing. Output over 64 KiB, not one JSON object, a non-zero exit, or a timeout passes nothing (`hook.tool.failed`), which leaves the action as the CLI would have handled it without the hook; aggy hook-tool always exits 0. What it drops is recorded (`hook.tool.filtered`) by fixed names only, never a key or value the hook wrote (L78-5). A rewriting hook changes the command Claude runs, and Claude matches its permission rules against the rewritten input, not the original (live, 2026-10-29, claude 2.1.312: a deny on the original let the rewrite run), so when a wired hook says `rewrites = true` with `rewrite_prefix = "rtk "` and the safety policy is on, the launch adds every policy Bash rule again with that prefix in front, and for each key file a rule denying any prefixed command that names it (`Bash(rtk *.env*)`), covering both (`parity.RewriteDeny`, H78-1; RTK is the only built-in that rewrites): since a rewrite that passes is exactly the prefix plus the original, every prefixed Bash rule matches it whenever its rule matches the original. A hook whose definition says `approves = true`, or that docs/verification.md records as approving (`rtk hook codex`, S63-9), is never wired (`tool.hook_approves`).

Skills (T6708). No CLI takes a skill folder for one session, so a tool's skill is linked when it is turned on or off, not at launch: `aggy tool on|off` links `~/.aggy/skills/<name>` into each vendor's skill folder (as `aggy skill link` does aggy's own, through the manifest, so `aggy unwire` undoes it) for every vendor whose setting for every repo has it on, and unlinks it from the rest; while Grok is off and a Claude or Codex link is in a folder Grok scans, the folder goes in Grok's `[skills] ignore` (T6709). aggy never fetches or writes a tool's skill: `on` refuses (`tool.skill_missing`, saying where to copy it from) unless the folder is in place and checks out, re-checked through safefs at each link: a real folder, not a symlink, that resolves to itself under the state dir's `skills`, holding a regular `SKILL.md` and only regular files and folders (no symlink, at most 1,000 entries). Only `~/.aggy/skills/<name>` is linked from (TODO(T6715): a built-in's skill elsewhere under home). Limits: a skill is linked into the CLI's user skill folder (`~/.claude/skills`, `~/.agents/skills`, `~/.grok/skills`), so while on it reaches every session of that CLI, aggy's or not, borrow children (review included) among them, and every repo: `--repo` does not change its links, a repo's `tools_off` cannot hide it, and a tool that is only a skill refuses `--repo` and `scope = "repo"` (L78-8). The folder's sha256 is recorded when it is first linked, and `on` refuses a folder that changed since (`tool.skill_changed`, L78-4); no `aggy tool off` forgets it, whether it unlinks the folder or not, so a folder changed while the tool was off is refused too, failing closed (M2 of #89, T6822): the only re-pin is `aggy skill add <dir> --replace`, and `aggy tool remove` and `aggy skill remove` forget the pin. A built-in with a skill (Caveman) has no pin until its first link records one; after that the same rule applies. This does not keep an edit from the CLIs: a link already made is a symlink, so it shows the folder as it now is. A launch checks the pin too (R80-3): a tool that is on and whose linked folder no longer hashes to the record gets none of its MCP servers or hooks wired for that launch or borrow child (`tool.skill_changed`, failing closed when the index cannot be read), and its links stay until `aggy tool off`. A tool that is no longer loaded (its file deleted or refused), or whose definition no longer has a skill, is off for that skill, and `aggy tool off <name>` and `aggy tool remove <name>` take its links and Grok's ignore entry away (T6727, H83-2), and `aggy tool remove` forgets the pin; removing a refused file named like a built-in leaves the built-in's settings and links alone (L83-6). Limit: a user tool whose file was edited, or whose edit dropped its skill, is off, but a skill it linked stays until one of those runs; `aggy doctor` reports it as stray. `TestToolOffLeavesNoTrace` proves, for every built-in and a user tool with every part, per vendor, that off leaves no MCP flag, file, or server, no hook or rewrite deny rule, no skill in a folder that vendor scans (for Grok, the folder on `[skills] ignore` while a Claude or Codex link stays), and no line in the shared memory or a brief's missing-tools list. `aggy run --tool <name>` (repeatable) turns a tool on for that one session (`Board.Session`): no setting is written, the repo's `tools_off` and a per-repo tool's scope still win, an unknown name is a `tool.unknown` warning, and a switch to another vendor does not carry it (a resume of the same session for a tool change does, T6729); a switch gets its own with `aggy switch --tool <name>`, which the user confirms with the switch. Borrow children get no MCP server or hook but an edit child's `routing.edit_tools` (T6709, section 9 above); a linked skill still reaches them, as above.

**Applying a switch to a running session** (T6729). Most CLIs load MCP servers, hooks, and skills when a session starts, and aggy knows no verified way to reload them in place for any of the three (docs/verification.md, "Tool reload"; TODO(T6729)), so a change reaches a running session as a resume of that same session, through the switch path, which the user confirms at a turn end:

- *The notice.* After recording a setting (and changing any skill link), `aggy tool on|off` sends a `tools-changed` request to each running supervisor's socket (`run/<parent-id>.sock` whose lock is held) whose parent has the setting's vendor on screen (`--vendor`, or any) and, with `--repo`, runs in that repo; it says how many it told. Without one, nothing changes: the tools take effect at the next launch. The notice carries no field and proves nothing, so it is taken from any process of the user's (the command runs in any terminal), not only the session's tree, and refused by `aggy --direct`.
- *What changed.* The supervisor reads, off its loop, what its session would get now: per tool, `mcp` and `hook` where the launch would wire them (Claude: MCP, and hooks when `--settings` is in its help; Codex: MCP when `-c` is; Grok: nothing, while its tools are gated), and `skill` where `aggy tool on|off` links the tool's skill for that vendor (for every repo, whatever `tools_off` says: a repo cannot hide a skill). These are the settings, the repo's `tools_off`, the per-repo scope, and the session's own `--tool` names, as the launch decides them. Only a change from what the launch got counts: a setting for another vendor or repo, or one `tools_off` blocks, offers nothing. Whether a running CLI picks up a newly linked skill without a restart is unverified, so a skill counts as needing a resume. A set offered and turned down (Esc) is not offered again; a later change is. Settings put back as they were at launch drop a resume still waiting.
- *The offer.* On Claude (and any vendor with a hold signal) the change queues a resume like a picked switch: it waits for the turn end, unsent text, a hold, and the quiet gap, and the status line reads `aggy: tools +context7 -rtk, same session -> claude. Ctrl+\ resumes, Esc stays. See claude's prompt? It types /exit.` (`+` on, `-` off, `~` changed; a line too narrow for the keys drops the names). Only the switch key confirms, so an agent that runs `aggy tool on` inside the session cannot restart it; the notice itself confirms nothing. On Codex, which has no hold signal, a turn end can be forged from its tree as for an agent's switch request, so aggy only shows a note naming the changes; the switch key there (once 500 ms show it was meant for the note) queues the resume, which still waits for the turn end and the switch key (`switch.tools_no_hold`). A switch to another vendor already waiting wins; its launch wires its own tools, and if it is cancelled the next notice offers the change. A limit's handoff wins over a resume not yet confirmed. A change while the offer is up closes it and asks again with the new list, its guard re-armed. One turned down (Esc) is not asked again before the next turn end, however the settings move. A read of the tools stuck for 30 seconds is given up on at the next notice.
- *The resume.* Once the CLI exits, aggy launches the same child again with its resume flag, through the normal launch wiring (`addTools`, with every check: the digest, `tools_off`, the Grok gate, the name clashes, the skill pin). It is the same session, so, unlike a switch to another vendor, it keeps the launch's `--tool` names and one-launch model; it gets no brief, and `--no-policy` is not carried over (S-6). A session the vendor never saved (a new Claude child with no turn, a Codex child whose id was never recorded) starts a new session, as `aggy resume` would.
- *Records.* `tool.session.notified` (the command: how many sessions it told), `supervisor.tools.changed` (the session: how many tools changed, and what it did), and the switch's own records with `resume` set; no tool name the user chose is stored by these.

**Your own skill** (T6706). `aggy skill add <dir> [--name N] [--yes] [--replace]` stores a skill folder once, in `~/.aggy/skills/<name>` (the folder's name, or `--name`), and writes a user tool definition that is only that skill (`version = "0+sha256.<12 hex>"`, global, `network = false`, linked for every vendor, off), recorded as `aggy tool add` records one; `aggy tool on <name> [--vendor V]` then links it as above. Before storing anything it shows the frontmatter's name and description, every file with its size, the total, and the folder's sha256 (the skill pin's digest), and stores it only after a yes at a terminal; `--yes` skips the question there and never works without one, and a borrow child is refused (`tool.delegated`; the PreToolUse guard denies `aggy skill add` and `remove` too). The source is read whole once, through safefs, so what was shown is what is copied: a real folder, not a symlink, holding a regular `SKILL.md` and only regular files and folders, no symlink at any depth, no file with a second hard link, at most 1,000 entries and under 8 MiB (`tool.skill_refused`). After the yes everything is checked again (the name's tools, definition file, stored folder, pin, switches, and links), and anything changed while the question waited refuses the add (M1). The copy is staged with new files only (0600, 0700 for a file the owner could run, in 0700 folders) in a temp folder beside the store, `.<name>.tmp-*`, and must hash to what was shown there; an old folder and definition are moved aside, the new ones moved in with `safefs.RenameNoReplace`, and the old ones deleted only once the records are written, so a failure puts back what was there and removes only what this run made (H1). Its digest becomes the skill pin (`tool_skill`), so a later change is caught by `on` and at launch. A name already used by a stored folder, a built-in, or a user tool is refused (`tool.skill_exists`) unless `--replace` is given. `add` refuses while the tool is on anywhere or its skill is linked into any vendor (`tool.still_on`), even for a fresh name, since a link left from an earlier tool would show the new folder at once; `--replace` replaces only a definition that is only a skill, for a built-in that is only a skill (Caveman) stores the folder with no user definition, and for a user tool with more than a skill whose skill is linked from `~/.aggy/skills/<name>` stores the folder and pins it, leaving the definition as it is (T6822), so every pinned skill can be pinned again. `aggy skill remove <name>` deletes the folder (only the one it looked up: it is checked before anything is removed, moved aside under a private name, and checked again there, and a folder swapped in is put back and refused, `tool.skill_swapped`), the definition (as `aggy tool remove`), and the pin, and is refused while the tool is on anywhere or still linked, and for a definition that is refused or more than a skill, which is `aggy tool remove`'s (M3). The preview warns when the frontmatter name differs from the store name, or is aggy's or a built-in's, and says when a user definition is replaced. aggy's own skill keeps `aggy skill link`, `unlink`, and `status`, and `aggy` is never a name `add` takes.

## 10. Parity

Without parity, a switch lands in an agent that does not know the project's rules, lessons, or safety settings. Codex reads only `AGENTS.md`, while many repos have only `CLAUDE.md`. Claude's auto-memory is invisible to the other two. A repo's `.claude/` permission rules apply only to Claude.

- **Instructions.** aggy adds `CLAUDE.md` to Codex's `project_doc_fallback_filenames` in `~/.codex/config.toml` (or `$CODEX_HOME/config.toml`). That is one config line and no repo changes. Grok already reads `CLAUDE.md`. The key is taken to be a top-level array of file names; that shape is assumed, not yet checked against a live Codex. The change is a minimal text edit through the manifest, not a re-serialization: an existing list keeps its entries, comments, and line endings and gains `"CLAUDE.md"`; a missing key gets one top-level line. The result is decoded and compared with the original before anything is written, and `aggy unwire` undoes it.
- **Memory.** A shared project memory at `<repo>/.aggy/memory.md`, capped at 4 KB and delivered at session start. Claude takes it with `--append-system-prompt-file <path>`, which works interactively and with `-p` although `--help` does not list it (verified live); Claude snapshots the system prompt on the first request, so a changed file is ignored on `--resume` until compaction unless `--system-prompt-snapshot off` is passed. Codex takes it with `-c developer_instructions="…"` on every subcommand. The memory comes from the repo of the child's own directory, never the current one, since `aggy resume <id>` works from anywhere. Grok takes it with `--rules "<text>"`, inline text only. Grok stores the rules with the session at the first launch and ignores new ones on resume (live, 2026-10-29, grok 1.0.70), so an edited `.aggy/memory.md` does not reach a resumed Grok session; a new session gets it. How Codex treats new text on resume is open (section 21). The file is repo content that every CLI sees, so it is treated as data: a symlinked `.aggy` or `memory.md` is refused, a file over the cap is not delivered (rather than cut), terminal escapes, other control and format characters, variation selectors, private-use characters, and Hangul fillers are stripped, every angle bracket (ASCII, full-width, or small) is escaped as an entity so no tag can end the block, and the text is framed as notes that do not override the agent's instructions or safety rules. Codex's `-c developer_instructions` replaces the value of every layer below it, so aggy reads the system, user, selected-profile, and project-tree configs as Codex does and keeps a system or user value in front; a profile or project value makes aggy skip Codex rather than drop it. Codex's cloud-managed layers cannot be read, so a value there is replaced unseen. `aggy memory import --from claude` copies chosen entries from Claude's memory folder, which is plain markdown, after a preview. It is a separate, explicit step. It reads only the topic files in `<config dir>/projects/<project>/memory/` (not the `MEMORY.md` index, transcripts, or anything else under the config dir), each through `safefs` with symlinks skipped, adds each as a `## <name>` section unless that heading is already there, shows the diff, and writes only on a `y` or `--yes`, through the manifest (with the git exclude line), so `aggy unwire` undoes it; a result over the cap is refused. Claude documents the folder but not how `<project>` is derived from the repo path, so the default (the main checkout's path with every character but a letter or digit made `-`) is unverified, and `--dir` overrides it. To share memory across machines, remove its git exclude line and commit it.
- **Task file.** The skill tells every harness to keep `.aggy/task.md` current at step boundaries, under fixed headings and at most 60 lines. When a vendor is cut off mid-turn, the file is at most one step behind. A `Stop` hook nudges when it is 5 or more turns stale and files changed.
- **Connected tools.** Claude.ai connectors exist only inside Claude, and aggy cannot copy their logins. Where the same server is public, aggy adds it to Codex (whose own `codex mcp login` signs in) and to Grok: `aggy mcp wire [--vendor codex|grok] [--server NAME]... [--dry-run]` copies the public (remote, http or SSE) user-scope servers of `~/.claude.json` into `[mcp_servers.<name>]` of Codex's and Grok's `config.toml` through the manifest, so `aggy unwire` takes them out. A stdio server is a program that runs with the user's access to every repo (a file server pointed at a private folder, a tool using ambient cloud credentials), and Codex and Grok config is global, so it could reach a vendor a repo's `allowed_vendors` leaves out: it is copied only when named with `--server`, and `--server` copies only the servers it names. It appends a table per server and never re-encodes the file (the result must decode to the old document plus the new tables), never changes a server the CLI already has by name, and refuses a file that writes `mcp_servers` as an inline table. Because a `.git` file can name any directory, the git dir must hold a `HEAD` file and the common dir `HEAD` and `objects/`, and neither `info` nor `info/exclude` may be a symlink; otherwise nothing is planned. The line `.aggy/` is added through the manifest, once (a file that has it is left alone), with the file's own line ending, so `aggy unwire` removes it again. To commit the shared memory, delete that line, or `git add -f .aggy/memory.md`: exclude rules never apply to a tracked file.

## 11. Hooks and limit detection

Each vendor calls `aggy hook --vendor <vendor> <event>` from its own hook config (`aggy hooks install` writes it). Hooks call a fixed absolute binary path. The payload is parsed as JSON, cut down to the fields aggy uses (the session id, the event, its source or error class: never prompts, assistant text, or tool input), and forwarded to the supervisor over the socket named by `AGGY_SOCKET`, which `aggy hook` first checks is a socket of the user's own in the state directory's 0700 `run/`. It never reaches a shell. Outside aggy (no `AGGY_SOCKET`), for another vendor's hook, or on any failure, `aggy hook` exits 0 and writes nothing to stdout (Claude adds a `SessionStart` hook's stdout to the model's context), so the vendor CLI is never disturbed; the whole call is bounded to 3 seconds and the payload to 1 MiB. One exception (T6910): Claude's and Grok's `UserPromptSubmit` are installed so that a command inside a session picked from the CLI's menu is caught before the model. For those, `aggy hook` forwards nothing of the prompt but a parsed command's own line (`prompt-command`), and prints a block decision on stdout only when the supervisor took it (section 5, "Commands inside a session"); every other prompt, and every prompt outside aggy, gets no output and exit 0.

**Installing.** `aggy hooks install [--vendor V] [--dry-run]` writes aggy's entries through the manifest, so `aggy unwire` undoes them and `--dry-run` only prints the diff. Each is its own matcher group with no matcher (every occurrence) and one `command` hook with `timeout` 10: `test -x <aggy> && <aggy> hook --vendor <v> <event> || true`. Every CLI runs a hook command through a shell (Claude `sh -c`, Codex `$SHELL -lc` or `/bin/sh`, Grok "an inline shell command"), so the aggy path may hold only `[A-Za-z0-9/._+@-]` and needs no quoting under sh, bash, zsh, or fish, login shell or not; `test`, `&&`, and `\|\| true` make a hook whose binary is gone exit 0 quietly, where Claude would show a "hook error" notice on each event (Codex records a failed hook and goes on). The path is aggy on `PATH` when that is the same file as the running binary (Homebrew's stable `bin/aggy` link rather than a versioned Cellar path), else the running binary; a `go run` build is refused, and so is a binary whose path, link target, or any directory above either belongs to someone other than the user or root or is group- or world-writable, since every session of every CLI runs it. The edit inserts text and never re-encodes the file, so indentation, key order, number spellings, escapes, and line endings (CRLF included) stay byte for byte; an empty `hooks` object or event list, which Claude's `/hooks` UI can leave behind, counts as none; an aggy entry from an older path is updated in place; a file whose merge would be ambiguous is refused untouched: not one JSON object, a duplicate key, `hooks` or an event of the wrong type, or two aggy hooks for one vendor and event. **Undoing.** While the file still holds what aggy wrote, `aggy unwire` restores its old bytes. Vendors rewrite their own settings (Claude rewrites `settings.json`), so once the file has changed, a hooks change is undone structurally instead: aggy's own entries, found by their command (an absolute path ending in `/aggy`, then `hook --vendor`), are deleted from the file as it is now (a group that held only them goes whole, then an event list or `hooks` object left empty), everything else, later deny rules included, stays as it is, and the current bytes are backed up first; the dry run shows that diff. The change row records this as its `reverse` (`aggy-hooks`, schema version 9). TODO(T6738): a general structural reverse for other change kinds. `aggy hooks status` and `aggy doctor` (code `hooks`, with no path in the message) say whether each vendor's hooks are in place. Claude gets `Stop`, `StopFailure`, `SessionStart`, and `Notification` in `~/.claude/settings.json`. Codex gets `Stop` and `SessionStart` in `$CODEX_HOME/hooks.json` (it has no failure hook). Codex runs them only after the person approves them once in interactive Codex (`/hooks`); aggy says so in `aggy hooks install`, `aggy hooks status`, and `aggy doctor`, has no documented way to check it, and never passes a trust-skipping flag. aggy installs no Codex legacy `notify`: it would get every turn's prompts and reply as argv (`legacy_notify.rs`), readable through the process table, for every Codex session, and `Stop` already gives the turn end and the thread id. Grok gets `Stop`, `StopFailure`, `StopCancelled`, `SessionStart`, and `Notification` in its own `~/.grok/hooks/aggy.json` (`$GROK_HOME/hooks` when set, unverified), rather than relying on the Claude hooks Grok also runs: those miss `StopCancelled`, stop with `[compat.claude] hooks = false`, and exist only when Claude's hooks are installed.

Attribution: each installed command names its vendor, and `aggy hook` forwards it only when that is `AGGY_VENDOR`, the vendor aggy has on screen. Grok runs Claude's `settings.json` hooks too and sets `GROK_HOOK_EVENT` and `GROK_SESSION_ID` for every hook it runs, so a Claude-labeled hook that sees either is dropped; Grok's own hooks (`~/.grok/hooks/aggy.json`, which also carry `StopCancelled`, which Claude has not) report it instead. Each event is so forwarded once. Every process the CLI starts inherits `AGGY_SOCKET` and `AGGY_VENDOR`, and aggy cannot scrub them from the CLI's own tool subprocesses: a nested `claude -p` or `codex exec` run by the agent's shell tool, or the agent piping JSON into `aggy hook` (say, under prompt injection), reaches the socket as the on-screen vendor. So no hook event sets or replaces the index's session id on its own (see the session id table above), the socket marks only events from the CLI's process tree (peer-pid lineage, section 5), a limit reported by a hook counts only when so marked, and the switching logic (T6664) must treat even a marked hook event as a hint, not proof.

Two hook facts shape the wiring:

- **Codex trusts hooks by hash.** A hook in `hooks.json` or `config.toml` runs only once its hash is recorded as trusted (`[hooks.state."<key>"] trusted_hash`), which the user approves in interactive Codex, or with `--dangerously-bypass-hook-trust`, which aggy never adds on its own (a person's own needs `--no-policy` and gets a launch note). ## 12. Config changes: the manifest, `--dry-run`, and `aggy unwire`

Parity and tool wiring edit other tools' config: `~/.codex/config.toml`, Claude and Grok settings, skill folders, and MCP entries. Every such change is:

- **Planned.** `--dry-run` shows each file and the change before anything is written.
- **Guarded.** A patch names the file and the hash it expects. If the file has changed since, the patch refuses and writes nothing. Applying a patch twice is a no-op.
- **Backed up.** The old bytes are copied under `~/.aggy` before the write, and the write is atomic.
- **Recorded.** Each change goes into the manifest in the store: file, hash before, hash after, backup path.
- **Undoable.** `aggy unwire` restores every file byte for byte, or removes a file aggy created. It refuses to overwrite a file someone changed after aggy did.

No other code path writes another tool's config.

A patch is one of three kinds. A **content** patch rewrites a file through a transform (deleting a TOML or JSON entry is a content patch whose transform drops it; undo restores the bytes, so it needs no kind of its own). A **link** patch makes the path a symlink: it creates one, or replaces the file or link there. A **removal** patch removes a file or a symlink. Link and removal patches never follow a symlink at the path: they read it with lstat, record a symlink by its target (`link-` and the target's sha256, so a link's hash never equals a file's), back up a replaced file's bytes or a replaced link's target under `backups/<change-id>/<hash>.bak`, and act only on a path that still has the device and inode they checked. A link whose target is, or resolves to, a vendor credential file is refused, and so is replacing or removing one. Undo puts back the same file and mode, or the same link, or removes the link aggy made, under the same drift, superseded, blocked, and sweep rules as a content change. For these kinds, "the same file" is the link's own path (its directory made canonical, its name kept), not what it points to, so two links to one target are two paths. A content patch on a path that is a symlink still reads and writes through it (the limit below).

`aggy unwire (--change ID | --run ID | --all) [--dry-run]` undoes changes newest first (reverse id order), because a later change to a file was planned against the earlier one's result. Each undo runs under the target's lock, restores the old bytes and mode (or removes a created file and any directories made for it that are now empty), and marks the row undone. `--dry-run` prints the diff of each undo, escaped for the terminal. No-op rows and the marker row of a run that changed nothing are skipped.

A row is `pending` until its write is recorded, and `failed` when the write failed after the row was written. A `failed` row never wrote: the target write is an atomic rename, and the only error after it, a failed directory sync, is recorded as applied. Drift found by the re-check just before the write also leaves a failed row, with no backup. A failed row is *cleaned* whatever came after it (the file is not even read): the file is left as it is, only the empty directories its own Apply made are removed, and the row is marked undone. A failed row records only the directories its Apply made itself (one another process made between the plan and the mkdir is not aggy's), each with its identity; a directory it has no identity for is never removed by path alone. A pending row may have been written or not, so unwire compares the file with the row's hashes: still the hash before means nothing was written, and only empty directories made for a new file are removed (by path: a pending row stopped before it could record their identities); the hash after means the write happened before the process stopped, and it is undone from `backups/<change-id>` like an applied change, or fails loudly when that backup is gone; anything else is drift. Either way the change leaves nothing behind.

Before acting on a row, unwire checks that it looks like a change aggy could have made: the file is an absolute, clean path, the backup is named `<change-id>/<hash>.bak`, and every directory recorded as created is an ancestor of the file and below the home directory (never the home directory, an ancestor of it, or `/`). Any other row is refused untouched. This is a sanity check against a damaged or mistaken row, not a security boundary: whoever can write `~/.aggy` can plant a well-formed row and a matching backup together, and so can make unwire write or remove any file the person can. The backup is always read from the current `backups/` (the state directory resolved now), whatever prefix the row recorded, so a state directory spelled differently than when the change was made (`/tmp` and `/private/tmp`, or `~/.aggy` moved into a dotfiles directory and linked back) still undoes.

Any other change is undone only after every newer change to the same file (by canonical path) that is still in effect: applied, pending, or failed. `--change` refuses, forced or not, while such a newer change exists, and names it: undo it first, or use `--all`. In a `--run` or `--all` undo, an applied change behind such a newer change outside the selection is refused the same way. So is a pending change that a newer change was planned on (the newer change's hash before is this change's hash after): its write may have happened and is under the newer one, and `--all`, newest first, undoes the newer one before it. A pending change behind a newer change is *superseded* only when some newer change to the same file, still in effect, was planned on this change's hash before, under the target lock: that newer change read the file under the lock and found this change's write had not happened (a change planned where the file system cannot lock is recorded as `unlocked` and proves nothing, since its plan may have raced a live write), and while it is in effect nothing older can have been undone, so the file holds the newer changes' writes. It is left alone, only empty directories made for the old change are removed, and the row is marked undone. An undone newer change proves nothing, because undoing the changes between can bring the old write back. Any other pending change behind a newer change is refused the same way as above, because its write may have happened and been edited by hand before the newer change was planned on the edit; once the newer change is undone, the file no longer matches either of its hashes and it is reported as drifted, still pending, with its backup in place, for the person to see and undo by hand or with `--change <id> --force`. Nothing is marked undone while its line may still be in the file.

After any undo, unwire also sweeps the directories every undone change created and removes those now empty, unless a change still in place created them too. A created directory's identity is its device and inode, plus its birth time where the file system reports one (macOS and the BSDs; Linux has it only through `statx`, which the standard library does not expose), recorded once it exists. Device and inode alone do not prove a directory is aggy's: ext4 hands a freed inode number straight to the next directory made, so a directory the person removed and made again can match. So the sweep removes a directory only while its identity still matches, birth time included when one was recorded, and either a birth time was recorded (which on its own tells aggy's directory from a new one), or the unwire is related to it: it undid the change that created the directory, or itself removed a file aggy created inside it. A file found already gone relates the unwire to nothing, because the person may have removed it along with the directory and made the directory again. An unrelated later unwire never sweeps a directory known only by device and inode. APFS can rewrite a directory's birth time (a restore, or a tool that sets it) but never reuses an inode number, so during the undo of the change that made a directory, a device and inode match is enough; any other unwire still needs the birth time to match. Once aggy sees a recorded directory gone, or with another identity, it forgets the identity. Known limits, without birth times: if the person removes aggy's directory with aggy's file in it and makes it again, the unwire of that file's change removes the new directory while it is empty; and if an undo removed aggy's file and stopped before recording it, the next unwire finds the file gone and leaves the now-empty directory of an earlier undone change, rather than risk removing one the person made.

Two hand edits count as undoing aggy's change, not as drift: a file aggy created that now holds only white space is removed (with the directories made for it), and a file that is its old content plus one line ending, which aggy added before its own line, gets its old content back exactly.

A file changed after aggy changed it in any other way is reported and left alone, and unwire goes on with the rest. `--force` undoes one such change anyway: it needs `--change` and `--yes`, without `--yes` it only shows what it would overwrite, and the edited bytes are saved under `backups/<change-id>` first.

Known limits of a content patch (TODO(T6607) follow-up): a file that is a symlink is restored through the link, a hard link to a changed file is not kept (the restore writes a new inode), and extended attributes are not restored.

## 13. Security model

aggy runs with your privileges next to agents that can run shell commands. Every surface that carries outside text or writes config has a named control.

**What aggy never reads.** The goal is that aggy never reads the vendor credential files: `~/.claude/.credentials.json`, `~/.codex/auth.json`, `~/.codex/.credentials.json` (Codex's MCP token store), `~/.grok/auth.json`, `~/.grok/mcp_credentials.json`, and the same files under a relocated `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, or `GROK_HOME`. A guard enforces it: all file access goes through one wrapper, `internal/safefs`, which on every call:

- checks the path first, resolved through symlinks and compared in Unicode NFC and, on macOS, with full Unicode case folding and then the `/System/Volumes/Data` firmlink prefix removed (in any spelling APFS takes for it) (so `ſ`, `ß`, and the Kelvin sign match the way APFS matches them), and then acts on the resolved path
- refuses the credential files by file identity (device and inode, read from metadata only), so a hard link or a different spelling of the same file is caught
- reads through an opened descriptor, opened with `O_NOFOLLOW`, whose identity is checked before any byte is returned
- refuses, on macOS, any path in `/.vol`, which names a file by device and inode around every path check
- refuses a `RemoveAll` whose tree holds a credential path, or any entry with a credential's identity, before removing anything
- fails closed: when it cannot find an absolute home directory, or a relocation variable is a relative path, every call is refused
- refuses a regular file with more than one hard link, since its other name could be a credential file

Known gap: a hard link made to a credential before the vendor rotates its token keeps the old inode, now with one link and the old token, and safefs reads it like any other file. Remembering old identities was tried and removed: ext4 reuses inode numbers at once, so aggy refused its own new files, and the history was easy to delete or redirect. The gap is closed where such a file could leave the machine: a borrow's artifacts pass a gate (`internal/borrow`, artifact.go) that takes only a regular file with one link, made after the child started (its birth time; on Linux, which exposes none to aggy, its modification time), under a size cap (50 MiB for an image, 256 MiB for a video), whose magic bytes are PNG or JPEG for an image and MP4 for a video. Anything else is refused, and the report says why. Hardening is also still in progress for check-then-act races in the path-based calls (`Chmod`, `Remove`, `MkdirAll`).

Lint bans the main file-system entry points (`os`, `io/ioutil`, `io/fs`, `filepath` walks) outside `internal/safefs` and test files; every `syscall` name except an explicit allowlist (errno values, the open flags safefs needs, `Stat_t`, flock, process attributes, and darwin's `statfs` in one safefs file, for the file system type), in safefs too; signals and process attributes outside `internal/execrun` and `internal/store` (`internal/supervisor` may send signals); `os/exec` outside `internal/execrun`, `internal/supervisor`, and `internal/borrow`; every `net/` package except `net/url` and `net/netip` (and `net` itself, except in the supervisor socket's files, which may call only `net.ListenUnix` (the method forms `net.ListenConfig.*` and `net.Resolver.*` are banned too), and its client, which may call only `net.DialUnix` on a path it has checked is aggy's own socket, and `internal/execrun/proxynet.go`, which may only connect to a turned-on tool proxy's loopback address, GET its health path, and, after that proxy dies mid-session, listen on that same address and close each connection unread (T6780): every other dial, other listener, and name lookup stays banned), `log/syslog`, `debug/*`, `go/parser`, `go/build`, `unsafe` (and so `//go:linkname`), and cgo (`make nocgo` asks `go list` for each OS's cgo files, which lint cannot see when cross-compiling); `golang.org/x/sys/unix`, except for the socket's peer-uid and peer-pid calls in two supervisor files, darwin's `sysctl kern.proc.pid` for the lineage check, Linux's peer pidfd (the stdlib has no `getpeereid` or `LOCAL_PEERPID` on darwin), and Linux's `waitid` in `internal/execrun/reap_linux.go` (the kill before the reap; darwin uses the stdlib's kqueue calls, allowlisted by name in `reap_darwin.go`), and the atomic no-replace rename in safefs (`renameat2` `RENAME_NOREPLACE` in `rename_linux.go`, `renameatx_np` `RENAME_EXCL` in `rename_darwin.go`, and `linkat` then `unlinkat` in `rename_atomic.go` for a regular file on a file system without the flag); Go assembly and `.syso` objects, which make raw system calls past every ban (`make noasm`); `toml.DecodeFile` and `toml.DecodeFS`; the SQLite driver and `sql.Open` outside `internal/store`; the process-starting runner, which is its own package (`internal/execrun`) that only the files of `internal/cli` and `internal/devfix` (not their subpackages) and tests may import, so no other package can re-export it to the adapters, which never start processes, run commands only through the runner the caller passes, and may not import `internal/execrun`, `internal/cli`, `internal/devfix`, or `os/exec`; and requires every `nolint` comment to name the linter and give a reason. Lint runs for darwin/arm64, darwin/amd64, linux/amd64, linux/arm64, and windows/amd64. Other packages that open files are covered by review. The SQLite driver is the main exception to the wrapper: it opens the database and its `-journal`, `-wal`, and `-shm` files itself, by path, and the driver cannot be told not to follow a symlink, so the store pins the database by identity (`internal/store/pin.go`): before opening, it must be a regular file with one link and its sidecars regular or absent, and after every connection SQLite opens it must still be the pinned file, with `safefs` clearing all four paths. The others are fixed paths: `creack/pty` opens `/dev/ptmx`, and the supervisor's listener creates its socket (and sets its mode) in `run/`, after `safefs` has checked the directory and any stale socket. The read-only handle that `aggy log`, `aggy doctor`, and the `--dry-run` preview use carries a SQLite authorizer that allows only SELECTs and the `user_version` read, so it cannot `ATTACH` another file, change a PRAGMA, or `VACUUM`.

**What aggy never sends.** aggy collects no telemetry, sends nothing to the project, and makes no model or vendor API calls of its own. It never routes vendor traffic through anything unless the user explicitly turns on a local proxy tool for a vendor (section 9, T6780); then every request of that vendor's on-screen CLI, the login token included, passes through that local process, which aggy starts on loopback, checks, and stops. aggy's own network use for it is a connect and a health GET to that loopback address, and a listener there that reads nothing if the proxy dies. Every process the CLI starts inherits the variable, so the user's own scripts that call that vendor's API with a key go through the proxy too. The network surfaces aggy itself will open are all planned and opt-in: the remote client and chat connection, local webhooks, `aggy pr`, which opens a pull request on your git host, and `aggy usage`, whose ccusage reader may fetch pricing data unless it runs offline (section 21). Third-party tools aggy starts are kept from sending telemetry by default (T6822): every tool process aggy starts (an MCP server through `aggy tool exec`, a hook through `aggy hook-tool`, a CodeGraph prebuild or rebuild, and a local proxy tool, T6780) gets `DO_NOT_TRACK=1`, plus the tool's own documented opt-out from its definition's `telemetry_env` (CodeGraph 1.6.2: `CODEGRAPH_TELEMETRY=0`, from its README, verification.md), each over any value the person set. Headroom's proxy beacon honours `DO_NOT_TRACK` (live, 2026-10-29, section 9). Whether RTK, Context7, Playwright MCP, and Headroom's MCP server honour it or have an opt-out of their own is unverified (TODO(T6822)). `telemetry_env` is a built-in's only: a user definition that has it is refused, so a user tool gets `DO_NOT_TRACK=1` and nothing else. Even a built-in's holds at most 16 `NAME=VALUE` entries, each name of `A-Z`, `0-9`, and `_` naming telemetry (it holds `TELEMETRY`, `TRACK`, `ANALYTICS`, `OPTOUT`, or `OPT_OUT`), never one the env rules refuse (a base URL, proxy, secret, loader, or aggy, vendor, or cloud setting), one aggy builds the environment from or sets itself, or one that changes how a package runner, resolver, loader, or shell behaves (the prefixes `NPM_CONFIG_`, `PNPM_`, `YARN_`, `BUN_`, `DENO_`, `UV_`, `PIP_`, `PIPX_`, `COREPACK_`, `GO`, `CARGO_`, `RUSTUP_`, `RUSTC_`, `XDG_`, `SSL_`, `DOTNET_`, `ELECTRON_`, `LUA_`, a `_CA_BUNDLE` suffix, and `HOSTALIASES`, `LOCALDOMAIN`, `RES_OPTIONS`, `GCONV_PATH`, `ZDOTDIR`, `BASHOPTS`, `SHELLOPTS`, `JDK_JAVA_OPTIONS`), and each value is one of `0`, `1`, `true`, `false`, `off`, `no`, `yes`, `disabled`. `aggy tool add` and `aggy tool on` say what aggy sets. The person opts in with `[tools] allow_telemetry = true` in the user config (`~/.aggy/config.toml`; a repo's `.aggy/config.toml` has no `[tools]` table, so a clone cannot): aggy then sets none of these, the person's own `DO_NOT_TRACK` still reaches every tool process, hooks included, and the other variables pass through where the definition's `env` allows, as before. A user config that cannot be read keeps them set, and `aggy doctor` warns about it. Not covered: MCP servers and plugins in the person's own CLI config, which aggy does not start, and the vendor CLIs themselves, whose own telemetry settings are the person's. What a vendor CLI receives from aggy is limited to:

- a brief, which has lines matching secret patterns removed, can be previewed with `--brief --show`, and only goes to a vendor in the repo's `allowed_vendors`
- a borrow prompt: the task, paths, constraints, and date, never the parent transcript
- for research and news, only what the task needs; those children run in an empty temp directory, never see copied secret files, and have built-in file and shell tools removed (Codex research and news are refused until its `apply_patch` oracle is closed; see section 7)

**What other local users can see.** A process's arguments are readable by every local user through `ps` and, on Linux without `hidepid`, `/proc/<pid>/cmdline`. So the shared memory goes on Codex's and Grok's command line in the clear: Codex as `-c developer_instructions=…` (with the user's own system or user `developer_instructions` in front) and Grok as `--rules …`. Neither CLI has a file variant: Codex's only file key, `model_instructions_file`, replaces its built-in prompt (`config/src/config_toml.rs` at `6aaac69`), and Grok's `--rules` takes inline text only (`src/app/cli.rs` at `2bdd1d6a`). Claude reads a 0600 file instead. Codex's legacy `notify` hook is the same: Codex passes its JSON payload, the turn's last assistant message included, as the hook command's last argument (`hooks/src/legacy_notify.rs`). Keep secrets out of `.aggy/memory.md`, and on a shared machine use `hidepid=2` on Linux or skip the memory for Codex and Grok.

**What aggy stores.** Ids, paths, status, CLI versions, and connection status. Never tokens.

**Threats and controls:**

| Threat | Control |
| --- | --- |
| A planted instruction on a web page puts a secret into a search query | Research and news run in an empty temp dir with built-in file and shell tools removed, and get only what the task needs. Grok's flag set also removes MCP meta-tools. Codex is refused for both kinds, because `apply_patch` can confirm guessed file contents (section 7). |

| A hook payload runs as shell input | Fixed binary path, JSON parsing, never a shell. |
| Webhook text steers an agent with a shell | Localhost only, a required shared-secret signature, the payload wrapped as data, and a watcher child that is read-only or in its own worktree. |
| Someone else drives your terminal | Remote client pairing with a one-time code, per-device tokens, LAN by default, no project-run relay. |
| A tampered release | Signed checksums, build provenance, pinned dependencies. |

## 14. The store

Per-user state lives in `~/.aggy` (or `$AGGY_HOME`):

```
~/.aggy/
  config.toml                 user config
  aggy.db                     SQLite index
  backups/                    copies taken before any config change
  inbox/<borrow-id>.md        finished borrow reports
  research/<date>-<slug>.md   research and news reports of borrows run outside a git work tree
  research/cache/<key>.json   the research cache, by question
  recipes/<name>.toml         saved segues (M6)
  run/<parent-id>.sock        supervisor socket for hooks, aggy switch, and aggy tool notices
  logs/aggy.log
```

Per-project state lives in `<repo>/.aggy`. The folders of aggy's own output (`briefs`, `research`, `assets`) each hold a `.gitignore` of `*`, made through the `.aggy` rule (`internal/aggydir`), so `git status` and `git add .` pass them over; the repo's own ignore files are not touched. `.git/info/exclude` gets the line `.aggy/` only from `aggy memory import` (section 10), through the manifest:

```
<repo>/.aggy/
  config.toml                 allowed_vendors, tools_off, check commands, worktree copy list, setup command
  task.md                     current task state
  memory.md                   shared lessons, 4 KB cap
  briefs/<child-id>.md        briefs handed to children
  research/<date>-<slug>.md   research and news reports
  assets/<path>.json          sidecars for generated images and video
```

The index is SQLite in WAL mode, with the file at mode 0600, in a directory created 0700 if it does not exist, using a pure-Go driver. One index covers every directory. The driver opens the database, `-journal`, `-wal`, and `-shm` files itself, outside `safefs`, and cannot be passed `SQLITE_OPEN_NOFOLLOW`, so the store pins the database file by identity: it refuses a symlink or a non-regular or multiply-linked file there or at a sidecar before the open, and checks after every connection opens that the file is still the pinned one and that `safefs` clears all four paths. SQLite's own unix VFS refuses a symlinked journal, `-wal`, or `-shm` with `SQLITE_CANTOPEN`, which covers a sidecar planted after that check.

| Table | Holds |
| --- | --- |
| `parents` | id, title, directory, last vendor, created, last active |
| `children` | id, parent, vendor, vendor session id, kind, model, cwd, worktree, transcript path, status, process lease, last active |
| `borrows` | id, child, kind, vendor, model, task hash (of the normalized task and its inputs, section 8), budget, status, outcome, artifacts, image count, tokens, report path, start, end |
| `changes` | the config-change manifest: file, hash before, hash after, backup path, applied, undone |
| `probes` | per vendor: CLI path, version, connected, capabilities, probed at |
| `vendors` | what `aggy setup` last found, one row per vendor: connected (`connected`, `not_connected`, or `unknown`), CLI version, checked at |
| `events` | append-only log behind `aggy log`, security refusals (`refusal`) included |

The diagnostic log is a second database, `diag.db`, made and checked the same way, with its own migrations: one `records` table of events, reason codes, and correlation ids (run, trace, cause, parent, child, borrow, worktree), pruned by `aggy gc` per `[log]`, and read by `aggy diag`. [logging.md](logging.md) is its convention.

## 15. Vendor adapters

Every flag, file path, hook format, and transcript format aggy depends on goes through one adapter per vendor. All three CLIs update often, so a CLI change is fixed in one package, and adding a vendor is one adapter plus its routing entries.

Adapters build commands and parse output; they never start processes. They probe each CLI's version and capabilities, re-check them when the version changes, and degrade instead of failing. Each adapter declares the CLI versions it is tested on, and `aggy doctor` warns outside that range.

The interface is documented in [adapters.md](adapters.md). The interface is unstable until M1, while the first vendor adapters are built; adapters.md lists the known gaps.

**Open harnesses and API keys (planned, M8).** Only the on-screen OpenCode part is built (T6932, [verification.md](verification.md)): the launch, the rules with the shipped starter, the screen split, instructions, the guard and reporter, and supervision. Not built: `aggy key`, `--with-config`, the plan table and first-run questions, per-plan limits, `/aggy permissions`, approvals added to the list, suggestions from Claude Code, and `/switch <model>`'s grouped list (`TODO(T6932)`). OpenCode has been run live as [verification.md](verification.md) records; Hermes has not, and the other vendor facts below were read on 2026-11-06. Until it ships, the constraints in section 2 hold as written; when it does, "Official binaries only", "Vendor sign-in only", "No credentials", and "Subscription, not API" change as this says, and CLAUDE.md, including its rule on the on-screen environment, the README, CONTRIBUTING, and [adding-a-vendor.md](adding-a-vendor.md) change with them.

- **OpenCode.** From a spike at 2.2.5 and a review of it ([verification.md](verification.md) marks each fact live, fake-model, or source).

So a repo the person trusted for OpenCode (`aggy trust --opencode <dir>`, recording the repo root so a subfolder is not treated differently, since a subfolder launch still runs the root's plugins, and separate from the Codex and Grok trust in section 10, which changes what they load) gets the full screen, with OpenCode's own model command and full auto available. Any other repo gets `mini`, the whitelist, and a model chosen at launch, with a note pointing to Claude Code. The command says plainly that the repo's screen plugins will run. An empty launch folder plus `--session` kept the plugin from running on the full screen, but new sessions then start in that folder, so that is not used.
  - **Launch.** aggy removes every `OPENCODE_*` variable it inherits, since `OPENCODE_CONFIG_PROJECT_DISABLE=0` beats the variable below, and sets its own: `OPENCODE_DISABLE_PROJECT_CONFIG=1`, `OPENCODE_CONFIG` with aggy's config, rewritten at each launch and never a manifest entry, `OPENCODE_CONFIG_DIR` at a folder aggy owns, and `OPENCODE_DISABLE_AUTOUPDATE=1`, since aggy tests a pinned version. System and managed policies remain, so `aggy doctor` warns about them. A repo's own OpenCode config stays off even in a trusted repo unless the person asks with `aggy trust --opencode --with-config`, since it can allow everything, disable the guard, run a local MCP server, read files through `{file:}` and `{env:}`, and repoint a signed-in provider, and the command says so.
  - **Rules.** Allows go in `permissions`, as an ask for `*` plus the listed rules, since `policies` only ever deny. Denies go in `policies` on `tool.use`, one per tool (`read`, `edit`, `shell`, `grep`, `glob`, `external_directory`, `webfetch`, `websearch`, `subagent`, `skill`, MCP tools), since a rule for one does not cover the others; `grep`'s and `glob`'s resource is the search pattern rather than a file (source), so a path rule there matches only a pattern spelled that way, and aggy lists literal names for `grep`; the session's own `todowrite` and `question` are allowed, or every plan and question would ask first; `execute` has no permission check, but its inner calls reach the guard. A path deny stops the read tool only: `cat` or `python3` in the shell still reads the file.
  - **Modes.** The default is a whitelist: listed commands run with no prompt, and anything else asks, edits included, since the shipped starter lists none, with OpenCode's Allow once, Always allow, and Reject. A compound command needs every part allowed, so most rewordings miss the list and ask. This is not airtight: OpenCode's permission check skips variable declarations, so `PATH=<dir>:$PATH; git status` or a changed `GIT_CONFIG_VALUE_0` ran arbitrary code with no prompt under an allowed `git status` (fake model). The scanner gives no resource to any statement that only sets a variable: a declaration, a `for` or `select` variable, or `(( ))`, even inside `$(...)` or a compound command, so `for PATH in ./bin; do git status; done` also ran a planted git with no prompt (live, on a fake model). The guard's scan of the command's text covers the variables that matter (see Guard). That catches mistakes only, and the launch's own git variables give a model something to change, so `-c` in the rule is preferred where it is enough. Full auto is a setting, only in a trusted repo, and maps to `--auto`, seen live: a shell command or edit that is not denied runs with no prompt, headless and on screen and in a resumed session, hard denies hold, and nothing is saved. OpenCode has no classifier like Claude's and aggy makes no model requests, so setup says once that full auto has none. A shared `ask` rule is answered once under `--auto`, so it does not hold there. Shipped exact rules were tested with a fake model, not under `--auto`.
  - **Whitelist.** One list with three sources, each entry showing where it came from in `/aggy permissions`, a deny always winning, and only on OpenCode: it is never rendered to Claude or Grok. A rule matches a command exactly, with no wildcard, because `git diff *` allows `git diff --output=<file>`, which wrote a file, and `ls *` allows `ls > x`. OpenCode gives `*` and `?` in a rule their wildcard meaning with no escape, and expands `{file:}` in rule text, so aggy refuses a command containing `*`, `?`, or `{` as a rule rather than listing it as if exact. That means more prompts than wildcards would give, such as for `git log -5`. aggy ships a small starter, such as `git status`, and `git diff --no-ext-diff --no-textconv`. It sets git config at launch so `core.fsmonitor` from a repo cannot run a script, but a repo's clean filter, and a hook such as `post-index-change`, can still run from `git status` or `git diff` once a tracked file's time changes, with no known stop. So even the starter can run a repo's code; those need a `.git` folder, which a clone does not bring, so an archive or an earlier write is the route. `cd anywhere && git status` still passes. Approvals in aggy add to the list per project. Commands that run code or read arbitrary paths (`python3`, `npx`, `find`, `rg`, `awk`, `sed`, `cat`) are never added, and listed edits cannot include anything under `.git`, at any depth. In a repo trusted for OpenCode the starter also lists `read`, `grep`, and `glob`, or every read would prompt. Not in other repos: a cloned symlink to a key file was read and sent to the model with no prompt under a `read` allow, past a deny on the target's name (fake model), so reads there ask. The guard also resolves the real path of a read, expanding `~` as OpenCode does, and refuses one outside the repo, except OpenCode's own saved tool output, and refuses the denied names in any case; `grep`'s search text is not covered (unit tests). A shared rule with a wildcard is named and skipped here, since `Bash(git diff *)` would bring the wildcard problem back. Only an exact command with no wildcard is rendered, so most approvals in Claude do not carry over to OpenCode. OpenCode's own Always allow is not aggy's list: it saves a wildcard such as `python3 *` or `git push *` in `opencode.db`, it cannot be turned off, and its rows beat `ask`. A `permission` plugin hook can reset ones that break these rules back to ask, but that fails open if the plugin breaks. Those rows cannot be shown in `/aggy permissions`, and carrying them to other harnesses would need the plugin to report them (unverified).
  - **Suggestions from Claude Code.** Each time aggy opens, a goroutine in the aggy process, which never delays the launch and is not a daemon, reads new lines through `safefs` in this repo's Claude Code session files, with no model. It checks each line's `cwd`, because different folders can share a session folder name, and records commands with counts, dropping any line that holds something secret-shaped rather than storing an edited copy, for shell calls that ran in `auto` without an error, in small transactions with its read position so a second aggy cannot double-count. New candidates get one line on screen. `/aggy permissions suggest` (`--all` for other repos) shows each command, all of this through `termsafe`, and adds only what the person confirms at the keyboard. These files are plain text a model's shell can write, so a line can be forged, and a command having run does not prove it safe. The fields it reads (`permissionMode`, `is_error`) are recorded in verification.md and are not a documented format, so a change makes it stop quietly and `aggy doctor` says so. An error cannot separate a denied command from a failed one, so both are skipped.
  - **Guard.** A plugin aggy ships, from the folder aggy owns (only the directory form loads), whose `execute.before` hands each command to a local aggy check. It sees subagents' and `execute`'s inner calls, refused under `--auto` with the model seeing why, and a crashed, hung, or missing check refuses. It catches mistakes only: it sees the raw command, so a variable, a glob, a script, or base64 gets past it, and text denies are weaker still (`shell:curl *` missed 15 of 26 shapes).
    - **When the scan runs.** Only when it matters: when every command left may be allowed, so nothing prompts. If the text holds no allow rule, OpenCode asks and the person sees the command, and a refusal would only replace a prompt they could answer. So the scan runs if the text holds a full rendered allow rule as words, in any of the three forms below with whitespace collapsed. A short rule such as `ls` matches as a word, which only runs the scan. OpenCode itself needs far less: a resource must be the rule exactly, since `Wildcard.match` has no whitespace rule, so `\git status`, `command git status`, `/usr/bin/git status`, and `g"it"   status` ask (source); they count here anyway.
    - **Always allow.** A rule approved with OpenCode's Always allow is not in the rendered list, and OpenCode saves it per project in `opencode.db`, past the session (`permission.ts`). `permission.replied` carries the reply (source; not seen live). When it is `always`, the plugin tells the guard for the rest of its session and runs `aggy hook opencode-always`, which leaves a mark per repo in `~/.aggy/opencode-always`, so the guard scans every command in that repo from then on, in later sessions too. A mark aggy cannot read counts as seen, so losing the plugin's state or the mark's folder only scans more. Removing the file goes back to the rule above. **The gap:** a command approved in a way aggy cannot see, such as Always allow in OpenCode opened by hand in that repo, or in an aggy session whose report failed. `PATH=./bin; npm test` then runs a planted `npm` with no prompt. aggy never opens `opencode.db`, so it cannot check (T6953).
    - **What the scan refuses.** It does not parse shell and knows nothing of quotes. It reads the raw text, again with line continuations removed, and again with quotes and backslashes removed too, and any of the three can refuse. It refuses: a variable on its list named as a bare word, unless every mention reads it (`$PATH`, `${PATH`, but not `${PATH:=x}`), in any syntax, including comments and quotes; a setting shape of a common-word zsh name (`path`, `cdpath`, `fpath`, `manpath`, and zsh/parameter's `commands`, `functions`, and `aliases`: `path=`, `path+=`, `path[`, `for x path in`, `read a path`); a definition of a function named as the first word of a rendered allow rule (`git()`, `function git`, today `git`, `ls`, and `pwd`); and a declaration builtin or `unset` with a `$` or a backquote where a name goes, in any word, while `export A=$X B=$Y` passes. The refusal names the variable or function, and gives the usual ways round: `git --no-pager`, `git commit -F`, and the grep tool. The list comes from what changes the shipped whitelist, each with its reason in `internal/hook/opencode.go`: `PATH`, `GIT_*`, `LD_*`, `DYLD_*`, `DEVELOPER_DIR` and `TOOLCHAINS` (on stock macOS `/usr/bin/git` is a shim that honours them, and `export DEVELOPER_DIR=./dev; git status` ran a planted `xcrun` in bash and zsh), `GCONV_PATH`, `BASH_*`, `ENV`, `SHELLOPTS`, `BASHOPTS`, `PS4`, `ZDOTDIR`, `HOME`, `XDG_*`, `CDPATH`, `FPATH`, `MANPATH`, `SHELL`, `PAGER`, `MANPAGER`, `LESS`, `LESSKEY`, `LESSOPEN`, `LESSCLOSE`, `EDITOR`, `VISUAL`, and `RIPGREP_CONFIG_PATH`. `GOOS`, `CGO_ENABLED`, and the language tools' variables (`GOFLAGS`, `NODE_OPTIONS`, `PYTHON*`, `PERL5*`, `RUBY*`) are not on it, since no shipped rule runs those tools. Nor is `IFS`: bash, zsh, and dash split only expansions, and no shipped rule holds one, so it cannot change an exact rule's command, and `while IFS= read -r line` is too common to refuse. A rule with an expansion would need it back.
    - **What that costs.** Beside an allowed command, a commit message or a search that names `PATH` is refused, as in `git status && git commit -m 'fix PATH'`, and so is `CDPATH= cd sub && pwd`. A search for a rule's short name can be read as one: `rg 'ls\(\)' src` holds `ls` as a word, and with its quote marks gone it looks like a function called `ls`.
    - **What it does not cover.** Any declaration of a variable not on the list passes, and it can still affect a whitelisted command, only through a variable missing from the list. A name split by quotes or a backslash is refused, as is one built at run time in a declaration builtin or `unset`. Elsewhere a name built at run time passes the scan: `eval "${X}TH=./bin"` asks, since `eval` is a resource, but `x=GIT; (( ${x}_CONFIG_COUNT = 0 )); git status` has no resource and runs with no prompt. zsh's `git foo() ./bin/git`, a function of two names with no braces, passes the scan, since telling it from a commit message would need parsing, and OpenCode's own scanner fails that call (source). The promise stays guardrails until T6939.
    - **Under `--auto` the scan is skipped**, since auto runs `./bin/git status` directly with no prompt, so a declaration hides nothing there. Denies still apply: they match each simple command's text, and a declaration does not change that text, so `PATH=./bin; rm -rf x` is denied as `rm -rf x` is. A denied word hidden in a variable (`x=rm; $x -rf y`) gets past them with or without the scan. The launch tells the guard through the plugin's options, not the tool call, and `--auto` cannot be turned off during a session (`tui/src/context/permission.tsx` at `v2.2.5`). A session started without it and put on auto in OpenCode's settings keeps the scan. The path checks and the `opencode auth export` refusal apply in every mode.
    - **Other refusals.** It refuses a tool call outside the launch's folder (unit tests; `/open` was not run under aggy), because the full screen's `/open` moves a session to another project with the first repo's settings: in a test, full auto carried over and ran a command there with no prompt, and that project's `allowed_vendors` and trust would not apply. That is a limit if the guard is not loaded, and opening an existing session may send its history with no tool call for the guard to see (unverified). It loads per folder and can be overwritten or unloaded mid-session, and a plugin that fails to load gives no error. So it reports to aggy's socket per folder, and a missing report shows a warning. That is not a guarantee, since a same-user process can forge it.
  - **Models and providers.** `provider.use`, as a deny-all plus an allow-list in `OPENCODE_CONFIG`, limits the list to the person's plans and keys and to the repo's `allowed_vendors`, since OpenCode is one vendor with many destinations. A repo must allow `opencode` for it to run at all, and then `xai` counts as `grok`, `openai` as `codex`, and any other provider needs its own name in the list, which `internal/config` must learn to accept. Narrowing can stop a resume whose model's provider is denied (exit 1, no request), and aggy says why. It held against a repo trying to re-allow. A model that is denied exits 1 with no request on `run -m`. It always denies `claude-agent`, which runs the local `claude`, and `opencode`, since `opencode/*` free models send prompts to OpenCode's own service; `anthropic` is allowed only for an API key added with `aggy key`. On-screen launches drop API-key variables, which would otherwise add providers. A key already stored in OpenCode itself is untested.
  - **Keys.** `"apiKey": "{file:<path>}"` reads a 0600 file aggy writes per session, removes at exit, and sweeps at the next launch after a crash. This does not protect the key from the shell, so a key session warns the person. Removing the file early does not work: OpenCode reads it at config load, per folder, and after a new folder or a reload it sends no key and reports no error. A missing file leaves the provider listed, so aggy lists a key provider only in a session that has its key. The server password also exposes the key through `/api/config`: tool shells inherit it under `opencode serve`, and under `--standalone` it is out of the tool's environment but visible to the same user through `ps`, so a shell can still get it.
  - **Supervision.** The full `opencode` screen uses the alternate screen and the mouse; the switch picker works on both screens (live), and mouse, focus, and private-mode reports do not count as typing. `--session <new id>` sets the id. `/exit` exits 0, but over a permission dialog its letters are dropped and Enter chooses Allow once, so aggy must see no pending `permission.asked` or question (`form.created` in OpenCode's events) before typing it, and keys sent during one are not composer text. An ask whose reply never arrives holds the switch, and the person is told to check the prompt, and that picking the vendor again goes on. On the full screen an Enter in the same write as the letters is lost, so aggy sends it 0.5 s later (live). In that gap keys are held: typing takes the command back and cancels the switch with the text in the prompt, and a reported dialog stops the Enter and tells the person. A race remains: a dialog OpenCode has opened but not yet reported, since the report comes through a process the plugin starts, still gets the Enter, which would choose Allow once. A reply can lag the same way, so keys typed just after answering may not count as composer text. The full screen ignores SIGHUP and SIGTERM, so aggy sends SIGKILL 10 s after its terminal goes or it gets either signal, with `--direct` too (live for a closed terminal). A SIGKILL to aggy cannot be handled, so that session outlives it. A per-launch plugin reports `session.execution.succeeded`, `failed`, and `interrupted` with the session id, works with project config off, and adds slash commands that use no model turn, which replaces hooks here. The ChatGPT limit shows as `provider.chatgpt-limit`, and a generic `provider.rate-limit` covers others; xAI has no specific type and no real limit has been seen, so a 429 is the fallback.
  - **Transcripts and instructions.** Sessions live in `opencode.db` with the credentials, so `opencode.db*`, the legacy `auth.json`, and any `OPENCODE_DB` or channel path go on the `safefs` deny list, and aggy reads transcripts only through `opencode session export`, an `experimental` API. The guard also refuses `opencode auth export`. OpenCode reads no `CLAUDE.md`, and project config off drops `AGENTS.md`, so aggy opens those files, and the shared memory and a brief, itself through `safefs`, refusing a symlink, and passes a copy by absolute path in `instructions`. A repo's `CLAUDE.md` passed by path would follow a symlink: one to a canary reached the request body.
- **Hermes.** Takes the key as an environment variable, since `--api-key` shows in `ps` and its own store is a plain `~/.hermes/.env`. That is weaker: Hermes's own docs say its terminal tool can read denied files, and any process it starts can read the variable. It has command approvals only (`command_allowlist`, `approvals.deny`, in global config), with no general rules for file reads, so shared permissions reach it only in part, and a repo-scoped approval cannot stay per repo. Shell hooks can block a tool call and carry a session id; a turn-end signal is unverified. Hermes is also a personal agent with a long-running gateway and messaging. aggy supervises the CLI only: the gateway runs outside any aggy session, so it keeps Hermes's own key store, and aggy neither starts it nor gives it a key.
- **Borrows.** No open harness is routed to until its lockdown passes the same read test as the others. An environment-only key does not reach a borrow child; the child's environment allowlist would need a narrow, reviewed exception.

## 16. Other commands

- `aggy setup` checks Claude, Codex, and Grok in turn: it finds each CLI on `PATH` and probes it through its adapter for version, capabilities, and sign-in status. You can skip any and rerun setup later; `--only claude,codex` picks vendors, and `--yes`, or a stdin that is not a terminal (`/dev/null` counts as none), checks without asking, and input that ends at a prompt switches to that for the rest, so every vendor not skipped is recorded. A CLI that is not signed in gets the vendor's own sign-in step printed (`claude` then `/login`, `codex login`, `grok login`), and on a terminal setup waits and checks again. aggy never runs a login itself: no adapter has a verified login command. Nor has any a verified sign-in status command yet, so today every installed CLI's status is `unknown`. Setup records only, per vendor, connected or not, the CLI version, and when it checked (the `vendors` table). It writes no vendor config; applying the parity layer comes with M2.
- `aggy doctor` checks, per vendor, install, the CLI version against the adapter's tested range (`adapter.VersionWarning`, a warning, shown only here), and sign-in status; the API-key variables, the base-URL variables, and the vendor config settings that route a CLI to an API key or another endpoint (named by variable, file, and key, never by value); and config drift, which is an `aggy unwire --all` dry run that takes no locks and writes nothing (`manifest.Drift`), so doctor and unwire cannot disagree: a change unwire would refuse without `--force` is drift (warning); one it cannot check, such as a row naming a credential file, which is reported and never read, or an invalid row, is an error; one waiting on a newer change to the same file that is still in place, which must be undone first, is info naming that change; one unwire would undo cleanly (restored, removed, cleaned, superseded) is not reported. Its Tools section (T6710) checks the managed tools against the switches, per tool and vendor, in the current repo, reading only: a refused user definition and a user file that is not the one `aggy tool add` recorded (`tool.def_invalid`, `tool.changed_since_add`); for each tool that is on, a program not on `PATH` (`tool.exec_refused`), a name clash with the CLI's own servers from every source the launch reads (`tool.name_clash`, `tool.wire_failed` when one cannot be read), a `{repo}` the repo's path cannot fill, and a hook that approves or that the CLI takes no per-session form of (`tool.hook_approves`, `tool.no_launch_flag`), all from the launch's own checks (`toolwire.MCP`, `toolwire.Hooks`); Grok as "on for grok, not wired: unverified" (`tool.vendor_unverified`, info); and each skill's links: one for a vendor the tool is off for, or for a tool no longer loaded (`tool-skill-stray`), one missing for a vendor it is on for (`tool-skill-unlinked`), Grok's `[skills] ignore` not matching the links (`tool-grok-ignore`), and the folder missing or changed since first linked (`tool.skill_missing`, `tool.skill_changed`): a tool with a server or hook whose skill changed is reported per vendor as not wired, as the launch refuses it (R80-3, `changedSkills`). Each problem is a warning naming the command that fixes it. Its message is aggy's fixed text; anything else (an error, a path, a config's server name) goes in the detail, which `--report` leaves out, and so do a user tool's name and the fix naming it (H83-1). A file put in `~/.aggy/tools` by hand is reported apart from an edited one, with its own fix (move it out, then `aggy tool add` it); `aggy tool on` and a session's `--tool` refuse both (M83-3, R76-F1). Doctor fixes nothing. Each finding has a stable code and a level: **error** when aggy cannot work as set up (no vendor CLI, a CLI that fails its version check, a changed file that cannot be checked, an unreadable index), **warning** when something may cost money or surprise you (API keys, base URLs, config routes, an untested or unreadable version, not signed in, drift), **info** otherwise. It exits 1 when any finding is an error, writes nothing but an error finding's code to the diagnostic log, and never creates the index. `aggy doctor --report` prints the same findings for a public issue: aggy's version, OS and architecture, each CLI's version, and each finding's level, code, and message, scrubbed: a finding's path is kept apart from its message and shown as `~/…` under home and as `<path>/<base name>` anywhere else (so spaces in a path cannot leak it), error text from a CLI or the system is left out, any other absolute path in the text also becomes `<path>/<base name>`, the user name is replaced wherever it stands as a word (unless generic, such as `root`), and then the fixture scrubber (`internal/devfix`) removes home paths, host names, emails, UUIDs, and token-shaped text; it holds no environment value, file content, or session id.
- `aggy switch <vendor>`, run by a linked skill inside a CLI aggy supervises, sends a `switch-request` over `AGGY_SOCKET` (section 5) and says whether aggy queued it; the user still confirms at the turn end. Outside aggy it fails and says to use the switch key.
- `aggy check` runs the repo's typecheck, lint, and tests from repo config: the `check` list in `<repo>/.aggy/config.toml` (for example `check = [["go", "vet", "./..."], ["make", "lint"]]`), in order, at the repo root, and nothing else; it never guesses commands from `package.json` or a Makefile. The commands are the repo's own code, so aggy prints them before it runs them and runs them only when asked. The config is untrusted input: at most 20 commands of at most 64 arguments, no control or format characters, and a program that is a bare name found on `PATH` or `./` and a clean path inside the repo (no `..`, no `.git`, not resolving outside the repo), never a shell string. Each runs through `internal/execrun` with the scrubbed environment (no API keys or proxy settings), no stdin, the last 1 MiB of each output stream kept, and a time limit of `check_minutes` (default 10, at most 120) that kills its process group, as do Ctrl-C, SIGTERM, and SIGHUP. When the command exits, whatever it left running in its process group is killed too; a process that left the group (`setsid`) escapes that, and tracking it (a Linux subreaper or cgroup) is a follow-up. aggy prints one line per command and, for a failing one, the last 20 lines of its output with every secret-shaped line removed (`internal/redact`); nothing is stored. It exits 0 when every command passed, 1 when one failed or none is configured, and 2 on a usage or config error. Run by hand in an edit worktree (a directory under `<state>/worktrees/`, compared by real path), it refuses: that config and code are the child's, and `aggy check <borrow-id>` from the main checkout is the gate for them (section 7).
- `aggy log` records which harness and model were on screen (a `screen` row once the CLI of a launch that is not a switch's has started), the switches (a `switch` row once the next CLI has started: from, to, model, and why: `user` for a pick in the list, a pick again over another's switch included; `agent` for `aggy switch` from the session; `limit` for a limit aggy queued, `limit, unverified` when only a hook reported it; or `back: it never started` when aggy reopens the CLI before one that never started), the borrows, and the files changed (a `files` row when `aggy accept` applies an edit borrow's diff, with at most 50 names and a count of the rest; changes made inside an on-screen session are not logged). A restart of the same session for a tool change (section 9) writes no row, and neither does a launch that ends before its CLI starts. `aggy inbox` holds finished borrows.
- `aggy stats` (T6700) shows the finished borrows per kind and vendor from the borrows table: how many ran, how many ended `ok`, the average tokens and time of an `ok` one, and how many `ok` ones were redone (section 8), as "1 of 4 (25%)". It opens the index read-only, as `aggy log` does: it never creates, migrates, or writes it, and an index older than schema version 12 is reported, not upgraded. The numbers are aggy-observed and say so: tokens are what each CLI reported for its borrows, not vendor billing, and a vendor whose output gives no count shows 0. Running borrows are left out. It prints a plain table only; no other command has a `--json` form yet.
- `aggy gc` prunes finished worktrees, closed children, stray processes, old inbox items, and expired research, and only what aggy made, inside its state dir and index. As built (M3):
  - **Worktrees.** It removes an edit worktree accepted 30 days ago (its branch is kept until then for `aggy pr`), one whose reject was cut short, and a pending one whose borrow ended 30 days ago (a pending one first moves to rejected, the lock accept takes too). Each must be a record whose path is `<state>/worktrees/<id>` and branch `aggy/edit-<id>`, whose borrow is not running, whose lease is free, and whose path is a real directory, not a symlink. An accepted one is listed and kept, never removed, while it differs from the accepted tree (a tracked file changed, or a new file that is not ignored; ignored files such as `node_modules` do not count) or aggy's branch has commits past its base whose tip is not the accepted tree (commits the edit child made of its own work, which hold exactly that tree, do not keep it, and the listing says how many commits removing the branch deletes); acceptance time is `worktree_accepted_at` (an index from before version 14 uses the borrow's end). It is removed the way `aggy reject` removes one (`git worktree remove`, a compare-and-swap `git update-ref -d` of aggy's branch, only aggy's own admin entry when the directory is gone, never a repo-wide prune), except that its branch is judged again once the worktree is gone and deleted only at the commit judged, so a commit made in between keeps it. A pending one past 30 days keeps its branch by the same rule as an accepted one: commits past its base whose tip is not the recorded tree keep the branch, and only the worktree goes. A branch kept with nothing else left is summed up in one line per run, not one line per branch. The removal is claimed in the store first (`worktree_removed_at`, schema version 14), so reject and gc never both act on one, and an accept refuses a removed worktree. Each one's record is read again just before it is removed, after the person answered, and it is skipped if its borrow runs or its lease was taken since. A removal cut short (a crash after the claim) leaves a directory that the next gc removes, checked the same way; a crash after the directory went leaves aggy's admin entry or branch, which the next gc also removes, and a leftover with neither (or with an admin entry `dropAdmin` would refuse) is not listed. A leftover's branch is deleted only by the same rule: one with other commits (the person checked it out and committed) is kept and listed as kept, and only its directory and admin entry go.
  - **Children.** A closed borrow child last active 30 days ago leaves aggy's index, unless its lease is held or a worktree of its is still there; its borrows stay, for stats. Interactive children are sessions the person can resume and stay. Vendor session and transcript files are never touched.
  - **Stray processes.** A lease records aggy's own pid but no start time. A lease whose lock is free has a dead holder, so a live process with its pid cannot be shown to be that holder: gc lists it and kills nothing. Processes a child moved out of its group (`setsid`) are not recorded and so are not found.
  - **Inbox and research.** An inbox report last written 30 days ago is removed (and no longer listed); a research cache entry past its time to live (a day for news, a week for research; an unreadable one by its modified time) is removed. Only regular files with the names aggy gives them, directly in `inbox/` and `research/cache/`; a symlink is refused.
  - **Retention.** The days are set in the user config only, `[gc]` with `pending_worktree_days`, `accepted_worktree_days`, `closed_child_days`, and `inbox_days` (each 1 to 3650, default 30); a repo's config has no such table, so a cloned repo cannot make aggy delete sooner.
  - It shows what it would remove, with sizes, then asks on a terminal; without one it removes nothing unless given `--yes`. `aggy gc --dry-run` shows the same list and removes nothing: it opens the index read-only and never creates, migrates, or writes it. A borrow child (`AGGY_DELEGATED`) cannot run it.
- `aggy usage` reads each connected CLI's local usage logs (through ccusage and `grok usage`) and shows consumption. ccusage may fetch pricing data unless run offline (section 21). Remaining allowance appears only where a vendor writes its limit state locally. As built (T6698): `aggy usage` shows, per vendor not recorded as signed out, the remaining share and reset time of each window Codex last wrote to a rollout (the session's quotas only, as for limits in section 11; the newest of the last eight days' rollouts that holds any, read like the limit watch), and, for Claude and Grok, says aggy cannot see what is left: no local allowance file of theirs is recorded in docs/verification.md, so none is read. Where a vendor's share used is at or past `[switch] warn_at`, a `near limit` line follows (T6699): the largest share used among the ordinary Codex quota's windows whose reset is still ahead (a model-scoped quota is left out, as Codex's own usage warnings key off the ordinary quota alone; a window with no reset time or length, one already past, or one that resets further ahead than it lasts, stale or forged, says nothing about now; a rollout dated more than a minute ahead is skipped). An unreadable user config does not stop `aggy usage`: it says so on stderr and uses the default `warn_at`. The same rule drives the near-limit warning in `aggy run` (section 5), so which vendors can warn is: Codex, from its rollout's `token_count` rate limits (source-checked, section 11); not Claude or Grok, whose CLIs write no remaining allowance locally that docs/verification.md records. Their consumption alone would mean guessing a quota, so they never warn. Then, for every such vendor, the borrows aggy ran in the last seven days: count, the tokens the CLIs reported (and how many borrows reported none), and wall time, labelled as what aggy observed, never as the vendor's count, bill, or allowance; on-screen sessions are not counted. No dollar figure is shown, and Codex's credits balance is left out (its unit is not recorded). ccusage and `grok usage` are not used yet (T6696). It opens the index read-only and never creates it.
- Attribution: aggy sets `AGGY_VENDOR` and `AGGY_MODEL` (when a model is configured) for each child, on-screen and borrowed, and a commit hook adds them as `Aggy-Vendor:` and `Aggy-Model:` trailers. `aggy attribution wire [--dry-run]` installs the hook, on explicit opt-in, per repo: a `commit-msg` hook in the repo's common git dir, so it covers every worktree of the repo, edit borrows' included. It is written through the manifest, so `aggy unwire` removes it. aggy never replaces a hook: when a `commit-msg` hook already exists, or `core.hooksPath` is set at any scope, wire refuses (chaining is a follow-up). wire reads git config with aggy's scrubbed environment, so a `core.hooksPath` set only through `XDG_CONFIG_HOME`, `GIT_CONFIG_GLOBAL`, or `GIT_CONFIG_COUNT`/`KEY`/`VALUE` is not seen, and the hook is then installed where git never runs it. The hook is fixed text with nothing from the repo in it; it adds trailers only when `AGGY_VENDOR` is set, and only values of 1 to 64 characters from `[A-Za-z0-9._:-]`, and a failure never blocks the commit. The trailers are a record anyone can write, so aggy uses them only to steer routing (section 8), never to grant anything. They also feed routing stats (M4).
- Desktop notifications (`internal/notify`) when the CLI on screen waits for the person (its `Notification` hook: Claude and Grok), a borrow finishes, or a limit is recorded. Off by default; `[notify] desktop = true` in the user config turns them on, and a repo's config cannot (it rejects the key). macOS runs `/usr/bin/osascript` with a fixed `on run argv` script and the title and body as its arguments, so no text is ever compiled as AppleScript; Linux runs `notify-send -- <title> <body>`. Both start through `internal/execrun` (`NotifyRunner`: the scrubbed environment plus the session bus and display variables notify-send needs, a 5-second limit). The text is aggy's own (vendor names, borrow kinds, outcome classes, a time), never a payload's message, a session id, a path, or an environment value; it is still stripped of control, format, and markup characters (`< > &`) and a leading `-`, and capped at 64 and 200 characters. One kind is shown at most every 30 seconds, and only one runs at a time, so a process flooding hook events cannot flood the desktop. A missing tool or a failure shows nothing and says nothing. Not yet checked on a real desktop: the tests check the commands, not what a desktop shows.

## 17. Testing

CI never signs in to a vendor.

- Unit tests cover routing, briefs, budgets, config patches, and `aggy unwire` restoring files byte for byte. Every patch aggy can make has golden diffs (`internal/parity/testdata`). The M0 gate (`TestM0Gate`) builds a temp HOME with realistic vendor config (TOML and JSON, comments, CRLF, no trailing newline, a fake credential), applies setup-style patches through the manifest over several runs (including a create with an explicit mode, a file at a non-default mode under a 077 umask, a failed run that made directories, a pending change whose write happened, and a mode another tool changed afterwards), checks the dry run's diff lines, runs `aggy unwire --all`, and requires every file byte-identical with the same mode and no extra file or directory. It runs on macOS and Linux in CI.
- Fake CLIs (`fake-claude`, `fake-codex`, `fake-grok`) follow scenario files. They honor flags, print terminal output, call hooks with recorded payloads, write session files and images where the real CLI does, and raise limit errors.
- End-to-end tests drive the supervisor in a pseudo-terminal against the fakes, on macOS and Linux.
- Fixtures are real outputs scrubbed of home paths, emails, and tokens. CI fails if a fixture holds one.
- Tests that touch home paths set `HOME` to a temp dir.
- Real-vendor smoke tests are opt-in and run locally, because they spend quota.
- Before each release, a handoff evaluation checks that a new child states the goal and next step correctly in 9 of 10 recorded handoffs.

## 19. What stays outside

- A runtime aggy owns, with its own tool loop and stored vendor credentials
- One live cross-vendor session: shared hidden reasoning, shared tool-call ids, or a command that survives a switch
- Mid-turn handoff of a running test
- Team logins and unattended fleets
- An LLM router inside aggy
- Image or research MCP servers that call a vendor API with a key
- An aggy-drawn screen that redraws the thread
- An aggy model picker inside a session; each vendor has one (`/switch` only chooses what a launch starts on, section 5)

- Any proxy or compressor in front of `claude`, `codex`, or `grok` that the user did not turn on as a local proxy tool (T6780)

## 20. Decisions

- **Pass-through, not a screen.** aggy stays the parent process and relays a pseudo-terminal unchanged. Drawing its own screen would duplicate each vendor's UI and break with every release; `exec` leaves nothing to perform a switch.
- **Brief without a model, as a file.** The vendor being left may be out of quota, and a brief must not cost a model call. A file avoids `ARG_MAX`. The task file, kept during the work, is a better source than a summary written at handoff.
- **Key plus turn-end hooks.** A reserved key works the same in every CLI, and hooks say reliably when a turn has ended. A skill can also request a switch.
- **Borrows are a shell command.** MCP tool calls time out on long headless runs, and a shell command behaves the same in all three harnesses.
- **The agent picks the kind, aggy picks the vendor.** The agent already understands the task; a static table makes the vendor choice predictable, cheap, and editable.
- **Go.** A single static binary, mature pseudo-terminal support, pure-Go SQLite with no cgo, and simple macOS and Linux builds.
- **SQLite index in `~/.aggy`.** One index for every directory, safe across processes, with leases for busy sessions.
- **`Ctrl+\` as the switch key.** Not a known shortcut in any of the three CLIs (to be confirmed in M2), configurable, and sent through when pressed twice.
- **MIT license.** The shortest and best-known license. It gives up only Apache-2.0's patent grant, which rarely matters for a CLI wrapper.
- **Windows after 1.0**, on a pseudo-terminal library that supports ConPTY, so it is a port rather than a rewrite.
- **Managed tools switch off cleanly, at zero tokens, and are ready to switch on** (2026-10-27). Every tool, plugin, skill, and MCP server aggy manages, aggy's own skill included, can be turned off per vendor, and off leaves no trace in what any agent loads: no MCP entry, no skill link, the skill on the ignore list of a CLI that scans shared skill folders, no text-injecting hook, and no line in memory, the brief, or the missing-tools list, proved per vendor by a test. `aggy tool list` and `aggy doctor` show each tool's estimated token cost per vendor, so the cost is visible before it is paid. Tools are installed once at a pinned version with any index prebuilt and stay ready while off; `on` and `off` only rewire, on the command line of the next launch or resume (a manifest config edit only for a CLI without a launch flag), and take effect at the next turn end, resuming the same session where the CLI allows it, never mid-turn.
- **Tool scope is per repo, set in aggy's state, and wired at launch** (2026-10-27). A tool is on per vendor and per repo, stored in `~/.aggy`; a repo can never turn a tool on, only off (`tools_off` in its `.aggy/config.toml`), so cloning a repo cannot start an MCP server. Each session aggy launches gets its tools on its command line (Claude `--mcp-config`, Codex `-c mcp_servers…`, Grok an `--agent` file with `mcpServers`), with a manifest config edit as the fallback for a CLI without a launch flag. `--tool` on `aggy switch` and `aggy borrow` turns a tool on for one session only; research, news, image, and video borrows refuse file-reading tools. The CodeGraph index is built lazily per repo and copied to a worktree only when a session there uses it. A CLI's own subagents get their parent session's tools until a CLI can scope an MCP server to a subagent.
- **One permission model, Claude Code's** (2026-11-06). The goal is that aggy feels like one harness, so an approval given once holds on every CLI. Claude's format is the shared one because Grok already reads it, and auto mode is the intended setting because it removes routine prompts while a classifier still stops things like `curl | bash`, where removing every prompt would leave only deny rules that match command text. Rules are passed at launch rather than copied into vendor config, and aggy does not answer prompts on the screen, since one misread dialog could approve the wrong thing.
- **OpenCode on screen for ChatGPT and SuperGrok plans** (2026-11-06). Each on-screen CLI costs switching, hooks, first-screen, and permission work, and those plans can sign in to OpenCode, so one harness can carry both and fewer harnesses need that work. A plan may then need a second login for borrows, which stay on the official CLIs because their lockdown is built and tested. The cost is losing the Codex and Grok interfaces on screen, and depending on vendors continuing to allow this, which the version check re-reads.
- **OpenCode defaults to a whitelist, with full auto as a setting** (2026-11-06). The owner wants routine work to run without prompts, and OpenCode has no classifier, so the reason recorded above for choosing auto does not hold there. A whitelist of exact commands keeps routine work silent and stops most of the unexpected at a prompt, though not all (section 15). It costs some prompts, and it rests on three sources (shipped, the person's approvals, and confirmed suggestions from Claude Code history). Full auto stays available in trusted repos.
- **OpenCode promises guardrails, not protection from a hostile repo, and splits by trust** (2026-11-06). Without an OS sandbox aggy cannot enforce more, and tests showed it, mostly against a fake model; waiting for a sandbox would have held up ChatGPT and SuperGrok on screen indefinitely. The owner wants the full screen's model command for daily work, and a repo's screen plugin runs there with no way to stop it, so trusted repos get the full screen and others get `mini` or a pointer to Claude Code. A repo's own OpenCode config stays off even when trusted, unless asked for, because it can disable the whitelist and guard.
- **The OpenCode guard scans raw text for names, and does not parse shell** (2026-11-07). Two reviews in a row got past a word parser, and it refused 33 of 105 everyday commands, heredoc commit messages among them. A scan for a list of variable and function names, with no quote awareness, refuses every shape those reviews found that changes a whitelisted command with no prompt, at the price of refusing a commit message that names `PATH` beside an allowed command, and of leaving a name built at run time to the OS sandbox (T6939). It runs only when the text holds an allow rule, since otherwise OpenCode asks and the person sees the command, which leaves 0 of the 105 refused and 4 of a further 83. Its gap is a command the person approved earlier in a way aggy cannot see, such as Always allow in OpenCode opened by hand. The scan is skipped under `--auto`, which has nothing for it to protect. This was the T6932 orchestrator's call, flagged for the owner.
- **API keys go to open harnesses only** (2026-11-06). Keys are for OpenCode and Hermes, which are built to run any model; Claude Code, Codex, and Grok stay on their subscriptions, so a key cannot change their billing and their login tokens never pass through a translating proxy. aggy stores the keys the person adds, in the OS keychain, because one place to add a key is part of feeling like one harness and beats the plain files some harnesses use. This reverses "aggy holds no keys" only for those keys; vendor logins stay out of reach. Hermes is included, despite weaker key and read protection than OpenCode, for its use as a personal agent as well as a CLI.

- **Conservative calls in shared permissions, for the owner to check** (2026-11-07). The owner settled four in review: exact run commands wait for trust rather than being dropped (wildcards stay dropped), `aggy trust --opencode` counts as trust for aggy's rules, a repo's `settings.local.json` allows wait for trust, and an untrusted repo gets only known read-only forms. A bad untracked `settings.local.json`, or a bad untracked link in its place, withholds aggy's allows, and a tracked one does not, so a planted `.git` with an empty index could make a repo's file withhold them. `bypassPermissions` refused as an aggy setting. In an untrusted repo git gets only the six pinned forms, so a bare `git diff`, `git log`, or `git show` waits for trust, though the owner named those programs as read-only, and `rg` applies only with no flags; the owner can overrule this. The held-rules launch note is on OpenCode only, as Claude and Grok read that file themselves. Codex's allows carry only into trusted repos, and Grok's as exact commands. Non-git folders do not read a `settings.local.json`. A confirmed suggestion is an exact command at repo scope. T6912 to T6916's builder's calls, none run live.
